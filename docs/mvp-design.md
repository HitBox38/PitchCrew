# MVP design

Pitchcrew is a personal job-search workbench. The same React renderer opens in a browser or a sandboxed Electron window; both use a daemon bound to 127.0.0.1.

Visual language: claymorphism and wabi-sabi used as materials rather than decoration. Paper: the page, sheets and documents are flat rice paper with grain and hairline edges. Clay: only things you press (buttons, job cards, the active tab or nav item, the select) have volume; pipeline columns are trays pressed into the paper. Wabi-sabi: natural dye colours, radii a hair off symmetric, and no ornaments, slogans or fake controls. Copy is plain and specific, and summaries come from board data. Tokens: paper #f2f1ec, surface #f8f7f3, sumi ink #2b2d31, muted #61646b, aizome indigo #3a5482 (actions only), teal #2f6a69 (Scout), plum #76517a (Writer), moss #53673d (success, Reviewer), ochre #82601c (awaiting approval), rose #9f4757 (closed). Dark mode follows the system by default; a System / Light / Dark switch in the sidebar overrides it and is remembered in the browser. public/theme.js applies the choice before the first paint, and every colour, shadow and texture is a token redefined under :root[data-theme='dark'], so clay keeps a faint top-left rim and the dyes are lifted for contrast. Typography: locally bundled Fraunces for headings and Source Sans 3 for body text. Left-aligned navigation and a spacious horizontal pipeline make application progress the main visual.

```
sidebar (shadcn)            | toggle · running roles
  search ⌘K · new job N     | page heading + data summary / add job
  board › stages · crew …   | pipeline / closed toggle, filter
  crew status · actions     | pipeline trays / job cards
  recently opened           | recent board events
  theme · data folder       |
```

The board is the product's organizing structure. Cards show company, role, location and salary, fit, owner or state. A detail sheet contains the packet and immutable history. Empty states offer add-an-opportunity and explicitly labeled example-data actions. No fictional data is presented as a live job search.

The desktop window adds a 40px draggable paper title bar above the shared renderer. macOS keeps its native traffic lights; Windows and Linux use native window-control overlays. The title bar and controls follow the app's saved Light / Dark / System choice. A sandboxed CommonJS preload observes the resolved theme and sends only validated theme values over a main-frame, origin-checked IPC channel; Electron APIs stay isolated from the page. The sidebar starts below the title bar, and macOS fullscreen hides that row.

Packages: core (contracts and transitions), board (SQLite events and projections), adapters (demo, Claude Code, Codex), packet (evidence validation and files), mcp (role-scoped tools), orchestrator (HTTP daemon and run scheduling), ui (shared renderer), desktop (Electron host).

The sidebar is the shadcn Sidebar: it collapses to an icon rail with tooltips (⌘B/Ctrl+B, the toggle or the edge rail), remembers that state in a sidebar_state cookie, and becomes a sheet below 768px. It holds search (a cmdk command palette over views, jobs, roles and actions, ⌘K/Ctrl+K), new job (N), workspace navigation with counts and a collapsible list of pipeline stages that scroll to and highlight their column, crew status opening role chats with a Chat / Configure / Pause menu, recently opened jobs (kept in localStorage), a theme menu, and the data folder with copy-path. UI interactions use shadcn/ui source components: buttons, text inputs, selects, checkboxes, tabs, dialogs, side sheets, sidebar, command, dropdown menus, tooltips and kbd. Base UI (@base-ui/react) provides focus trapping and keyboard behavior. Styling keeps the workbench identity through shared Tailwind theme tokens and scoped CSS. Fonts are bundled locally, with no third-party font requests.

Tooling uses Oxlint, Oxfmt, Vite's Oxc React transforms, and Rolldown. tsdown builds the Electron main process. TypeScript remains the type checker; ESLint and Prettier are absent.

MVP flow: add lead (or scan saved job sources) → scout evaluates → shortlist → writer drafts → reviewer requests changes or agrees → request local export approval → approve/reject → export packet. Track manually submitted applications and interviews. Export is deliberately local; read-only connectors do not send or submit. Opt-in [local browser computer use](computer-use.md) now supports individual user-approved form interactions.

Real runtime launches begin with user chat or workflow actions and may continue through bounded board-backed crew tasks. Provider CLIs receive isolated role folders and scoped MCP tools; their own sign-in stays with the CLI. No shared runtime sessions. Demo is deterministic and labeled. Stored routines schedule agent tasks while the daemon runs, and an optional per-user background service starts the daemon at login. [Job discovery](job-discovery.md) reads user-saved public Greenhouse, Ashby and Lever boards through fixed read-only endpoints; other job sites stay manual.

Claude Code, Codex, Gemini CLI, OpenCode, GitHub Copilot CLI, Cursor Agent, Goose, Kiro CLI, Grok Build, Pi and oh-my-pi implement the same adapter contract. Gemini CLI receives per-run system settings that disable built-in tools, extensions, skills and hooks and allow only the Pitchcrew MCP server. OpenCode receives isolated configuration and a fresh primary agent with deny-by-default permissions, only Pitchcrew MCP tools allowed, external plugins disabled and session sharing disabled. Its credential data directory stays with the CLI; user config and custom provider definitions are not imported. Copilot CLI isolates its configuration, disables hooks and session export, and exposes only Pitchcrew MCP tools; native keychain/environment sign-in is required because configuration-file credentials are not imported. Cursor Agent uses isolated settings, deny rules for shell/files/web and an allowlist for Pitchcrew MCP tools, without force or automatic tool review. Builds before 2026.09.26 are rejected because global MCP discovery is not isolated. Goose uses an isolated config/data root and a recipe with only Pitchcrew MCP. It supports an explicit allowlist of API/local-model providers and excludes providers that spawn another agent CLI with native tools. Recipe prompt parameters preserve job/profile text literally instead of compiling it as template source. Kiro CLI uses one V2 ACP session and an isolated custom agent exposing only Pitchcrew MCP, with external MCP and powers disabled. ACP filesystem/terminal capabilities are disabled and permission requests are cancelled. Goose uses native keyring/environment authentication; Kiro uses native headless API-key authentication. User config-file credentials are not imported. Grok Build isolates its configuration and uses only native MCP search/call helpers, with a permission allowlist for Pitchcrew and denials for file-backed arguments; other built-in/hosted tools are excluded. Pi loads only its native MCP extension with direct scoped tool exposure and disables built-in tools and ambient resources. oh-my-pi waits for native MCP readiness, exposes only the scoped MCP tools and disables ambient discovery, memory and auto-learning. Each uses a fresh isolated configuration; Grok, Pi and oh-my-pi use native environment authentication without importing login files. Minimum-version checks reject CLIs that lack the required scoped tool controls. Runtime-managed policy and account extensions remain the runtime's responsibility. Adapter contract tests use fictional subprocesses without provider calls.

Every card/crew/approval/run/message/proposal/task change appends a versioned event and updates its projection in one SQLite transaction. Old event decoders are retained. Approval tokens bind a card, exact packet snapshot, action, and digest; the MCP export gate consumes the token once. Agents have no approve tool. HTTP user mutations require a same-origin session and application header. Run capabilities expire when a run finishes.

Verification covers actual HTTP and MCP stdio flows using fictional sources, plus an isolated Electron/production-daemon smoke test with screenshot evidence. Packet lint validates registered source quotes and the user's [packet rules](packet-rules.md) and reports formatted page counts; it does not prove the factuality of every free-form sentence. The full packet remains subject to independent review and user approval. Provider integrations have been checked against installed CLI help and mock process contracts, without spending tokens on live runs.

## Agent conversations

The chat view pairs a conversation rail with a transcript and a compact job-aware composer. Role-colored identity, real availability state, readable message widths, date dividers and sender avatars make each conversation easy to follow. Role-specific starter prompts focus the composer. Job and recipient choices use Base UI selects. A separate Crew work tab surfaces proposed changes and follow-up history, with pending-work counts and current/proposed instruction comparisons; decisions stay out of the transcript. Vercel AI Elements conversation/message/prompt-input source components are adapted to Base UI and existing paper/ink/clay tokens. Text-only input, Markdown replies, status feedback, accessible keyboard submission and scroll-to-latest controls are supported. Optional file uploads, screenshots, response branching and diagram/code plugins are omitted. Remote Markdown images are not loaded. The view is lazy loaded so chat rendering dependencies stay out of the board’s initial bundle.

Chats use isolated runtime CLI calls through the adapters, not a provider loop in the orchestrator. Direct user chats belong to one role; board-backed crew messages are visible to all roles and the user. A scoped run may only read its role’s direct chat and the crew conversation and only change its attached job. Responses to crew tasks are pinned to the explicit task request, even when other messages arrive.

Message/invocation tools append a visible message and a queued task. The daemon launches follow-ups after parent completion, serializes work on a role/card, and caps each user-started chain at six tasks across descendants. Failed/cancelled parents cancel queued descendants. A user cancellation stops running siblings and queued work in the chain; daemon restart marks interrupted runs and queued/running tasks failed. No runtime session is shared. Workflow invocations reuse the packet evidence checks and state machine. A chat can shortlist a lead or request changes; it cannot skip review, approval, export or manual tracking. Requesting changes invalidates outstanding packet approvals.

Role capabilities control messaging, invocation and workflow changes at the daemon boundary. Agents can only propose their own instruction/capability changes, capped at three proposals per run. Explicit user decisions apply them after active runs finish or decline them. Proposal decisions and role settings are serialized against concurrent starts. Event version 2 adds chat messages, proposals and tasks; retained version 1 events remain decodable and replayable.

## Read-only workflow connectors

GitHub and Google Workspace use the existing scoped MCP gateway. Connector clients and authentication live in `packages/mcp/src/connectors/`; credentials remain in the daemon and never enter role prompts or runtime MCP configuration. Google Desktop OAuth uses PKCE and a dedicated temporary loopback callback; GitHub uses user-selected fine-grained repository tokens. Gmail, Drive/Docs, Calendar, Sheets and GitHub capabilities are disabled per role by default and enforced on each gateway call. Event version 3 adds these optional capabilities while retaining both older versions. Account changes require the local UI session. External source content does not bypass local profile quotation checks. Outward connector actions remain deferred and must use an exact-payload approval gate when implemented. See [connectors.md](connectors.md) for setup and tool coverage.
