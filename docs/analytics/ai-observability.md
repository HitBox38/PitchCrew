# AI observability

Pitchcrew launches runtime CLIs through its existing adapters. It does not own the provider model loop. This instrumentation observes actual workflow/chat turn boundaries and adapter execution; it does not represent each turn as a model generation.

Each admitted turn gets a new telemetry-only UUIDv4 trace ID. Each actual adapter invocation gets a separate telemetry-only span ID. These IDs never derive from board runs, conversations, roles, jobs, sessions or capabilities and are not persisted. The daemon records a native `$ai_span` before the final `$ai_trace`. Names are fixed: `runtime_execution`, `workflow_turn` and `chat_turn`. Mode and outcome use closed vocabularies; duration uses a monotonic clock and native `$ai_latency` seconds.

Trace duration includes admitted setup and result handling, ending before browser cleanup. Span duration covers the adapter call, including its CLI execution and normalized result parsing. Setup failure creates only a failed trace. A successful adapter call followed by invalid packet handling can yield a successful runtime span and a failed turn trace. Waiting for user input and cancellation are separate outcomes and do not claim provider errors.

Source extraction, document-correction stages and deep-review stages use the same lifecycle, including setup and result-validation failures. The managed deep-review orchestration also finishes its own trace; it has no adapter span of its own. Each stage's terminal trace and actual runtime span share a telemetry-only `$ai_trace_id`. Failed traces retain the closed `failure_category` and `$ai_error` label even when runtime execution succeeded or never started.

Compare terminal workflow failures with failed `$ai_trace` outcomes, rather than assuming every failure has a failed `$ai_span`. The renderer's `run_finished` events remain session-observed aggregate measurements without trace IDs: nested workflow runs, setup/processing failures and independent sampling mean their counts need not equal runtime-error spans. Review seat reservations are excluded from run metrics because they do not execute work. This repair cannot identify the eight historical unmatched outcomes in [Inbox report 934f7545](https://eu.posthog.com/project/295060/inbox/reports/934f7545-3c74-46c4-9f84-bd70dba0578b); validating production coverage requires an updated build and consented traffic.

The standard runtime contracts expose replies/workflow results without normalized token counts or cost. No `$ai_generation`, token/cost estimates, model/provider identity, prompts, replies, reasoning, tool arguments/results, session IDs, errors, paths, credentials or content are captured. Installing provider-specific PostHog plugins would introduce a separate telemetry path and is not part of this implementation.

The optional `CrewContext.diagnostics` sink writes only to the coordinator's bounded nonpersistent buffer; the daemon has no outward analytics client. The elected renderer relays new observations only while production analytics, master usage consent and diagnostic consent permit it. Closed sanitizers run on both sides and fail closed for unknown events or invalid measurements. Normal failures retain the original thrown error and application behavior.

`observed_start_ms` is internal bounded numeric metadata for the coordinator to convert to SDK capture `timestamp`; it must be stripped before ingestion. Start timestamps permit native waterfalls to display the operation start despite completion-time delivery. If an integration does not supply capture timestamps, the native event timestamp reflects delivery and cannot be treated as an exact timeline. No backend history should be flushed after consent is enabled. Closed renderer windows, an exhausted/expired buffer or renderer leadership changes can lose observations. These are observed samples, not a complete audit trail.

The combined [AI & MCP dashboard](https://eu.posthog.com/project/295060/dashboard/1018318) has three native AI trend queries for outcomes, duration by mode and runtime execution latency. Its eight AI/MCP trend charts are included in an active weekly chart-only subscription. Queries and layouts were read back and executed successfully; real native AI/MCP observations are present in released builds. Empty outputs remain no samples, and token/cost/generation coverage remains Not collected. See `posthog/activation.json` for the activation audit.

Verification uses fictional local fixtures and no provider calls. Tests assert actual workflow/chat lifecycle wiring, exact result/error preservation, seconds timing, child-before-parent ordering, cancellation/waiting, disabled-buffer behavior, and rejection/removal of private fields.

Native schema references: [manual capture](https://posthog.com/docs/ai-observability/installation/manual-capture), [spans](https://posthog.com/docs/ai-observability/spans), [traces](https://posthog.com/docs/ai-observability/traces).

Failed native traces/spans now include a closed `failure_category` and matching `$ai_error` label. Only fixed labels are sent, never the source exception. A failed runtime span classifies the adapter boundary; a later processing failure can still produce a completed span and failed trace. These fields require the audit repair release and cannot reconstruct earlier unknown errors.

CLI and ACP premature exits retain optional `runtime_exit_code` (an integer from 0 through 4,294,967,295) and `runtime_exit_signal` (a fixed allowlist of OS signal names). Both the daemon and renderer sanitizers accept these fields only on failed `process_exit` observations; null codes and unknown signals are omitted. The fields do not include stderr, output, provider identity or arbitrary exception properties. A zero exit code can still mean an incomplete ACP turn. These diagnostics help distinguish future failures; they cannot establish the cause of historical `other` or `process_exit` samples or guarantee that provider failures have stopped.

Workflow result rejection retains a fixed local error code across the adapter's user-facing error wrapper, so empty, malformed, schema-invalid and role-mismatched results reach native spans/traces and operational logs as `validation` rather than `other`. The existing local error message is preserved; result text and validation details never enter telemetry. `process_exit` identifies a nonzero or signal-terminated CLI process but does not expose private stderr or establish the underlying provider cause. Unclassified errors still use `other`; historical unknown failures cannot be attributed to result validation from these observations alone.
