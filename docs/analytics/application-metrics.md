# Application metrics

Application metrics measure deliberate UI API requests and terminal workflow/chat runs observed in the current renderer session. These are client-observed measurements, not complete daemon or infrastructure monitoring. They are separate from provider token usage and cost.

## Collection

`Analytics/metrics/requests.ts` starts a monotonic timer for API calls matched by the fixed usage-action route allowlist. `api.ts` ends it after response JSON parsing. The duration includes the network, daemon and JSON parsing. Results are `success`, `http_error`, `network_error`, `invalid_response` or `aborted`. HTTP responses with invalid JSON remain HTTP errors when their status is unsuccessful; successful responses with invalid JSON use `invalid_response`. Existing HTTP error messages, network errors and abort exceptions remain unchanged locally. Measurements never include those messages.

`api_request_finished` contains only `operation`, `result` and `duration_ms`. Operations are fixed usage-action names (for example `chat_sent` and `job_created`), not API URLs. Snapshot/config reads, polling, previews, embedded browser input, streams and lease renewal do not match this allowlist. This intentionally covers reviewed actions rather than every request.

`Analytics/metrics/runs.ts` observes workspace snapshots without another poller. A run must first appear running or waiting, have a valid start timestamp at or after this observer's installation, and then reach completed, failed or cancelled. Earlier active runs, historical terminal records and completions whose active state was never observed are excluded. Fast runs completing between snapshots can be missed. Waiting is not counted as a terminal failure or success. `run_finished` contains only `mode` (`workflow`/`chat`), `outcome` and an optional `duration_ms`. Legacy runs without `mode` use their existing workflow default. Duration uses daemon start/finish timestamps, includes waiting time when applicable, and requires a finish at or before observation and a nonnegative interval no greater than 24 hours. Missing, inconsistent or excessive timestamps omit duration instead of emitting zero. Start timestamps that appear in the future are not admitted.

Correlation IDs remain local. The observer retains at most 512 IDs of at most 128 characters; terminal entries remain for deduplication. At capacity it stops admitting new runs rather than evicting entries and risking duplicate counts. Cleanup and any master/diagnostics consent change clear correlation and establish a new observation boundary. A closed app or disabled diagnostics omits activity; there is no later backfill.

`installApplicationMetrics(config, runLeadership)` accepts a shared leadership predicate for run collection while deliberate API request metrics remain per renderer. The integrated coordinator should pass `isDiagnosticLeader` from the shared telemetry leadership module and use `useDiagnosticLeader` as an installation effect dependency, so leadership transfer resets observation rather than replaying another tab's backlog. The standalone slice defaults to a true predicate for its tests. With that default, multiple opted-in tabs can each observe a run; do not call these canonical daemon-wide run totals or unique run counts. Same-origin leadership reduces duplicate tabs; browser and Electron origins/devices still have separate observation sessions. Counts represent observed sessions.

## Consent and transport

Both the usage/master preference and the diagnostics preference must be enabled. Installation telemetry configuration must be available and the analytics SDK ready before collection starts. Development and directly constructed offline daemons retain their existing configuration rules. Pending request measurements are invalidated even when consent is disabled and re-enabled before completion. Run state is cleared synchronously on preference changes. None of this changes job, browser or crew permissions.

The event sanitizer rebuilds both events from fixed enums and bounded numbers, then the existing outbound sanitizer adds reviewed common app-version/renderer/schema fields. No prompts, content, entity IDs, runtime/model choices, paths, URLs, request/response bodies or raw errors enter metrics.

In parallel, `Analytics/metrics/transport.ts` sends numeric OTLP JSON to the configured PostHog ingestion origin's `/i/v1/metrics` endpoint using its existing project token. Authentication uses a Bearer header, never a personal key. The body has a fixed `service.name=pitchcrew-renderer`, optional validated shipped `service.version`, fixed renderer/operation/result/mode/outcome dimensions and numeric samples. It contains no anonymous/user/session ID, SDK-generated URL, machine metadata or arbitrary resource attributes. The browser's usual network connection is required; the daemon has no independent remote metrics sender.

Native series are `pitchcrew.api.request.count`, `pitchcrew.api.request.duration`, `pitchcrew.run.count` and `pitchcrew.run.duration`. Counts are delta monotonic sums of one; durations are delta one-sample histograms in milliseconds. A run without valid duration contributes its outcome count only. Each observation sends one bounded batch containing its count and optional duration, without persistence, aggregation queues, automatic instrumentation or retries. At most two metric sends are in flight; excess native samples are dropped while event capture remains best effort. Each send has a five-second abort deadline. Disable/cleanup immediately aborts pending sends; requests omit credentials, reject redirects and do not use keepalive. Already completed requests cannot be recalled.

This direct numeric transport uses the documented OTLP JSON endpoint instead of the SDK's separately buffered `posthog.metrics` API, so diagnostics consent can discard pending metrics immediately. Tests stub all network calls; no test events or numeric metrics are sent to the live project.

## PostHog resources

`posthog/application-metrics/resources.json` describes the event-based Diagnostics dashboard updates and the native Metrics activation checklist for project 295060. Keep existing unsupported diagnostics tiles until their owning features have real instrumentation; do not treat empty tiles as proof of health. Event charts remain useful even when native Metrics is unavailable.

The current [Metrics documentation](https://posthog.com/docs/metrics) calls Metrics open alpha with 30-day native retention. Before activation, inspect the current project's Metrics onboarding and settings, then select **Enable metrics** if it is still required. No invitation is documented as required. Native ingestion and viewer activation are distinct: shipping code is not evidence that the project viewer is activated or that native samples have arrived. This feature's worktree performs no project writes.

The [JavaScript installation guide](https://posthog.com/docs/metrics/installation/javascript) documents the numeric SDK API, and the [architecture guide](https://posthog.com/docs/metrics/architecture) documents OTLP JSON/protobuf at `/i/v1/metrics`. Recheck these alpha contracts during deployment. The coordinator activates resources after all feature branches integrate and checks pass.
