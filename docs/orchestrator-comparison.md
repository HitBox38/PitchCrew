# Orchestration comparison with T3 Code

Reviewed against the local T3 Code checkout at `D:\CodeStuff\t3code` on 2026-11-07. These are source-backed findings, not a claim that either app has been exhaustively tested. T3 Code files below are reference paths in that checkout; Pitchcrew paths are relative to this repository. This review borrows design principles, not source code.

## Assessment

Pitchcrew's weakest orchestration boundary is uncertainty: a user can lose the response to a message send, and a daemon crash can erase the public activity explaining what happened. Adding more agents or more animation would not fix either problem. T3 Code has a clearer model of command acceptance, execution, and durable observation.

Pitchcrew already has meaningful safeguards. `crew/queue/admission.ts` reserves launches before asynchronous setup and prevents overlapping use of a participant's session. `crew/delegation-rounds.ts` records parent/delegate/collection dependencies and bounds follow-up work. `crew/lifecycle.ts` reconciles interrupted runs and queues and expires browser approvals. The scoped MCP gateway and explicit export/submission approvals are appropriate for a job-search app. None should be weakened to mimic a coding tool's broader permissions.

## First version and acceptance evidence

A synthetic benchmark confirmed material history-dependent queue cost. With one active queue held constant, median `activeQueues` time was 0.873 ms at 120 completed runs / 100 completed tasks, 34.028 ms at 12,000 / 10,000, and 366.537 ms at 60,000 / 50,000. Median `workspaceQueue` time was 2.524 / 72.149 / 826.703 ms respectively. The next iteration implements indexed lifecycle queries in `crew/queue/queries.ts`, preserving controller-owned terminal cleanup, completed-parent lookups, reservations, paused failures and job/routine/delegation scope. On the same synthetic workload, `activeQueues` medians became 0.256 / 0.260 / 0.251 ms and `workspaceQueue` medians became 0.867 / 0.822 / 0.815 ms. These are synchronous function timings under Bun 1.4.4 on this Windows machine, with warm SQLite caches, setup excluded, minimal valid settled chains, alternating method order and five to seven samples after warmup. They are not end-to-end UX latency or a measurement of T3 Code's speed. Other card/conversation/question/history scans remain. The baseline reproducer, source hashes and full timings are retained in `C:\Users\spide\AppData\Local\Temp\pitchcrew-queue-benchmark-02b8921eb9f7472da23d70228589837d`; after evidence is in `C:\Users\spide\AppData\Local\Temp\pitchcrew-queue-after-4d36799198344045abde94e38fe2301a`.

The first implementation covers idempotent conversation sends with response reconciliation, bounded durable public activity that retains the newest useful work, and recovery from silent chat streams. Server receipt handling lives in `packages/orchestrator/src/crew/chat-submissions.ts`; renderer reconciliation lives in `packages/ui/src/ChatView/composer-receipts.ts`. Activity checkpointing lives in `packages/orchestrator/src/crew/chat-activity-checkpoints.ts`. The stream watchdog resets on received bytes, including the daemon's 15-second heartbeats, and disconnects after 45 seconds of silence so existing snapshot/reconnect recovery can clear stale overlays. T3's corresponding supervision is in `packages/client-runtime/src/connection/supervisor.ts` and `packages/client-runtime/src/rpc/protocol.ts`. The later priorities remain follow-ups.

Required evidence includes concurrent reuse of the same client request ID, rejection of a changed payload, receipt recovery after restart, and renderer handling of acknowledged, rejected and still-uncertain sends without discarding a new draft. Activity checks must cover saturation, late step completions, checkpoint flushing, restart recovery, privacy limits and backward-compatible decoding of versions 1–35 alongside new version 36.

Automated tests may use deterministic adapter fixtures to exercise races. They do not establish live runtime compatibility. `scripts/orchestrator-live-smoke.ts` is an explicit opt-in production-daemon smoke using installed Codex and Claude Code, a new temporary workspace, a fictional profile and scoped MCP calls. It does not select Demo, access the user's Pitchcrew workspace, install software, or perform outreach. It checks parallel actual runs, observed profile/progress tools, receipt replay and restart persistence. Live model answers and provider availability remain nondeterministic, and a graceful restart is not a process-kill crash test.

The live smoke passed on 2026-11-07 at 12:01 UTC in about 35 seconds using `gpt-6.1-sol` and `claude-opus-5-5`. Both runs were observed concurrently, both used the scoped profile and public-progress tools, concurrent exact send replays created one provider turn each, and receipts plus settled public activity survived a graceful daemon restart. The JSON result is retained as `smoke-result.json` in the fresh temporary workspace printed by the harness. It ran under the installed Bun 1.4.2; this is below the repository's pinned Bun 1.4.4, so it is evidence about that installed environment rather than validation of the pinned version. Root TypeScript checking and linting of the smoke script passed. Full regression checks and independent patch reviews are separate acceptance evidence.

A separate `scripts/orchestrator-crash-smoke.ts --run` passed at 12:13 UTC under Bun 1.4.4. It launched its own production daemon process with a new fictional workspace, observed both actual providers running with durable public checkpoints, and hard-killed only that tracked process tree. After restart, the original checkpoint entry IDs were retained, unfinished commentary/phase markers became interrupted, and replaying accepted send IDs created no new runs. It does not establish full browser UX or final-answer correctness for the intentionally interrupted turns.

## Avoid a rewrite

T3 Code's orchestration contracts encompass native provider children, coding worktrees, checkpoint rollback, several environments and a durable effect outbox. Its main `Orchestrator.ts` alone exceeds 14,000 lines. Pitchcrew does not need that entire surface. Its domain should remain jobs, crew conversations, reviewed packets and controlled submissions. Borrow the durable command boundary and truthful execution visibility first; evaluate the later improvements independently.
