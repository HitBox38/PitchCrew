# Lifecycles

Rules for contributors and coding agents. If a change makes anything here false, update this file in the same change.

Every persisted status has one lifecycle table in `packages/core/src/lifecycles.ts` (zod-free, also `@pitchcrew/core/lifecycles` for the UI): runs, crew tasks, per-recipient message deliveries, questions, packet and browser action approvals, submission attempts, deep reviews and their subagents, delegation rounds, role/skill proposals, profile updates and tracking signals, beside the job workflow graph. A table lists the statuses, the only moves between them and named status sets (`approvalLifecycle.is('open', status)`, `runLifecycle.is('live', status)`, `deliveryLifecycle.is('unsent', status)`); use a set instead of spelling a status list inline, and add a set when two call sites need the same list. `board.record` checks every write against its table inside the write transaction (`board/lifecycle.ts`): creation in any status and writes that keep the status always pass, and replay never rechecks history. Tests run with `PITCHCREW_LIFECYCLES=enforce` (set in `scripts/test-setup.ts`), where an undeclared move throws a `LifecycleError` naming the allowed moves before anything is appended; other daemons save the move, warn once per edge on stderr and record a content-free `daemon_lifecycle_violation` operational log (table name and the two statuses only, through consented diagnostics; see [operational logs](analytics/logs.md)), so a move the tables missed never stops a user's work but still surfaces. A test fixture that must move a status backwards, such as making a finished run active again, uses `rewind` from `packages/orchestrator/test/helpers/rewind.ts`, which switches the board's `lifecycleMode` to `off` for that one write; product code never does. To add a move, change the table, cover the edge with a test and run `bun run docs:state-machines`, which regenerates the diagrams in [docs/state-machines.md](state-machines.md); a core test fails while the document and tables differ. Job statuses are checked by `board.move` (the normal graph) and `board.crewMove` (the normal graph plus `reworkTransitions` in `states.ts`: reviewing an existing packet again from changes_requested, agreed or awaiting_approval, and a correction pass from in_review straight to drafting), with the same enforce/report modes; crew work saving a job with a new status uses `crewMove`, never a raw `record('card', …)`. User and `manageWorkflow` corrections record jobs directly and may set any status.
