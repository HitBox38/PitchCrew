# Pipeline

Rules for contributors and coding agents. If a change makes anything here false, update this file in the same change.

Pipeline (`/pipeline`, view `pipeline`, ⌘/Ctrl+2) is the board. Its title row holds Open | Closed (labelled "Open or closed jobs", with counts, "N of M" while searching), Board | Table beside it (labelled "Pipeline layout"; see Table mode below), Search jobs (all jobs, before sorting and paging; Escape clears), Jump to (the five stages; scrolls to and focuses the column; Board mode only) and Add job with Import applications under its caret. The row keeps one arrangement in both modes: on one line where everything fits beside the segments, else the segments on line one and Search (with Jump to in Board mode) and Add job together on line two, ending on the right, so Add job never wraps alone and switching modes never moves the search to another line; on a 320px phone Board | Table wraps under Open | Closed. Add job's caret, Jump to and each column's Sort are menu triggers, which draw the house focus ring themselves. The page shows exactly four pipeline columns: Leads, Shortlisted, In progress (drafting through awaiting approval) and Applied (submitted through offer); Closed is a separate view. Each column has its own device-saved sort (fit high/low, date added newest/oldest, recently updated, company A–Z/Z–A, title A–Z/Z–A; default fit high to low with unscored last), 20 jobs per page (40 in Closed) with accessible Previous/Next and full counts, and up to five state beads; moves reveal their destination page before focus returns. Drags show a target for each exact status, a grouped column never picks a status on drop, and Move to… keeps every status. Cards show the recorded status for applied/closed jobs and fit as an ink number or a "Not scored" dash. Each column body scrolls on its own; columns keep at least 188px and scroll sideways when four do not fit, and phones show one stage at a time through a stage selector. With no jobs, Pipeline shows its empty state (Load example data on a `--dev` daemon; Add job stays in the title row). The Needs you deck, the tracking review strip and the setup checklist moved to [Home](home.md), which lists every attention item, decides in place what can be decided there and opens the existing form or page for the rest.

**Table mode.** The layout is `?mode=` when a link names it, else the one last chosen on this device (`pitchcrew-pipeline-mode-v1`), else the board; choosing Board or Table saves it and replaces the URL's search (`usePipelineMode`). Table mode (`packages/ui/src/PipelineTable/`, materials in `styles/pipeline-table.css`) lists one row per job in a recessed tray that ends at its last row and scrolls on its own: a real `<table>` with a checkbox, Company (the row's one stop: a header cell holding a button named "{company}, {title}" that opens job details), Title, Stage (the shared stage bead and status), Fit ("Not scored" when unknown), Queue and Updated, under a sticky 40px header, with no zebra rows, uppercase or whole-row colour. Columns fold by the tray's width: Updated below 70rem (so on 1280 and 1366 windows), Stage below 60rem (shown as the title's second line), and below 52rem each row takes two lines, every Queue story one width so its controls start on one edge (below 36rem they share the row's right edge); folded cells stay readable to screen readers. The Queue column widens from 25rem to 27rem at 64rem and to 29rem at 74rem, and Company from 120px to 160px at 65.5rem (1366 and 1440 windows keep whole company names), each step only where the Title keeps the 186px it has on a 1280 window, so a wider window never narrows the Title; a Queue story whose time does not fit beside its words puts the time under them instead of cutting the words. Unchecked boxes keep a muted hairline edge, since their sunken face matches the tray. Phones show the same rows as two-line items (a long story or next step wraps rather than being cut), with each row's fit and control in one right-hand column so fits line up, a View select and a Select toggle that shows their checkboxes. Search filters the table before sorting and paging.

Saved views live in `?view=` (an unknown name falls back to All open): Scope (All open, Needs you), what the crew is doing (Working, Waiting for a slot, On hold, Failed) and Not scored, which Home's "{k} not scored" and a job source scan open. Each counts its jobs ("18 of 38" while searching); Needs you, Working, Waiting for a slot and Failed also show the Queue column's bead they key, an empty socket at zero; below 58rem of width only Scope stays beside a "More views" select. Needs you lists jobs with an attention item and its caption says how many of Home's items it does not list ("3 jobs wait on you · 2 more on Home", linking Home), so Home keeps the one count. Working, Waiting for a slot and On hold follow the job queue's state (On hold counts paused, blocked and waiting queues; a ready queue behind a promoted brief takes no place in line, so it is in Needs you, not Waiting for a slot; and a ready queue whose agent cannot start its next request, paused, with its runtime missing or signed out, or on a runtime that cannot isolate a board action's application work, is On hold, since a free slot would not start it: the server holds such a queue when one frees); Failed uses the app-bar chip's rule, so the two agree for open jobs, while a failed standalone conversation or closed job counts only in the chip and on Home. All open groups its rows as Needs you (attention rank), Working (latest update), Waiting for a slot (place in line), On hold and Nothing queued (latest update); the other views keep that order without labels. In the Closed view the table lists closed jobs newest first, with no saved views, no selection and no Queue column unless a closed job on the page has something to say there (a tracking review, say). Rows page at 40 with Previous and Next always shown and an announced range ("1–40 of 114 jobs"); a new view or search starts at page one.

The Queue cell (`queueStories` in `packages/ui/src/lib/queue-story.ts`) tells the job's story from the first case that applies. Its highest-ranked attention item comes first ("Scout · failed"; ochre, rose for a failure; a browser request says when its run ends, "ends about HH:MM", and other asks their age), ending in one ink control named for the item ("Submission ›", "Question ›", "Failure ›", "Brief ›", "Screening ›") that opens that row on Home and decides nothing; its accessible name starts with that word ("Submission: open Initech’s browser action approval on Home"), so speech input finds it. Else its executing run: plum and breathing, the agent, its work and a compact duration ("12m", "1h 5m"), "+ 1" for another agent on the job, and View opening the run. Else an agent starting before its run exists, a slot reserved for a deep review, or the job's place in the workspace's waiting line: "Scout · Evaluate fit · starting" for the free slots' worth, then "Scout · waiting for a slot · 2nd", counted with standalone conversations by Home's Up next line (`readyLine`), and never a place for a queue behind a promoted brief, whose brief is the job's item, nor for work its agent cannot start ("Scout · paused", "runtime unavailable", "needs an isolated runtime" or "needs sign-in", in ochre: it waits on the user, not for a slot). Else a hold ("paused by you" or the saved reason). Else the job's next step in muted ink (`nextStepText`, which never says "Waiting on you").

Selection spans pages and views, and the header checkbox covers the current page (mixed while part of it is selected). The selection bar docks under the tray, never over a row (the tray, shrinking as it arrives, keeps the focused or just-ticked row in view): "{n} selected · {k} on other pages · {m} not shown · One queued action per job", then Evaluate fit (outline; Add job stays the page's one glaze) and Clear. Evaluate fit checks the snapshot before anything is sent. A workspace reason stops the batch with nothing sent ("Nothing was sent: …"): the Scout seat's checks (`seatBlocker`, which the single Evaluate fit action shares), then a Profile update waiting for recovery; never a reason read from one selected job. Each job is then not sent because it is not a lead, already queued (its fit runs or waits in its job queue, failed fits included, reported before a missing brief so the result matches the Queue column; a fit whose agent cannot start says what starts it, "Already queued · starts once you sign in to Codex in Settings"), not sent for another reason (no brief, or other work running on it or an agent owning it), or sent. Sending is one `POST /api/queue/actions` per job, one at a time in selection order, through `api` rather than the store's action, with `repeat` unset; the server answers a duplicate with the existing request, so a returned id already in the job's queue reads "Already queued". After one reload the result above the table reads "16 jobs · 10 queued · 3 already queued · 3 not sent", says once that each job is checked again when it starts (the server then rechecks the brief against the job source, so a queued job can still go on hold), and lists every job in table order with its place ("Queued · 4th in line") or reason; already queued lines offer Open entry (Queue), named "Open entry for {company} in Queue". A call the daemon refuses reads "Not sent · {server message}". A call that gets no answer (a network failure, or a reply that cannot be read) may still have queued the job, so it is checked against the refreshed snapshot as an answer would have been: a fit request for the job that was not in its queue before the call reads "Queued · {place}", one that was reads "Already queued"; with no such request (a failed refresh, or a fit that already ran) it reads "No answer from Pitchcrew · check this job’s queue before retrying" beside an ochre bead and Check queue (Queue, named "Check queue for {company}"), and the summary counts it apart from "not sent" ("· 1 unconfirmed", shown only then). Queued and already queued jobs leave the selection; jobs not sent or unconfirmed stay selected, and retrying one finds its request rather than adding a second. A batch queues board actions only: it approves, submits and sends nothing, and records no analytics event of its own.

The table's keys work only while focus is inside it, never from the window: j/k and the arrow keys move between rows (focus first, then the row scrolls into view clear of the sticky header), x selects the focused row, Enter opens job details, / goes to Search jobs and Escape clears the selection; keys typed in a field, on a select or with ⌘, Ctrl or Alt are left alone, and so are Shift with an arrow or Escape; holding j, k or an arrow keeps moving, while a held x, Escape or / acts once. A quiet foot shows them with `Kbd` (hidden on phones and touch screens) beside the pager. Closing job details opened from a row returns focus to that row. Queue cell and result links are 44px tall on phones and coarse pointers.

**Board.** One card per application. Allowed transitions live in core. Agents coordinate through persistent board state; launches start with user actions or stored routines and can continue through bounded board-backed agent tasks. Users can register known external submissions with a timestamp and confirmation note without generating or exporting a packet; registration performs no outward action and prevents likely duplicate company/title/URL or job-ID records. Existing pre-submission cards support a narrow user-only external fact registration that rejects active work, retains prior packets without identifying them as submitted, invalidates unused approvals and preserves history. Users can bulk import past applications from JSON or CSV (1,000 rows, 2 MB) through a user-only preview and digest-checked apply: never-submitted rows become packetless leads (or shortlisted/withdrawn), submitted rows reuse external registration and then walk valid transitions with history effective times, taking the shortest valid path when legacy history does not fit. Import never changes existing cards, skips likely duplicates, keeps legacy notes and unfitted history in the tracking note, maps new imports’ weight and lessons to structured learning fields while retaining the original note provenance, and stays retry-safe through a per-row import key in the card event message, so it needs no new event version. `scripts/convert-legacy-tracker.ts` converts a legacy SQLite tracker. Agents have no import tool. User-only drag status changes can record any status without an export; workflow moves and email reconciliation into submitted still require successful current-packet export. Card details expose user-managed job identifiers, Gmail thread links, tracking evidence, learning signals and, for discovered leads, their job source.

**Approval.** Exact packet snapshot and SHA-256 digest bound to a card, confirmed application context revision, independent packet review and export action. It is single-use; export calls enter the shared MCP gate. Agents have no approval tool. Successfully exported current packets allow workflow submission recording. Manual board status changes record user bookkeeping independently and do not authorize export or browser submission.
