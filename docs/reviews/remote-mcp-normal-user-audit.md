## Ranked issues

### 1. Medium — the request link focuses a section that remains offscreen

**Reproduce:** From Board with this fixture pending, open Notifications → Needs you → the fixture's connection notice. Settings search for `Grok` also showed this behavior during this run.

**Expected:** The destination should visibly present the remote request and its review controls, with keyboard focus in that visible area.

**Actual:** Accounts opened at its top, showing Connected services and Local agent apps. The remote heading had keyboard focus but its bounding box started at approximately `y=1046` in a 1280 × 800 viewport; **Approve read-only** began near `y=1396`. I had to scroll to reach the request. This was observed in the actual rendered page and confirmed with read-only DOM geometry. It is different from the earlier reported variant where a centered heading leaves just the approval controls below the fold; I did not reproduce that exact centered position.

**Impact:** A user following the urgent review notice can land among unrelated account controls and wonder whether the connection request arrived. The underlying consent and keyboard path still work.

[Observed landing](assets/remote-mcp-normal-user-notice-landing.png) · [Request after manual scroll](assets/remote-mcp-normal-user-read-only-consent.png)

### 2. Medium — approval feedback keeps saying the app has not finished connecting

**Reproduce:** Approve the fixture read-only, complete the public token exchange, successfully invoke `pitchcrew_status`, and use **Check status**.

**Expected:** The approval feedback should acknowledge completed authorization/request evidence or disappear once the authorized app is listed.

**Actual:** **Connection requests** continued saying **Approved. Waiting for the app to finish connecting; it will appear below.** At the same time, Authorized apps listed the fixture and its **Last successful request** timestamp. This persisted through the subsequent narrow-viewport and Stop-cancel checks.

**Impact:** The user receives incompatible answers about whether the app finished connecting. The actual authorized-app evidence was accurate, and the tool request succeeded.

### 3. Minor — Board gives an unqualified all-clear during pending remote consent

**Reproduce:** Leave Board open and start this fixture's public OAuth connection.

**Expected:** Either include remote consent in the decision summary or qualify that summary as job/application decisions.

**Actual:** Board said **Nothing needs your decision** while the bell showed **1 unread** and its Needs you group contained the pending connection. The notice itself worked.

**Impact:** The prominent all-clear conflicts with the smaller actionable cue. This did not block discovery in the tested flow.

[Board with pending notification](assets/remote-mcp-normal-user-board-pending.png)

The unread count dropping after following the notice was independently reproduced. I do **not** classify that as a separate bug: the control explicitly reports unread notifications, not unresolved decisions. The Board wording and offscreen destination make the loss of that attention cue more noticeable.

## Limits, audit error, and cleanup

- T3 preview tools drove only two owned browser tabs, with UI actions for all local consent, Stop cancellation, and disconnection. Read-only DOM inspection supplied text, labels, focus, and geometry when snapshots were bounded. No local private API was used to make a decision.
- The fixture setup, token exchange, MCP tool list/status, and post-disconnection check used public OAuth/MCP endpoints. The callback deliberately used an unresolvable example host; its browser error is a fixture limitation, not a Pitchcrew issue. Clipboard contents remain unverified. Native Electron behavior, real Grok Bot reconnection, and provider crew runs were outside this independent pass.
- **Audit error:** Before the fixture existed, I clicked **Stop remote connection** intending to open and cancel a confirmation. With zero authorized apps and zero pending requests, Stop intentionally acts immediately. This stopped the supplied test tunnel. I reported the mistake promptly; the parent then explicitly authorized recovery through the visible **Start temporary connection** action. The resulting replacement public address was `https://ocean-eos-first-unavailable.trycloudflare.com/mcp`, was reported to the parent, and was left running. The zero-app immediate Stop is not a product finding.
- Only my fixture grant was disconnected. A rejected HTTP 401 request verified revocation. Fixture secret values were cleared from the temporary in-memory client, and both owned browser tabs were closed.
- The fictional job was unchanged. No crew or agent messages were sent; no crew runs, applications, outreach, job mutations, personal tabs, or production-workspace connector calls occurred. The fixture's public client registration was not separately deleted; its grant is revoked.
