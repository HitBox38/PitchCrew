# Local browser computer use

For the desktop architecture, see [ADR 0003](adr/0003-native-desktop-browser.md). The web viewer keeps the [streaming design and fixture measurements](browser-interaction-performance.md).

Enable **Crew → agent settings → Computer use**. The desktop app uses its bundled Chromium. For the web app and headless tests, install Chromium once:

```sh
bun run browser:install
```

The agent's browser appears inside **Chat → Browser**. Desktop hosts real Electron `<webview>` pages in a permanent renderer host: human input goes directly to the page, and the daemon automates the same pages through a private authenticated CDP relay. The relay exposes only that job/conversation's guest targets, never the app renderer. Guests have no app preload or Node access. Native agent screenshots retain Playwright credential masking but use Electron viewport capture with `stayHidden`/`stayAwake`, avoiding CDP surface readback stalls in hidden Windows guests. Capture waits for credential-mask styles to paint in an isolated world before reading the surface. The paint wait and readback share a bounded deadline. A timed-out paint wait releases the capture queue without reading the surface; the next image still requires fresh credential masks. An actual native copy remains serialized until Chromium finishes it. A CDP screenshot clip places its origin in document CSS pixels (Playwright sends the scroll position for a viewport screenshot; element picks send their box plus the scroll position), while Electron copies a rect of the visible view, so the same isolated-world paint wait reports the painted visual-viewport position and native capture moves the origin back into the view, scaled by page zoom. Clip sizes stay as sent. Sub-pixel rounding is absorbed; a page that scrolled away from the requested clip between metrics and copy fails with a retryable error instead of capturing another region. Without this translation, every agent image of a scrolled page failed with `UnknownVizError`. Exact display backing-pixel dimensions are normalized, while empty images and mismatched viewport dimensions are rejected. A daemon that has never connected to a desktop host uses headless Playwright Chromium and the web panel streams its page view. Once a desktop host is registered, losing its heartbeat reports a disconnected browser instead of silently opening a different headless page.

Neither engine attaches to your daily browser or reads its cookies. Agents have separate persistent website profiles, shared by their independent job/conversation sessions. Headless profiles live under the data directory's `browser-profiles/<role-id>`. Native profiles use Electron's persistent session storage, partitioned by a hash of that workspace/profile path. Both retain sign-ins across runs and restarts; existing headless sign-ins are not copied into native storage, so first native use may require signing in again.

## Chat panel and manual control

Manual desktop navigation finishes its command when the main document commits; remaining resources keep loading with the existing loading and failure indicators. A private session's pending viewport update does not block recovery of an expired controller lease, but still blocks agent actions until the update finishes. A transient lease-renewal timeout retains the controller only until its last confirmed expiry; definite rejections and expiry require recovery and never return the private page to an agent.

The panel opens when a participating agent starts browsing. Closing the panel suppresses automatic reopening in that conversation for the tab session; its Browser button still indicates activity. The compact header combines the selected agent, live status and manual handoff. Its agent menu lists conversation participants with waiting/manual indicators, keeps one selected view and never switches away automatically. Desktop has native page tabs, Back, Forward, Reload/Stop, hard reload, an address/search field and Find on page. Page settings supplies native page zoom, website Light/Dark/System appearance, tab audio muting, DevTools, Open in system browser and cache clearing without removing sign-ins. The history menu searches up to 50 manually visited addresses per agent/profile and restores up to 20 recently closed tabs in the current session; OAuth token/callback addresses are excluded. Cmd/Ctrl+Shift+T restores the last closed tab, and Alt+Left/Right (or Cmd+[ / Cmd+] on macOS) navigates history. Loading, failed navigation and renderer crashes have visible status and retry controls. Cmd/Ctrl+plus/minus/0 changes or resets page zoom; Cmd/Ctrl+Shift+R reloads without cache. Its shortcuts include Cmd/Ctrl+L, T, W, R and F, plus Ctrl+Tab/Shift+Tab. The streamed viewer keeps its address toolbar and Page view settings for zoom and panning. The initial selection follows the selected conversation participant. The panel is resizable with a pointer or arrow keys on its divider, and opens as a focus-managed full-screen sheet on small screens. Expand browser opens the same sheet on desktop, with the agent's activity, Stop, a message box and the approval tray beside the page; Back to chat (or Escape) returns to the split view. Fill panel follows the available panel size. Devices selects a phone, tablet or desktop CSS viewport, custom dimensions or rotation; its logical page viewport stays fixed while its presentation scales to fit. These presets change dimensions rather than pretending to change the browser user agent. Native resizing invalidates unused exact-action approvals before reflow; it waits during execution. Streamed resizing waits while an exact action is pending or executing. Another viewer cannot resize a manually controlled browser. Page view settings offers Fit to panel and enlarged views; Pan enlarged view moves around the image without sending page input. It is unavailable in read-only crew history and agent DMs.

The selected agent's browser can be viewed from another conversation it participates in. The header marks a browser belonging to another conversation as elsewhere. Browser task details links to its actual conversation or job, states the active run's captured mode and lists/revokes task site grants. Browser preferences, native tab metadata and live frames are separate from the workspace snapshot. Native controls require the owning desktop, the local app session, conversation membership and a live manual lease. App context menus, popovers, dialogs and sheets layer above the live embedded page without hiding or recreating it. The shell owns guest nodes independently of chat routes and split/expanded chrome, so moving between those views preserves the same automated page. Hiding the panel preserves manual pause. Switching chats retains a separate manual-control lease for each agent/job or standalone conversation; chats attached to the same job share its lease. Renderer-session tokens and their renewals survive leaving Chat for another route, and device viewport choices stay with the native tab. Returning to Chat never silently changes a fixed device viewport to Fill panel. Native paint and viewport updates preserve the selected guest surface, while background session painting stays below the app and scales to fit the compositor without reflowing the page. DOM guests never enter Electron’s `BrowserWindow.contentView` overlay; inactive capture surfaces remain beneath the opaque app instead of relying on native child ordering, while idle guests park offscreen. The following stream behavior applies to web viewing, including a web viewer of a desktop-hosted session. Stream requests require the local user session, UI client header and current conversation membership. Capability and conversation checks run before frame delivery and on static-page heartbeats. HTTP responses are not cached and live frames are never archived. Each session shares one Playwright screencast across viewers; a slow viewer retains only the newest pending frame, with bounded response buffering. The renderer decodes one frame at a time and retains only its newest pending image. Navigation, page replacement and viewport changes invalidate older frames and stale manual clicks. Dialog, title and warning updates do not depend on another image arriving. Hiding the panel or backgrounding the app document stops that viewer's subscription without returning manual control; capture stops after the last viewer leaves. Browser streaming falls back to shared, low-rate screenshot capture when screencast startup fails or produces no first frame. The panel labels this reduced-rate view. Set `PITCHCREW_BROWSER_SCREENCAST=0` before starting the daemon to select the screenshot fallback explicitly.

Opening the native browser takes control implicitly. While no agent run uses the browser, its toolbar, tabs, address field, history, find and page tools work directly and the first action (or a press on the read-only page) takes control implicitly; an implicit lease is handed back automatically when an agent run starts using the browser. While an agent works, the page stays in viewing mode until **Take control**, the header chip reads Working, and a press on the page flashes the chip ochre. Explicit takeover keeps its return-it-yourself contract. Relayed automation pointer moves and presses are drawn as a plum agent cursor that carries the agent's name, pings on a press, outlives the navigation a click starts and then fades; it is presentation only and never approval evidence. Desktop supports direct typing, IME, selection, paste, scrolling and native editing/link context menus. Script and sign-in popups use separate, owned sandboxed browser windows to preserve their real opener. They remain part of the same session, appear in its tab list with an explicit separate-window message, and share its manual-control, automation and cleanup gates. Ordinary foreground/background link tabs use the embedded page host, and background links preserve the selected tab. Blank-write and POST/script windows keep their genuine native opener. Human file pickers and downloads use the native browser; agent attachments remain restricted to approved packet files. Native manual changes are tracked in an isolated world using trusted input events; only transient noncredential fingerprints return to the daemon, not entered text.

In the streamed web viewer, choose **Take control** to sign in, handle CAPTCHA, navigate or correct a field inside the panel. Click the page, then type or paste; Tab and arrow keys operate remote controls, and Escape returns focus to the panel's controls. On touch devices, swipe vertically to scroll the remote page. Choose Type on page for a private text-entry tray, with explicit Send text, field navigation, selection, deletion and scroll controls. This tray is cleared when hidden, when changing agents or when control is returned. The tray supports the device keyboard and paste; it never saves entered text. Manual text never becomes a chat message or board event. Browser dialogs and prompt answers have explicit manual controls. In both engines, agent actions and inspection pause during takeover, including snapshots already in flight. An inspection spanning takeover and return is discarded even if the agent has control again when it finishes. Pending and unused approved actions are invalidated. **Return to agent** discards old page evidence and lets the agent inspect the current page again. Agent snapshots redact recognized password and one-time-code fields, including revealed passwords, and mask those fields in screenshots. Agent password fills remain forbidden.

One manual controller holds a renewable 45-second lease per agent browser session. Takeover and agent-tool waiting apply only to that job or standalone conversation; other sessions for the same agent retain independent control. Conversations attached to the same job share that agent's job session. A disconnected or expired controller leaves the session's agent inspection and actions paused; recover control from the panel after the old lease expires. Pending input is sent in order. Manual control does not bypass an unresolved submission attempt: verify its outcome on the job before further interactions.

**Hide browser** keeps the browser and manual pause. **Browser options → Close browser** stops its active run and closes Chromium. **Browser options → Reset saved sign-ins** also removes that agent's saved sign-ins and website storage, after an explicit confirmation; packets and history remain. A finished run expires its approvals but keeps the browser available. An idle browser closes after ten minutes without an active run or viewer. A different job or conversation starts with a fresh tab; the same context can continue on its current page. Profiles survive both idle closure and restart. Daemon shutdown closes all browser processes. All production CLI/ACP runs retain the common 30-minute deadline; manual takeover does not extend it. Demo does not call agent tools.

## Permission modes

Each agent browses in one of five permission modes, from most to least supervised: **Supervised**, **Autonomous preparation**, **Accept edits**, **Auto** and **Full access**. A mode decides which exact actions the server may approve without asking; it never removes the per-action approval record. Supervised is the default for existing and new agents, including Scout, Career Coach and Submitter. Labels and one-sentence summaries live in the zod-free `packages/core/src/browser-modes.ts` (`@pitchcrew/core/browser-modes`). These modes are Pitchcrew's own: they never change a runtime CLI's permission or sandbox mode, and a runtime's mode never changes them.

In **Supervised**, every navigation, click, hover, scroll, drag, fill, selection, keypress, dialog decision and packet attachment requires a separate exact-action approval. Review it in the pinned area below the browser, in **Decisions** or in its open row in Home's **Needs you**: the reason, parameters, frozen page evidence and exact upload contents remain available in each. The panel keeps the decision buttons visible and places full frozen evidence behind Review exact action and page evidence. Home's open browser row has its own Control/Command+Enter scope, which never covers a final submission, whether marked `purpose: submission` or a dialog continuing an uncertain submission (see [Home](home.md)); Decisions offers no approval shortcut. A browser approval already visible in the panel does not also display an overlapping toast; it remains in notification history. In the other modes, only the requests a mode leaves to the user reach the tray, Decisions, Home and notifications.

During a native browser run, the panel reserves a stable review area before requests arrive. Showing, expanding or resolving a request therefore does not resize the inspected page and expire its own approval. Genuine viewport changes still invalidate unused approvals. Execution reports the saved invalidation reason so the agent can inspect again and request fresh approval.

**Autonomous preparation** requires the user to allow an exact HTTPS origin for the current task. The panel can allow the site and its pending navigation together, lists granted sites and offers revocation. Grants are isolated per agent and task chain, survive related follow-up runs, and never carry into a different user request or daemon restart. Agents cannot grant or modify site access. Site grants exist only in this mode. User site decisions and automatic preparation records append event version 17; versions 1–16 still replay.

Autonomous preparation has conservative tested rules for the hosted Greenhouse, Ashby, Lever, Comeet and Workable sites. It permits recognized read-only board/posting navigation without query parameters, and filling, native selection or attaching the attached job's approved/exported packet on recognized native application forms. Controls must be unique, visible, enabled and non-credential; the native form must have one recognized submission button and a same-origin form action. Custom domains, frames, widgets, changed or ambiguous forms fall back to exact-action approval. In this mode all buttons, submission keys and dialog decisions ask. Supervised, Autonomous preparation and Accept edits therefore ask before the final submission even when the agent omitted its submission purpose marker, because they never approve a button, Enter or dialog on their own. Auto and Full access catch an unmarked final submission only through the best-effort classification described below, so agents must always mark it. The gateway enforces these rules independently of the runtime's own permission mode.

During Autonomous preparation's automatic actions, browser requests that write, navigate through page scripts or target an inspected native submission endpoint are blocked. A blocked request is reported to the agent and viewer and disables further automatic form preparation on that page; retrying requires an exact user approval. Sites requiring autosave, GraphQL writes or asynchronous uploads may therefore need exact approvals, or Accept edits, Auto or Full access, which run without this guard. Attaching a file is not proof that its upload succeeded. A user-approved interaction, or one that Accept edits, Auto or Full access approved, permits its website-controlled side effects; these rules do not prove arbitrary third-party script behavior or provide an OS network sandbox.

**Accept edits**, **Auto** and **Full access** need no site grants and work on any public site. The server reads the element an action targets on the live page, sorts the action into a class and approves it on its own when the mode allows that class:

| Mode                   | Read          | Edit                              | Routine interaction | Risky interaction | Sending |
| ---------------------- | ------------- | --------------------------------- | ------------------- | ----------------- | ------- |
| Supervised             | Asks          | Asks                              | Asks                | Asks              | Asks    |
| Autonomous preparation | Granted sites | Recognized forms on granted sites | Asks                | Asks              | Asks    |
| Accept edits           | Automatic     | Automatic                         | Asks                | Asks              | Asks    |
| Auto                   | Automatic     | Automatic                         | Automatic           | Asks              | Asks    |
| Full access            | Automatic     | Automatic                         | Automatic           | Automatic         | Asks    |

- **Read**: opening a read-only address, scrolling and hovering. A read-only address follows the task browsing rule below (HTTPS without credentials or a port, whose path and query do not look like an action such as submitting, sending, applying, deleting, signing out, checking out or confirming), or is a recognized Greenhouse, Ashby, Lever, Comeet or Workable board, posting or application page. An address that names sending is never read-only (see Sending).
- **Edit**: filling a field, choosing an option, attaching an approved packet file, clicks that focus a field, open a picker, tick a checkbox, radio or switch, or pick a listbox option, and Space in a field or on a choice. A choice named like a risky action, or one that agrees, consents, accepts, acknowledges or certifies (I agree, terms of service, privacy policy, I consent, I certify, plus common Spanish, Portuguese, French, German, Italian, Dutch and Hebrew words), is risky instead, so Accept edits and Auto ask before ticking it; recognized password and one-time-code fields are never edits. In a job's application (a run attached to a job), a box the server would tick or an option it would pick on its own must match a reviewed answer by its label or value, like a chosen select option; otherwise, including while the brief is unconfirmed, it asks.
- **Routine interaction**: buttons and menu items with an ordinary name (letters or digits, no sending or risky word, letters only in the Latin or Hebrew script), tabs and disclosures whose names are not risky or in another script, links to read-only addresses, site searches (a search button that is unnamed or named like Search, Find or Filter, or Enter in the search box), Tab, arrow, Home, End, Page Up and Page Down and Escape keys, dismissing a dialog and accepting an alert whose message does not look risky.
- **Risky interaction**: names that could change an account, delete, buy or share (delete, remove, withdraw, unsubscribe, sign out, pay, buy, purchase, book, confirm, share, follow, allow, authorize, continue as, sign in with, cancel followed by what it cancels, such as Cancel subscription, accept or decline an offer or invitation, plus common Spanish, Portuguese, French, German, Italian, Dutch and Hebrew words); a button, menu item, tab or similar control whose name has letters in a script other than Latin or Hebrew, which the word lists cannot read (links are judged by their address, choices as edits); links, navigation and explicit GET forms to any other address that does not name sending (including plain HTTP, and destructive-looking addresses such as `/unsubscribe/…` or `?action=delete`); explicit GET forms to read-only addresses, since they add the agent's entries to the address; a site search's button with any other name; reset buttons; Enter in a field outside any form; drags; recognized password and one-time-code fields; and accepting a confirm, prompt or leave-page dialog that does not mention sending. In a form the page posts or sends with its own code, two kinds of submit control are risky rather than sending, because the page receives the answers but nothing is finished: a step button named Next, Continue, Proceed, Review or Save, and, in a small form (at most three short entries and no file, multi-line, email, phone or password field), a search button named Search, Find, Filter, Show results, Update results or See results, each with the same words in common job-site languages.
- **Sending** asks in every mode, Full access included:
  - a click or Enter marked `purpose: submission`, and a dialog decision continuing an uncertain submission (`submissionAttemptId`);
  - a button, submit control, link, menu item or other clickable element (fields, form choices and tabs aside) any of whose names (label, text, value, title, alt) has a sending word: submit, send, post, publish, repost, reply, comment, invite, connect, endorse or apply, or a common word for sending or applying in Spanish, Portuguese, French, German, Italian, Dutch, the Scandinavian languages, Polish, Czech, Hebrew or Russian ("Apply filters" and similar stay routine). A harmless label cannot hide a sending one. A link named only to apply (Apply, Apply now, Easy Apply) is judged by its address instead when it opens a read-only address, such as a posting, or a recognized application page;
  - the submit control of a POST form, including a link the page sends as a POST (a Rails or Turbo `data-method` other than GET), or of a form the page sends with its own code (no method, or its own submit handler) that is not a site search, other than the step and small-form search buttons above;
  - Enter in a field of such a form, or of any form whose default (first) submit button is itself sending, and Enter in a multi-line field or editable region, where chat apps send;
  - opening an address that names sending, by navigating, through a link or through an explicit GET form, unless it is a recognized application page: a `submit`, `send` or `apply` path segment (also percent-encoded), a `submit` or `send` query key, or an `action`, `method`, `do`, `op` or `cmd` query value (with or without a leading underscore) holding a sending word. Some sites send on a plain GET, and the same address must not bypass a link that would ask. An address that cannot be read asks too;
  - accepting a confirm, prompt or leave-page dialog whose message mentions sending in any form (submitted, submission, sent, sending, posted, applied, invited and the like, plus common translations);
  - anything the server cannot read: a click, Enter or Space on an element it cannot find or read; an unnamed button or other clickable element, or one named only by symbols (an icon-only send arrow such as ➤ could be one); a click on an embedded frame (iframe, frame, object or embed) or on a container holding one; and a container with more than 40 controls inside. An unnamed link, tab or form choice, or the submit control of a site search or explicit GET form, is judged by the rules above instead.

The classification reads the live target without running page scripts: the element, every element around it with the browser's own activation behaviour (a button or link around a clicked icon, even with an ARIA role element in between and across open shadow roots), a label's control, every name the element shows or announces, a link's resolved address and Rails or Turbo method, and the form a control belongs to: its method (POST, dialog, explicit GET, a site search, or a form the page sends with its own code), the address an explicit GET form opens (read from its attributes, so a field named `action` cannot hide it), its size and its default button. A site search is a search landmark, or a small form with a search box or a field named q, query, search, keywords or search terms. Enter in a field is judged together with that default (first) submit button, and the riskier class decides. A click lands at an element's center, so clicking a container is also judged by every control inside it, including those in open shadow roots, and the riskiest of them all decides. A container with more than 40 controls (a whole page section, say), an embedded frame and a container holding one cannot be judged, so clicking them asks in every mode; agents act inside a frame through the action's frame selector, which is classified on the framed target. The server classifies an action when the agent requests it and again against the current page before it runs. A changed page or a class the mode no longer allows fails the approval, and the agent must request again. The class itself is never stored, shown or used as approval evidence.

Recognizing unmarked sending is best effort. The classification reads English names plus common words in the languages job sites use most, so a script-driven control whose names do not say it sends (a misleadingly labelled button, or a formless Finish) can still slip through in Auto and Full access. Full access also moves multi-step forms to their next step on its own, and Enter in a field outside a form, which it allows, can send. Website-controlled scripts remain outside payload verification. Agents must therefore mark the final submission with `purpose: submission` and the exact `exportApprovalId`: in Auto and Full access that marker is what makes sure the user is asked and the attempt recorded. Auto asks before buttons and tabs named in a script the word lists cannot read, such as Japanese; Full access allows them, except as the submit control of a form the page posts or sends with its own code. Accept edits, Auto and Full access run without the preparation write guard: an action the mode approved, like a user-approved one, permits its website-controlled side effects, such as autosave, asynchronous uploads and script-driven requests or navigation. Autonomous preparation keeps both its site grants and the guard.

Every automatic approval is still an exact-action browser approval record, bound to the run, role, card, page fingerprint and upload contents like a user decision. It is created approved with `automatic: true` by `system` ("Allowed browser action under the user's Full access mode", for example; task site grants keep "Allowed browser preparation under user-granted task site permission") and consumed before the action runs. Records from Accept edits, Auto and Full access carry the `mode` that allowed them and keep the page text but no screenshot: the request captures an image only when it has to ask. Automatic approvals are not decisions. They never wait in Decisions or Home's Needs you or count toward the Home badge or a job's beads, never appear in Decisions history and raise no notification; they appear as steps in the browser panel and on the Activity page. Event version 39 adds the three modes to role, conversation override and run configuration records, the optional `mode` on automatic approvals and the optional `external` flag on chat requests; versions 1–38 still replay.

Set a default in agent settings, or choose **Agent default** or one of the five modes in the conversation composer. Permission details explain the selected agent’s next turn in that conversation; the browser panel shows only the actual task’s captured mode, including when that task belongs to another conversation. Overrides are independent per participant and apply to future turns; a queued message takes the mode in effect when its run starts. Workflow follow-ups capture their originating conversation's browser override while retaining the saved runtime/model settings. Existing application conversations can also override future application workflow browser mode. Changing a mode does not escalate an already-started run. Only the user changes modes: agents cannot, and role change proposals carry only instructions and capabilities.

Some runs browse in Supervised whatever the agent's mode. Scheduled routines and everything that follows from them (crew follow-ups, answer continuations and runs queued from a routine's chat request) stay Supervised; follow-ups of routines queued through a job's chat request now do too, where before they used the agent's mode. Runs started by a message from an external MCP app (`send_message`, marked `external` on the chat request) and their follow-ups also stay Supervised, because external access grants no browser authority. Every mode keeps the hard limits: an uncertain submission blocks further actions, private-network and URL-credential addresses stay blocked, agents never type passwords, uploads stay limited to the approved packet with byte checks, job-attached fills and selections must use reviewed answers (and so must a choice a mode ticks on its own), manual takeover pauses agents and expires unused approvals, and runs keep the 30-minute deadline.

## Agent tools and gates

The shared stdio MCP server exposes three browser tools only to permitted roles:

- `pitchcrew_computer_inspect` opens the agent's browser if needed and returns inspected page text, controls, URL, title and snapshot-scoped `ref:` element IDs. `includeImage: true` adds a credential-redacted JPEG screenshot; text-only inspection is the tool default. References resolve to the same inspected DOM element and expire on a new inspection, navigation, tab change or manual handoff. CSS selectors remain supported.
- `pitchcrew_computer_wait` waits up to 30 seconds for all requested text, URL and visible selector/reference conditions, returning a bounded timeout result. Cancellation, capability loss and manual takeover interrupt waits without returning private page evidence.
- `pitchcrew_computer_request` proposes one exact action with a reason. It returns a pending user decision, or an automatic approval record when the run's browser mode or task site grant allows the action; it never performs the interaction.
- `pitchcrew_computer_execute` waits up to 30 seconds for a pending decision (an automatic approval needs none), then executes that exact action once. While pending, agents call it again to keep the run alive. During manual control, tools return a bounded waiting status without page evidence; agents call inspect again to wait.

The gate binds the run, role, card, action parameters, upload bytes and page fingerprint. It rechecks current role permissions, cancellation, site access, preparation rules or the mode's action class (with reviewed choice answers on a job's application), and page state before executing. A changed URL, DOM or form value requires a new request. Approval is consumed before interacting, so failed or uncertain actions cannot reuse it. Run completion, cancellation, failure and daemon restart expire pending/approved actions. Browser actions never automatically mark cards submitted; users verify the website confirmation and record the outcome.

The approval digest serializes run, role and card in an explicit field order, independent of the calling scope object's insertion order. A Submitter inspecting a form in a chat run uses its own role identity for the same persisted approval and Inbox request; the chat workflow seat does not change that identity.

Chat records each browser call the gateway receives (the `pitchcrew_computer_*` tools, `pitchcrew_assess_form` and `pitchcrew_capture_submission`) as a step of kind `browser`, named like the tray and never given a target. A browser call that failed before the daemon received it (MCP input validation, an unknown tool, or the runtime's own refusal, timeout or transport failure) appears from the runtime's stream as one failed `browser` step, "Couldn't use the browser", also without a target; a request Goose could not parse at all names no tool, so it shows as a generic "Tool failed" step with the same kind of shared sentence. Every failed browser step shows a fixed sentence for its classified reason, never Playwright text, typed or chosen values, URLs, selectors, call logs or the runtime's own error text: gateway steps use the browser sentences, such as "The page did not respond in time." or "The page or element could not be found.", and calls rejected before the daemon use the shared reason descriptions from `@pitchcrew/core/tool-failures`, such as "The tool rejected the arguments it was given." The tool's own error still reaches the agent unchanged. A declined request ("You declined to …") and a takeover pause ("Paused while you had control") are not failures and show no reason. See [chat turn activity](chat-turn-activity.md).

Uploads remain limited to `resume.md`, `cover_letter.md`, `form_answers.md`, `note.md` and generated resume/cover-letter PDF or DOCX files from the current approved, exported packet for the attached job. Paths resolve beneath that card's packet directory and file bytes are checked against the reviewed export. Agent tools expose neither arbitrary filesystem upload, shell execution nor JavaScript evaluation. Native human file picking belongs to private manual control; the streamed controls retain packet-only attachments.

Pages are untrusted data. Public HTTP(S) requests, redirects and subresources are checked against DNS/IP private-network rules. Local/private URLs and URL credentials remain blocked, keeping the browser away from the daemon's approval API. Headless sessions block service workers, WebSockets and downloads. Native sessions permit public WebSockets outside Autonomous preparation's guarded automatic actions and human downloads during takeover; requests without an owned guest (including worker-only requests) are denied. These are application boundaries, not protection against adversarial DNS rebinding at the OS network level. First-level iframe targeting retains inspected frame fingerprints and unique selectors; nested frames are uninspected. Autonomous preparation never acts inside frames on its own, while Accept edits, Auto and Full access classify a framed target like any other; a click on the frame element itself, or on a container holding one, asks in every mode. Popups become the selected page. Native desktop chrome provides tabs, navigation, search and find. Main-frame guest keyboard input and reload use the same native-routing approach as T3 Code, so an unfocused guest receives keys instead of the trusted renderer. Cross-site focus is checked before native text fallback. General desktop applications and whole-desktop control remain outside this feature.

Hover, bounded element scrolling and drag actions use the same exact-action gate as other interactions; persisted action variants use event version 29, retaining versions 1–28.

It performs no live provider runs or external submissions. `bun run test:desktop` also runs hidden Electron checks with real native guests, trusted human typing, same-page agent actions, private takeover, tabs, popup openers and graceful cleanup. No test shows or focuses an OS window. Live provider/browser combinations and third-party application site variants still require manual verification. Run `bun run browser:install` before testing on a new checkout.

`bun run test:e2e`, also included in `test:desktop`, drives the production React UI, real Bun daemon, sandboxed Electron preload/guests and scoped MCP stdio browser calls together. Its sixteen journeys check actual page/input outcomes, live compositor pixels beneath real app overlays, route and tab persistence, screenshot drafts, element picking, exact approval/rejection in Supervised, crash recovery and owned cleanup. Only the external website and provider are deterministic fixtures. See [browser E2E tests](browser-e2e.md) for running, evidence and the remaining integration-only boundaries.

## Form assessments and submission receipts

Both native and headless inspection return bounded read-only constraint evidence on controls. `constraints.minLength`, `maxLength`, `min`, `max` and `step` describe the corresponding HTML attributes as `declared` (the exact string, at most 200 characters), `absent` (no attribute), or `unavailable` (oversized or containing a recognized credential). These are declarations, including malformed strings, rather than proof of effective browser validation, script rules or server limits. Absent attributes do not mean unlimited: browser defaults may apply. Missing `constraints` on historical records means unavailable evidence. The existing numeric `maxLength` remains for compatibility. `uploadSizeLimit` is always `unknown`: HTML file inputs have no standardized maximum byte-size attribute, and neither `accept`, custom data attributes nor nearby prose establishes one. No validation handlers or page interactions are invoked to collect this evidence.

Select controls return at most 100 choices of at most 500 characters each. `optionsTotal` is the current native option count; `optionsTruncated` is true if either choices or choice text was cut. False means that this native select's current choices fit the bounds, not that later pages or dynamically loaded choices are complete. Missing choice completeness on older records is unknown.

Inspection also includes explicit ARIA radio/checkbox controls and toggle buttons with `aria-pressed`. Labels use bounded `aria-labelledby`, `aria-label`, native labels or custom control text; label extraction excludes nested native field content. An ancestor fieldset/legend or ARIA group/radiogroup supplies separate group metadata. Only an explicit radiogroup `aria-required` supplies group requiredness; otherwise it is `null` (unknown), including generic button groups. Required radio groups carry that flag onto their radio controls. Native disabled fieldsets and inherited `aria-disabled` remain disabled. There is no guess linking unlabeled hidden checkboxes to adjacent Yes/No buttons, no inference from asterisks or website-specific styling, and no resolution of external `aria-owns`, shadow-root or script-only relationships. Unsupported semantics require inspection of the page or agent annotations, never a claim that the form is optional or complete. Native controls keep their existing selectors; both native and custom controls share the 100-control limit per frame, with overflow listed as uninspected.

Constraint, group and choice-completeness evidence persists in assessments and confirmed form summaries, excluding raw HTML, selectors and entered values from the Writer/Reviewer summary as before. Event version 38 adds these optional fields; versions 1–37 retain their original shapes. A changed declared constraint or completeness finding makes adopted requirements stale through the existing confirmation and approval invalidation rules. These read-only additions grant no action, upload or submission permissions and remain part of existing page fingerprint evidence.

Before preparing a submission, agents with `readApplications` can use `pitchcrew_read_submission_attempts` to inspect bounded durable history for the attached card, or an explicitly selected card in a standalone chat. The read includes uncertain and resolved attempts across prior runs, with status, timestamps and confirmation presence/verification time only. It excludes browser evidence, private inputs and approval payloads and requires no browser access. `hasUncertainAttempts` covers all pages. This read does not resolve attempts or permit any interaction or retry; the exact-action and user-verification gates below remain authoritative. See [application tracking](tracking.md#permissions-and-tools).

`assessForms` and `recordSubmissions` are separate optional capabilities, defaulting off and requiring computer use. `pitchcrew_assess_form` snapshots current server-inspected controls onto the attached card from a text-only inspection: saved evidence never keeps a screenshot, so a failing page image cannot block it; agent-provided selectors must match inspected controls exactly, and duplicates fail. All controls remain present, including unassessed ones. Required/visible/disabled flags, labels, types, select choices and accepted file extensions come from the browser. Conditional requirements, missing answers and blockers are explicitly agent annotations, with uninspected sections recorded. Before drafting a linked application, **Job details > Application > Brief and requirements > Inspect application form** starts an attached inspection conversation with an enabled browser/form-assessment agent (Submitter by default). It needs no reviewed/exported packet and requests inspection only, under the agent's browser mode and manual takeover. Inspection only is the request's instruction; the server still refuses fills before the brief is confirmed and, in every mode, asks before a marked submission and anything it recognizes as sending. The user returns to the job, extracts or reviews the brief, and confirms the fields and files together with the brief. Required flags, accepted upload formats, choices and character limits come from inspected controls. Blocked or uninspected sections stay explicit. If inspection is unavailable, the user can explicitly choose to check the form themselves when preparing the brief; agents cannot make that choice. A missing job link remains an uninspected limitation.

Writer and Reviewer receive a bounded, user-confirmed form summary through the isolated prompt and card tool. Raw browser text/HTML, selectors, screenshots and entered values are excluded. Extraction can use the field metadata to propose legitimate questions but has no profile or tools, and its form summary is replaced with server-inspected metadata. Form confirmation grants no interaction permissions. Changed requirements make the old confirmation stale and invalidate packet review and unused packet/browser approvals; confirm the new findings and review the packet again. Identical summaries preserve validity. Submission preparation reinspects the current form and retains all existing final-submission gates.

Mark the final click or Enter request `purpose: submission` with the exact `exportApprovalId`; a marked submission asks in every browser mode, Full access included. An unmarked click or Enter that the server recognizes as sending also asks, but that recognition is best effort and only a marked submission records an attempt. Before performing the approved action, the gate atomically consumes its approval and records an uncertain attempt bound to the card, packet digest, export and browser page. All further interactions on the card are blocked, even an ordinary click without a purpose. `pitchcrew_capture_submission` saves an exact quotation from the changed browser snapshot for that attempt, read text-only like form assessments. It never marks a card submitted. Users verify the evidence on the job. After restart, users may enter a source URL, quotation/reference and explicit verification checkbox; this evidence is clearly recorded as user-reported, not server-observed. Verification rechecks the current packet and consumed/failed submission action; it transitions awaiting-approval cards or preserves later tracked states. Verifying no submission occurred resolves uncertainty and permits a separately approved retry.

## Binary packet review

Select PDF and/or DOCX when requesting export approval. Generation completes first; approval stores frozen bytes, MIME type and SHA-256 manifest alongside the exact packet. PDF displays every page inline in Inbox through lazy PDF.js, with only a local worker and whitelisted bundled Helvetica substitute font; formatted PDFs embed their own font. Closing cancels rendering and disposes the worker/document; failures are visible. DOCX previews complete source text. Formatted documents lay out Markdown structure and plain text documents print it literally; neither executes HTML or loads remote assets. PDF names unsupported characters explicitly; DOCX supports Unicode. Inbox shows page counts derived from the frozen bytes. See [packet exports](packet-exports.md). Local export validates the reviewed manifest before consuming approval and writes its exact bytes. Binary uploads verify SHA-256 and complete Buffer equality, plus the current packet and card-scoped export path; they never decode binary bytes as UTF-8 for verification. Browser upload proposals show the reviewed text, format and byte digest. Download links appear after approved export.

An uncertain submission can continue through a separately approved browser dialog only when `submissionAttemptId` binds the same run, card, current exported packet and observed dialog. This continuation asks in every browser mode. The consumed continuation approval is saved on the attempt. No click, keypress or navigation retry is allowed.

## Task browsing grants

In Autonomous preparation mode, **Allow browsing for this task** is separate from **Allow preparation for this task**. Browsing grants permit HTTPS read navigation (including ordinary search queries), scrolling and hovering on the exact origin. Application/submission and destructive-looking routes still ask, as do clicks, keys, dialogs, fields and files. Preparation grants retain the existing recognized-form policy. Writes and script-driven navigation remain blocked during automatic actions; a blocked page returns to asking. Grants are user-only, revocable, isolated to the task chain and lost on restart. Version 30 records the distinct grant type; older permission events remain readable. Accept edits, Auto and Full access need no grants: they apply the same read-only address rule on any public site.

## Agent tabs

`pitchcrew_computer_tabs` lists the current job/conversation's tabs, opens blank tabs, selects a tab or closes one. It cannot reach another session or profile. Tab changes expire unused approvals and are paused during manual takeover; unresolved submissions block changes. Actions, inspection and waits accept `tabId`. Proposed actions always bind the resolved tab, even when omitted by the caller, and execution returns to that exact tab before checking evidence. Version 31 persists that binding. Closing a tab skips before-unload scripts; ordinary website dialogs must be resolved first.

## Browser diagnostics

Inspection includes at most 30 console/script failures and 30 failed HTTP requests for the selected owned tab. Arbitrary console output is reduced to a generic error; recognized engine failures have quoted values, tokens and URLs sanitized. Request summaries contain method, resource type, status and a bounded URL with no credentials, query or fragment; headers, bodies, responses, console objects and stack traces are excluded. These buffers are memory-only, clear on page navigation and are cleared/disabled throughout private takeover. They are never sent to application analytics.

## Native browser profiles and importing sessions

During manual control, **Page settings > Manage browser profiles** creates, renames, selects and removes named profiles for the current agent. The selected default applies to new job/conversation browser sessions; existing tabs retain their original profile. The original Default partition is preserved. Profile names/default choices persist in Electron user data, separately from cookie storage and board history. Removing an unused profile clears its website storage; the UI confirms removal. Profiles in use cannot be removed, and imports require other sessions on that profile to be closed.

**Import sessions** opens a user-only native file picker for JSON cookie exports (arrays, browser-extension exports or Playwright storage-state cookies) and Netscape cookie text files. It does not decrypt another browser's profile or read provider CLI credentials. Review the target profile, cookie count, skipped count and domains, then explicitly confirm the copy. Raw cookie values stay in the main process and native browser storage, never the app renderer, daemon, agents, board or telemetry. Previews expire after five minutes. Exports are limited to 1 MB and 1,000 cookies; expired and partitioned cookies are skipped, and malformed/private scopes are rejected. Import failure attempts to restore previous cookie values. This is a one-time cookie copy; sites using other storage or device-bound sessions may require a fresh sign-in. Headless web profiles retain their existing behavior.

## T3 Code browser reference

The implementation follows the source-backed comparison in [browser benchmark and functional coverage](browser-benchmark.md). Permanent DOM guests, isolated main-owned registration, per-tab lifecycle serialization, capture queues and connection-owned focus/paint leases follow T3 Code’s approach. A timed-out native read remains in the per-guest capture queue until Chromium actually finishes it; later callers cannot overlap it. A credential-mask paint wait that has not started a native read expires at the same deadline and releases the queue; its late completion cannot start a copy. The hidden native smoke injects an unanswered paint promise during an exact-action request, verifies text-only inspection and a fresh pending approval on the same guest before that promise settles, and checks credential-mask pixels in the recovered evidence. This verifies recovery from a stalled paint wait, not why an initial renderer paint stalls on a real site. The same smoke scrolls the document 1500px and checks pixels in the agent's inspection and approval images: they show the visible region, with the credential mask on a scrolled password field. Relay detach/disconnect, navigation, crashes and destruction release abandoned holds. Independent stream owners share capture without stopping each other. macOS idle guests remain paintable offscreen instead of toggling `visibility:hidden`. During automation the webview retains its Chromium hit-test region so trusted input reaches cross-origin frames; a separate transparent app-owned shield blocks human page clicks until private takeover.

The screenshot action previews the actual page in a user-only editor with drawing/notes, PNG saving and attachment to the current chat draft. Recording captures only the browser page to a bounded WebM clip, without desktop, microphone or system audio access. It stops when the tab, controller or mounted panel changes. Videos save locally; chat attachments retain their existing supported types and size/count limits. The separate browser window mirrors the same guest and forwards human input while a live private lease exists; it does not open an independent copy of the website. Its capture and inputs stop being private-controller operations when that lease expires, and closing the owned session closes the mirror.

## Contributor rules

Browser manual takeover and MCP manual-control waiting use the same per-agent job or standalone-conversation session. Other sessions for that agent retain independent control; conversations attached to the same job share its session. Renderer manual-control tokens and store-owned renewals survive chat route unmounts in that same scope; device viewport choices stay with their native tab. Renderer manual-control leases use that same scope, and native paint/resize updates keep the selected guest attached while background guests stay below the app with zero opacity, including during capture and automation paint leases. A paint lease never authorizes visible presentation; negative stacking alone cannot hide an inactive guest inside the expanded browser's stacking context. DOM guests do not enter `BrowserWindow.contentView`; native overlay child ordering must never be used to hide inactive guests. Expired controller leases keep the affected session private until the user recovers and returns control.

Native browser runs reserve a stable approval review area so showing, expanding or resolving requests does not resize their inspected page. Genuine native viewport changes still invalidate unused approvals; execution reports the saved invalidation reason. Approval digests serialize run, role and card in an explicit field order independent of caller object insertion order. A fixed, isolated guest preload forwards only unused trusted Escape presses to the expanded browser's existing renderer dismissal path; website fields, menus, dialogs and consumed keys keep precedence, without a global shortcut or a change to session, device settings or manual ownership.

Floating native browsers open from the existing page's aspect ratio within the owning display's work area. Fit, 100% and display-scale controls resize only the streamed presentation, with scrollbars for overflow and pointer mapping through the displayed image bounds; they must never resize or zoom the inspected page or invalidate its approvals. Back to app closes only the floating surface and retains the same embedded guest.

Browser permission modes decide only which exact actions the server may approve on its own. Action classes come from the server reading the live target, at request and again before execution, never from the agent's reason, labels or claims. Automatic approvals always create and consume exact-action records; no mode skips the page fingerprint check or the hard limits. The sending class, including any activated element the server cannot read, asks in every mode, Full access included. Recognizing unmarked sending is best effort, so the agent texts must keep telling agents to mark the final submission and never to send, post or submit anything the user has not asked for. Routines, everything that follows from them and runs started by external MCP messages stay Supervised, and only the user changes a mode. Keep mode labels and summaries in `packages/core/src/browser-modes.ts`, and change the agent prompts, MCP tool descriptions, default role instructions and these docs together. A new persisted mode or approval field needs a new event version.

**Computer use.** Opt-in per role; shared MCP tools use the actual isolated Electron guest on desktop or a streamed headless local Chromium browser on web, shown in Chat's resizable browser panel with a compact agent/status header, an agent-switching menu, one address/view toolbar, task details linking to the actual conversation or job, and no automatic switching away from the selected agent. Task details also holds the captured mode and site grants; another conversation’s browser is labeled elsewhere. The panel auto-opens on browser activity, remembers manual closure per conversation/tab and uses a focus-managed full-screen sheet on narrow screens; expand/restore, page zoom with local panning, private touch text entry and remote swipe scrolling are available; history and agent DMs remain read-only. Each agent has a private persistent profile under `browser-profiles/<role-id>`; a different job/conversation gets a fresh tab. Finished runs expire approvals but leave their browser available; idle browsers close after ten minutes without a run/viewer, and shutdown closes all processes. Close browser stops the current run; Reset browser additionally removes that agent's sign-ins/storage after confirmation. User-only streaming/input APIs require the local UI session and conversation membership, retain backpressure and disconnect cleanup, and do not add live frames to snapshots/events. Manual takeover holds one renewable 45-second controller lease, pauses all agent actions/inspection, invalidates unused approvals and discards in-flight snapshots; idle browsing takes the same lease implicitly and returns it when an agent run starts. Commands that unblock a page (Fetch continuations, dialog decisions) bypass relay focus/paint holds, and a performed approved action stays consumed when its follow-up inspection fails. See [docs/browser-t3code-review.md](browser-t3code-review.md). Expiry/disconnect never silently returns agent control. Returning control refreshes evidence. Manual text is never saved to chat or events; recognized credentials, including revealed passwords, are redacted/masked in agent evidence and cannot be filled by agents. Five browser permission modes run from Supervised to Full access. Supervised is the default for every agent; in it every action requires exact approval in a pinned panel area, in Decisions or in Home's Needs you (whose Control/Command+Enter never covers a final submission), with expandable exact-action evidence. Browser maintenance lives in an options menu. Conversation permission editing stays in the composer, with active task permissions shown separately in the panel. User-configured Autonomous preparation permits only server-recognized hosted board/posting navigation and native form preparation on per-agent/task-chain origins explicitly granted by the user. Greenhouse, Ashby, Lever, Comeet and Workable have conservative fixture-tested native form rules; custom domains, frames, widgets and changed/ambiguous forms fall back to exact approval. Its automatic preparation blocks write requests, script-driven navigation and native submission endpoints; blocked requests are reported and switch further form actions back to asking, including sites requiring asynchronous upload/autosave writes. Accept edits, Auto and Full access need no site grants: the server classifies each action from its live target as read, edit, routine, risky or sending, and approves read and edit actions in Accept edits, routine clicks and keys too in Auto and risky ones too in Full access, all without the write guard; their automatic records carry the mode and no screenshot, and a choice they tick on a job's application must be a reviewed answer. Marked final submissions, uncertain-submission dialog continuations, anything classified as sending or posting and any activated element the server cannot read ask in every mode; buttons, keys and dialogs ask unless Auto or Full access allows them. Recognizing unmarked sending is best effort (Full access moves multi-step forms on by itself, and a misleadingly labelled script control can slip through), so agents must mark the final submission. Automatic approvals are not Decisions; they show as browser panel steps and on Activity. Agent defaults and per-participant conversation overrides affect future turns; workflow follow-ups capture conversation browser overrides without changing runtime/model settings; routines and everything that follows from them (including runs queued from a routine's chat request) and runs started by external MCP messages always remain Supervised; agents cannot change modes. Site grants and automatic exact-action records use append-only event version 17, preserving versions 1–16; version 39 adds the newer modes, the approving mode and external chat requests, preserving versions 1–38. Every execution rechecks run/role/card, current capabilities, page fingerprint, site access or the mode's action class, form rules and upload bytes, and consumes approval before side effects. All production runs retain the common 30-minute deadline. The existing exported-packet bounds, iframe fingerprints, form assessments, uncertain submission/approved dialog continuation, user verification and source-backed receipts remain enforced; manual input cannot retry an unresolved submission. No arbitrary JS, shell, filesystem upload, desktop control or cloud hosting. Public-network checks and private/local blocking remain; third-party scripts are untrusted and this is not an OS network sandbox. See [docs/computer-use.md](computer-use.md).

Desktop browser sessions use isolated Electron webviews in a permanent renderer host and persistent per-agent partitions, automated by the daemon through an authenticated guest-only CDP relay. Main authorizes each guest with a one-shot bootstrap nonce, exact partition, captured guest identity and main-frame/origin-checked registration; remote guests have no preload, Node access or nested webviews. Renderer reloads close the old guests and relays instead of silently replacing an approved page. Native browser chrome includes Stop, hard reload, real page zoom, cache-only clearing, load/crash recovery, bounded per-profile manual history and recently closed tabs, audio mute, website appearance, device viewport controls, user-only annotated PNG capture, DevTools-style element picking (a toolbar toggle beside Find, pressed while picking: the chip says Picking and the tray says what to click with a Cancel, Chromium highlights what the pointer is over in the app's primary without DevTools' info box, and a click returns that element as a padded crop named by role (scaled from CSS pixels to the screenshot's device-independent pixels, so page zoom never crops a neighbour), such as "Heading “Open Roles”", reviewed in the screenshot dialog (one glaze Attach to message; Undo and Clear only after drawing) before it is attached to the draft; Escape, a second press, a minute without a click (with a toast), the page leaving view or a control or tab change ends it, and reads use CDP’s DOM domain without page script) and bounded page-only WebM recording, plus a separate live mirror window. Main pushes guest state; daemon polling retains authoritative dialog/control metadata. Guest keyboard input and reload target the guest even while unfocused. Connection-owned paint/focus holds release on lifecycle changes and native captures serialize their actual Chromium copies beyond caller timeouts. The mirror has its own sandboxed CommonJS preload for bounded input forwarding and receives no app bridge. See [browser benchmark](browser-benchmark.md). Native manual input goes directly to the page; private takeover pauses agents, and native reflow expires unused action approvals. Native page settings manage named per-agent profiles and user-reviewed JSON/Netscape cookie imports through a main-frame-only IPC bridge; raw cookie values never reach renderer, daemon, agents or events. Headless profiles are retained separately without migrating sign-ins. Native screenshots use bounded Electron viewport capture with stay-hidden behavior and preserve Playwright credential masks; the hidden native smoke verifies mask pixels. Agent inspections support snapshot-scoped element references and optional screenshots, with bounded, privacy-checked condition waits and sanitized memory-only script/request diagnostics that are disabled during private takeover. Hover, scroll and drag actions use event version 29 with older versions retained. See [computer use](computer-use.md) and [ADR 0003](adr/0003-native-desktop-browser.md). Web browser viewing uses one public Playwright screencast per session shared across authenticated viewers, with shared low-rate screenshot fallback (`PITCHCREW_BROWSER_SCREENCAST=0` selects it explicitly). Per-viewer pending frames, HTTP backpressure and client decoding remain bounded; hidden/background viewers unsubscribe without changing manual pause. Heartbeats recheck access on static pages, metadata updates independently, and page/viewport generations reject late frames and stale manual clicks. Viewer images never replace credential-redacted agent inspection or exact-action evidence. Inspections spanning manual takeover and return are discarded. See [browser responsiveness](browser-interaction-performance.md).

Browser panels share sculpted clay chrome, raised active tabs, recessed address fields and a centered blank-page/connection state across native and streamed viewing. Blank native tabs hide their guest view so the app's address-entry guidance stays visible. Guests sit on a white base like any browser, so a page without its own background stays readable in the dark theme. The shell keeps DOM guests attached across routes, split/expanded presentation and app overlays. Context menus, popovers, dialogs and sheets layer above the live page without hiding or recreating it. Page loading uses a toolbar progress strip without moving the viewport, with static indicators under reduced motion.

Manual desktop navigation acknowledges main-document commit instead of waiting for the full page load. Private-control recovery may replace an expired lease during a pending viewport update without clearing its browser-action lock. Renderer renewal transport failures retain the token only through the last confirmed lease deadline; rejected or expired leases still require explicit recovery.

ARIA toggle buttons are identified as `type: "toggle"` while `buttonType` preserves their native `button`/`submit`/`reset` behavior. A toggle without a type in a form can still submit it; its semantic role never authorizes interaction. Inspection exposes valid live ARIA `checked` and `pressed` states (including mixed checkbox/toggle states); missing or invalid attributes stay unknown. These states are omitted from structured saved assessment controls and confirmed form requirements and never count as user-provided personal answers.
