# Local browser computer use

For the desktop architecture, see [ADR 0003](adr/0003-native-desktop-browser.md). The web viewer keeps the [streaming design and fixture measurements](browser-interaction-performance.md).

Enable **Crew → agent settings → Computer use**. The desktop app uses its bundled Chromium. For the web app and headless tests, install Chromium once:

```sh
pnpm browser:install
```

The agent's browser appears inside **Chat → Browser**. Desktop hosts real Electron `WebContentsView` pages: human input goes directly to the page, and the daemon automates the same pages through a private authenticated CDP relay. The relay exposes only that job/conversation's guest targets, never the app renderer. Guests have no app preload or Node access. With no connected desktop host, the daemon uses headless Playwright Chromium and the web panel streams its page view.

Neither engine attaches to your daily browser or reads its cookies. Agents have separate persistent website profiles, shared by their independent job/conversation sessions. Headless profiles live under the data directory's `browser-profiles/<role-id>`. Native profiles use Electron's persistent session storage, partitioned by a hash of that workspace/profile path. Both retain sign-ins across runs and restarts; existing headless sign-ins are not copied into native storage, so first native use may require signing in again.

## Chat panel and manual control

The panel opens when a participating agent starts browsing. Closing the panel suppresses automatic reopening in that conversation for the tab session; its Browser button still indicates activity. The compact header combines the selected agent, live status and manual handoff. Its agent menu lists conversation participants with waiting/manual indicators, keeps one selected view and never switches away automatically. Desktop has native page tabs, Back, Forward, Reload/Stop, hard reload, an address/search field and Find on page. Page settings supplies native page zoom and cache clearing without removing sign-ins. Loading, failed navigation and renderer crashes have visible status and retry controls. Cmd/Ctrl+plus/minus/0 changes or resets page zoom; Cmd/Ctrl+Shift+R reloads without cache. Its shortcuts include Cmd/Ctrl+L, T, W, R and F, plus Ctrl+Tab/Shift+Tab. The streamed viewer keeps its address toolbar and Page view settings for zoom and panning. The initial selection follows the selected conversation participant. The panel is resizable with a pointer or arrow keys on its divider, and opens as a focus-managed full-screen sheet on small screens. Expand browser opens the same sheet on desktop; Restore split view returns to chat. The live page viewport follows the available panel size so websites reflow to fill the view. Native resizing invalidates unused exact-action approvals before reflow; it waits during execution. Streamed resizing waits while an exact action is pending or executing. Another viewer cannot resize a manually controlled browser. Page view settings offers Fit to panel and enlarged views; Pan enlarged view moves around the image without sending page input. It is unavailable in read-only crew history and agent DMs.

The selected agent's browser can be viewed from another conversation it participates in. The header marks a browser belonging to another conversation as elsewhere. Browser task details links to its actual conversation or job, states the active run's captured mode and lists/revokes task site grants. Browser preferences, native tab metadata and live frames are separate from the workspace snapshot. Native controls require the owning desktop, the local app session, conversation membership and a live manual lease. App menus and dialogs hide the native guest so it cannot cover app controls. Hiding the panel preserves manual pause. The following stream behavior applies to web viewing, including a web viewer of a desktop-hosted session. Stream requests require the local user session, UI client header and current conversation membership. Capability and conversation checks run before frame delivery and on static-page heartbeats. HTTP responses are not cached and live frames are never archived. Each session shares one Playwright screencast across viewers; a slow viewer retains only the newest pending frame, with bounded response buffering. The renderer decodes one frame at a time and retains only its newest pending image. Navigation, page replacement and viewport changes invalidate older frames and stale manual clicks. Dialog, title and warning updates do not depend on another image arriving. Hiding the panel or backgrounding the app document stops that viewer's subscription without returning manual control; capture stops after the last viewer leaves. Browser streaming falls back to shared, low-rate screenshot capture when screencast startup fails or produces no first frame. The panel labels this reduced-rate view. Set `PITCHCREW_BROWSER_SCREENCAST=0` before starting the daemon to select the screenshot fallback explicitly.

Opening the native browser explicitly takes control; an automatically revealed page stays in viewing mode until **Take control**. Desktop supports direct typing, IME, selection, paste, scrolling and native editing/link context menus. Native popups remain tabs in the same session and preserve their opener. Human file pickers and downloads use the native browser; agent attachments remain restricted to approved packet files. Native manual changes are tracked in an isolated world using trusted input events; only transient noncredential fingerprints return to the daemon, not entered text.

In the streamed web viewer, choose **Take control** to sign in, handle CAPTCHA, navigate or correct a field inside the panel. Click the page, then type or paste; Tab and arrow keys operate remote controls, and Escape returns focus to the panel's controls. On touch devices, swipe vertically to scroll the remote page. Choose Type on page for a private text-entry tray, with explicit Send text, field navigation, selection, deletion and scroll controls. This tray is cleared when hidden, when changing agents or when control is returned. The tray supports the device keyboard and paste; it never saves entered text. Manual text never becomes a chat message or board event. Browser dialogs and prompt answers have explicit manual controls. In both engines, agent actions and inspection pause during takeover, including snapshots already in flight. An inspection spanning takeover and return is discarded even if the agent has control again when it finishes. Pending and unused approved actions are invalidated. **Return to agent** discards old page evidence and lets the agent inspect the current page again. Agent snapshots redact recognized password and one-time-code fields, including revealed passwords, and mask those fields in screenshots. Agent password fills remain forbidden.

One manual controller holds a renewable 45-second lease per agent. A disconnected or expired controller leaves the agent paused; recover control from the panel after the old lease expires. Pending input is sent in order. Manual control does not bypass an unresolved submission attempt: verify its outcome on the job before further interactions.

**Hide browser** keeps the browser and manual pause. **Browser options → Close browser** stops its active run and closes Chromium. **Browser options → Reset saved sign-ins** also removes that agent's saved sign-ins and website storage, after an explicit confirmation; packets and history remain. A finished run expires its approvals but keeps the browser available. An idle browser closes after ten minutes without an active run or viewer. A different job or conversation starts with a fresh tab; the same context can continue on its current page. Profiles survive both idle closure and restart. Daemon shutdown closes all browser processes. All production CLI/ACP runs retain the common 30-minute deadline; manual takeover does not extend it. Demo does not call agent tools.

## Permission modes

**Supervised** is the default for existing and new agents. Every navigation, click, hover, scroll, drag, fill, selection, keypress, dialog decision and packet attachment requires a separate exact-action approval. Review it in the pinned area below the browser or in **Inbox**: the reason, parameters, frozen page evidence and exact upload contents remain available in both places. The panel keeps the decision buttons visible and places full frozen evidence behind Review exact action and page evidence. A browser approval already visible in the panel does not also display an overlapping toast; it remains in notification history.

**Autonomous preparation** requires the user to allow an exact HTTPS origin for the current task. The panel can allow the site and its pending navigation together, lists granted sites and offers revocation. Grants are isolated per agent and task chain, survive related follow-up runs, and never carry into a different user request or daemon restart. Agents cannot grant or modify site access. User site decisions and automatic preparation records append event version 17; versions 1–16 still replay.

Set a default in agent settings, or use **Agent default**, **Supervised** or **Autonomous preparation** in the conversation composer. Permission details explain the selected agent’s next turn in that conversation; the browser panel shows only the actual task’s captured mode, including when that task belongs to another conversation. Overrides are independent per participant and apply to future turns. Workflow follow-ups capture their originating conversation's browser override while retaining the saved runtime/model settings. Existing application conversations can also override future application workflow browser mode. Changing a mode does not escalate an already-started run. Scheduled routines and their descendants always use Supervised mode.

Automatic preparation has conservative tested rules for the hosted Greenhouse, Ashby, Lever, Comeet and Workable sites. It permits recognized read-only board/posting navigation without query parameters, and filling, native selection or attaching the attached job's approved/exported packet on recognized native application forms. Controls must be unique, visible, enabled and non-credential; the native form must have one recognized submission button and a same-origin form action. Custom domains, frames, widgets, changed or ambiguous forms fall back to exact-action approval. All buttons, submission keys and dialog decisions stay supervised. The final submission always needs a user decision, even when the agent omitted its submission purpose marker. This is enforced by action kind and preparation rules in the gateway, independently of the runtime's own permission mode.

During automatic preparation, browser requests that write, navigate through page scripts or target an inspected native submission endpoint are blocked. A blocked request is reported to the agent and viewer and disables further automatic form preparation on that page; retrying requires an exact user approval. Sites requiring autosave, GraphQL writes or asynchronous uploads may therefore need supervised preparation. Attaching a file is not proof that its upload succeeded. A user-approved interaction permits its website-controlled side effects; these rules do not prove arbitrary third-party script behavior or provide an OS network sandbox.

## Agent tools and gates

The shared stdio MCP server exposes three browser tools only to permitted roles:

- `pitchcrew_computer_inspect` opens the agent's browser if needed and returns inspected page text, controls, URL, title and snapshot-scoped `ref:` element IDs. `includeImage: true` adds a credential-redacted JPEG screenshot; text-only inspection is the tool default. References resolve to the same inspected DOM element and expire on a new inspection, navigation, tab change or manual handoff. CSS selectors remain supported.
- `pitchcrew_computer_wait` waits up to 30 seconds for all requested text, URL and visible selector/reference conditions, returning a bounded timeout result. Cancellation, capability loss and manual takeover interrupt waits without returning private page evidence.
- `pitchcrew_computer_request` proposes one exact action with a reason. It returns a pending user decision or a server-approved preparation record; it never performs the interaction.
- `pitchcrew_computer_execute` waits up to 30 seconds for a decision, then executes that exact action once. While pending, agents call it again to keep the run alive. During manual control, tools return a bounded waiting status without page evidence; agents call inspect again to wait.

The gate binds the run, role, card, action parameters, upload bytes and page fingerprint. It rechecks current role permissions, cancellation, site access, preparation rules and page state before executing. A changed URL, DOM or form value requires a new request. Approval is consumed before interacting, so failed or uncertain actions cannot reuse it. Run completion, cancellation, failure and daemon restart expire pending/approved actions. Browser actions never automatically mark cards submitted; users verify the website confirmation and record the outcome.

Uploads remain limited to `resume.md`, `cover_letter.md`, `form_answers.md`, `note.md` and generated resume/cover-letter PDF or DOCX files from the current approved, exported packet for the attached job. Paths resolve beneath that card's packet directory and file bytes are checked against the reviewed export. Agent tools expose neither arbitrary filesystem upload, shell execution nor JavaScript evaluation. Native human file picking belongs to private manual control; the streamed controls retain packet-only attachments.

Pages are untrusted data. Public HTTP(S) requests, redirects and subresources are checked against DNS/IP private-network rules. Local/private URLs and URL credentials remain blocked, keeping the browser away from the daemon's approval API. Headless sessions block service workers, WebSockets and downloads. Native sessions permit public WebSockets outside automatic preparation and human downloads during takeover; requests without an owned guest (including worker-only requests) are denied. These are application boundaries, not protection against adversarial DNS rebinding at the OS network level. First-level iframe targeting retains inspected frame fingerprints and unique selectors in Supervised mode; nested frames are uninspected. Popups become the selected page. Native desktop chrome provides tabs, navigation, search and find. General desktop applications and whole-desktop control remain outside this feature.

Hover, bounded element scrolling and drag actions use the same exact-action gate as other interactions; persisted action variants use event version 29, retaining versions 1–28.

`pnpm test` covers real headless Chromium against intercepted fictional forms for all five providers, blocked preparation writes, credential redaction, persistent isolated profiles, resets, manual leases and in-flight privacy, idle closure, task grants, HTTP streaming/session protection, cancellation, approval replay and MCP contracts. It performs no live provider runs or external submissions. `pnpm test:desktop` also runs hidden Electron checks with real native guests, trusted human typing, same-page agent actions, private takeover, tabs, popup openers and graceful cleanup. No test shows or focuses an OS window. Live provider/browser combinations and third-party application site variants still require manual verification. Run `pnpm browser:install` before testing on a new checkout.

## Form assessments and submission receipts

`assessForms` and `recordSubmissions` are separate optional capabilities, defaulting off and requiring computer use. `pitchcrew_assess_form` snapshots current server-inspected controls onto the attached card; agent-provided selectors must match inspected controls exactly, and duplicates fail. All controls remain present, including unassessed ones. Required/visible/disabled flags, labels, types, select choices and accepted file extensions come from the browser. Conditional requirements, missing answers and blockers are explicitly agent annotations, with uninspected sections recorded. Before drafting a linked application, **Job details > Application > Brief and requirements > Inspect application form** starts an attached inspection conversation with an enabled browser/form-assessment agent (Submitter by default). It needs no reviewed/exported packet and requests inspection only, using the existing browser supervision and manual takeover. The user returns to the job, extracts or reviews the brief, and confirms the fields and files together with the brief. Required flags, accepted upload formats, choices and character limits come from inspected controls. Blocked or uninspected sections stay explicit. If inspection is unavailable, the user can explicitly choose to check the form themselves when preparing the brief; agents cannot make that choice. A missing job link remains an uninspected limitation.

Writer and Reviewer receive a bounded, user-confirmed form summary through the isolated prompt and card tool. Raw browser text/HTML, selectors, screenshots and entered values are excluded. Extraction can use the field metadata to propose legitimate questions but has no profile or tools, and its form summary is replaced with server-inspected metadata. Form confirmation grants no interaction permissions. Changed requirements make the old confirmation stale and invalidate packet review and unused packet/browser approvals; confirm the new findings and review the packet again. Identical summaries preserve validity. Submission preparation reinspects the current form and retains all existing final-submission gates.

Mark the final click or Enter request `purpose: submission` with the exact `exportApprovalId`. Before performing the approved action, the gate atomically consumes its approval and records an uncertain attempt bound to the card, packet digest, export and browser page. All further interactions on the card are blocked, even an ordinary click without a purpose. `pitchcrew_capture_submission` saves an exact quotation from the changed browser snapshot for that attempt. It never marks a card submitted. Users verify the evidence on the job. After restart, users may enter a source URL, quotation/reference and explicit verification checkbox; this evidence is clearly recorded as user-reported, not server-observed. Verification rechecks the current packet and consumed/failed submission action; it transitions awaiting-approval cards or preserves later tracked states. Verifying no submission occurred resolves uncertainty and permits a separately approved retry.

## Binary packet review

Select PDF and/or DOCX when requesting export approval. Generation completes first; approval stores frozen bytes, MIME type and SHA-256 manifest alongside the exact packet. PDF displays every page inline in Inbox through lazy PDF.js, with only a local worker and whitelisted bundled Helvetica substitute font; formatted PDFs embed their own font. Closing cancels rendering and disposes the worker/document; failures are visible. DOCX previews complete source text. Formatted documents lay out Markdown structure and plain text documents print it literally; neither executes HTML or loads remote assets. PDF names unsupported characters explicitly; DOCX supports Unicode. Inbox shows page counts derived from the frozen bytes. See [packet exports](packet-exports.md). Local export validates the reviewed manifest before consuming approval and writes its exact bytes. Binary uploads verify SHA-256 and complete Buffer equality, plus the current packet and card-scoped export path; they never decode binary bytes as UTF-8 for verification. Browser upload proposals show the reviewed text, format and byte digest. Download links appear after approved export.

An uncertain submission can continue through a separately approved browser dialog only when `submissionAttemptId` binds the same run, card, current exported packet and observed dialog. The consumed continuation approval is saved on the attempt. No click, keypress or navigation retry is allowed.

## Task browsing grants

In Autonomous preparation mode, **Allow browsing for this task** is separate from **Allow preparation for this task**. Browsing grants permit HTTPS read navigation (including ordinary search queries), scrolling and hovering on the exact origin. Application/submission and destructive-looking routes remain supervised, as do clicks, keys, dialogs, fields and files. Preparation grants retain the existing recognized-form policy. Writes and script-driven navigation remain blocked during automatic actions; a blocked page returns to supervised requests. Grants are user-only, revocable, isolated to the task chain and lost on restart. Version 30 records the distinct grant type; older permission events remain readable.

## Agent tabs

`pitchcrew_computer_tabs` lists the current job/conversation's tabs, opens blank tabs, selects a tab or closes one. It cannot reach another session or profile. Tab changes expire unused approvals and are paused during manual takeover; unresolved submissions block changes. Actions, inspection and waits accept `tabId`. Proposed actions always bind the resolved tab, even when omitted by the caller, and execution returns to that exact tab before checking evidence. Version 31 persists that binding. Closing a tab skips before-unload scripts; ordinary website dialogs must be resolved first.

## Browser diagnostics

Inspection includes at most 30 console/script failures and 30 failed HTTP requests for the selected owned tab. Arbitrary console output is reduced to a generic error; recognized engine failures have quoted values, tokens and URLs sanitized. Request summaries contain method, resource type, status and a bounded URL with no credentials, query or fragment; headers, bodies, responses, console objects and stack traces are excluded. These buffers are memory-only, clear on page navigation and are cleared/disabled throughout private takeover. They are never sent to application analytics.
