# Local browser computer use

For the responsiveness design, rollout and fixture measurements, see [Smoother browser viewing and manual takeover](browser-interaction-performance.md).

Enable **Crew → agent settings → Computer use** and install Chromium once:

```sh
pnpm browser:install
```

The agent's browser appears inside **Chat → Browser** in both the browser and Electron app. Chromium runs headless locally; the authenticated chat panel streams its page view. It never attaches to your daily browser or reads its cookies. Each agent has a separate persistent profile under the data directory's `browser-profiles/<role-id>` folder, retaining sign-ins and website storage across runs and daemon restarts.

## Chat panel and manual control

The panel opens when a participating agent starts browsing. Closing the panel suppresses automatic reopening in that conversation for the tab session; its Browser button still indicates activity. The compact header combines the selected agent, live status and manual handoff. Its agent menu lists conversation participants with waiting/manual indicators, keeps one selected view and never switches away automatically. A single browser toolbar keeps the current address visible, with manual Go/reopen actions and a Page view settings menu for zoom and panning. The initial selection follows the selected conversation participant. The panel is resizable with a pointer or arrow keys on its divider, and opens as a focus-managed full-screen sheet on small screens. Expand browser opens the same sheet on desktop; Restore split view returns to chat. The live page viewport follows the available panel size so websites reflow to fill the view. Resizing waits while an exact action is pending or executing, and another viewer cannot resize a manually controlled browser. Page view settings offers Fit to panel and enlarged views; Pan enlarged view moves around the image without sending page input. It is unavailable in read-only crew history and agent DMs.

The selected agent's browser can be viewed from another conversation it participates in. The header marks a browser belonging to another conversation as elsewhere. Browser task details links to its actual conversation or job, states the active run's captured mode and lists/revokes task site grants. Browser preferences and live frames are separate from the workspace snapshot. Stream requests require the local user session, UI client header and current conversation membership. Capability and conversation checks run before frame delivery and on static-page heartbeats. HTTP responses are not cached and live frames are never archived. Each session shares one Playwright screencast across viewers; a slow viewer retains only the newest pending frame, with bounded response buffering. The renderer decodes one frame at a time and retains only its newest pending image. Navigation, page replacement and viewport changes invalidate older frames and stale manual clicks. Dialog, title and warning updates do not depend on another image arriving. Hiding the panel or backgrounding the app document stops that viewer's subscription without returning manual control; capture stops after the last viewer leaves. Browser streaming falls back to shared, low-rate screenshot capture when screencast startup fails or produces no first frame. The panel labels this reduced-rate view. Set `PITCHCREW_BROWSER_SCREENCAST=0` before starting the daemon to select the screenshot fallback explicitly.

Choose **Take control** to sign in, handle CAPTCHA, navigate or correct a field inside the panel. Click the page, then type or paste; Tab and arrow keys operate remote controls, and Escape returns focus to the panel's controls. On touch devices, swipe vertically to scroll the remote page. Choose Type on page for a private text-entry tray, with explicit Send text, field navigation, selection, deletion and scroll controls. This tray is cleared when hidden, when changing agents or when control is returned. The tray supports the device keyboard and paste; it never saves entered text. Manual text never becomes a chat message or board event. Browser dialogs and prompt answers have explicit manual controls. Agent actions and inspection pause during takeover, including snapshots already in flight. An inspection spanning takeover and return is discarded even if the agent has control again when it finishes. Pending and unused approved actions are invalidated. **Return to agent** discards old page evidence and lets the agent inspect the current page again. Agent snapshots redact recognized password and one-time-code fields, including revealed passwords, and mask those fields in screenshots. Agent password fills remain forbidden.

One manual controller holds a renewable 45-second lease per agent. A disconnected or expired controller leaves the agent paused; recover control from the panel after the old lease expires. Pending input is sent in order. Manual control does not bypass an unresolved submission attempt: verify its outcome on the job before further interactions.

**Hide browser** keeps the browser and manual pause. **Browser options → Close browser** stops its active run and closes Chromium. **Browser options → Reset saved sign-ins** also removes that agent's saved sign-ins and website storage, after an explicit confirmation; packets and history remain. A finished run expires its approvals but keeps the browser available. An idle browser closes after ten minutes without an active run or viewer. A different job or conversation starts with a fresh tab; the same context can continue on its current page. Profiles survive both idle closure and restart. Daemon shutdown closes all browser processes. All production CLI/ACP runs retain the common 30-minute deadline; manual takeover does not extend it. Demo does not call agent tools.

## Permission modes

**Supervised** is the default for existing and new agents. Every navigation, click, fill, selection, keypress, dialog decision and packet attachment requires a separate exact-action approval. Review it in the pinned area below the browser or in **Inbox**: the reason, parameters, frozen page evidence and exact upload contents remain available in both places. The panel keeps the decision buttons visible and places full frozen evidence behind Review exact action and page evidence. A browser approval already visible in the panel does not also display an overlapping toast; it remains in notification history.

**Autonomous preparation** requires the user to allow an exact HTTPS origin for the current task. The panel can allow the site and its pending navigation together, lists granted sites and offers revocation. Grants are isolated per agent and task chain, survive related follow-up runs, and never carry into a different user request or daemon restart. Agents cannot grant or modify site access. User site decisions and automatic preparation records append event version 17; versions 1–16 still replay.

Set a default in agent settings, or use **Agent default**, **Supervised** or **Autonomous preparation** in the conversation composer. Permission details explain the selected agent’s next turn in that conversation; the browser panel shows only the actual task’s captured mode, including when that task belongs to another conversation. Overrides are independent per participant and apply to future turns. Workflow follow-ups capture their originating conversation's browser override while retaining the saved runtime/model settings. Existing application conversations can also override future application workflow browser mode. Changing a mode does not escalate an already-started run. Scheduled routines and their descendants always use Supervised mode.

Automatic preparation has conservative tested rules for the hosted Greenhouse, Ashby, Lever, Comeet and Workable sites. It permits recognized read-only board/posting navigation without query parameters, and filling, native selection or attaching the attached job's approved/exported packet on recognized native application forms. Controls must be unique, visible, enabled and non-credential; the native form must have one recognized submission button and a same-origin form action. Custom domains, frames, widgets, changed or ambiguous forms fall back to exact-action approval. All buttons, submission keys and dialog decisions stay supervised. The final submission always needs a user decision, even when the agent omitted its submission purpose marker. This is enforced by action kind and preparation rules in the gateway, independently of the runtime's own permission mode.

During automatic preparation, browser requests that write, navigate through page scripts or target an inspected native submission endpoint are blocked. A blocked request is reported to the agent and viewer and disables further automatic form preparation on that page; retrying requires an exact user approval. Sites requiring autosave, GraphQL writes or asynchronous uploads may therefore need supervised preparation. Attaching a file is not proof that its upload succeeded. A user-approved interaction permits its website-controlled side effects; these rules do not prove arbitrary third-party script behavior or provide an OS network sandbox.

## Agent tools and gates

The shared stdio MCP server exposes three browser tools only to permitted roles:

- `pitchcrew_computer_inspect` opens the agent's browser if needed and returns inspected page text, controls, URL, title and a credential-redacted JPEG screenshot.
- `pitchcrew_computer_request` proposes one exact action with a reason. It returns a pending user decision or a server-approved preparation record; it never performs the interaction.
- `pitchcrew_computer_execute` waits up to 30 seconds for a decision, then executes that exact action once. While pending, agents call it again to keep the run alive. During manual control, tools return a bounded waiting status without page evidence; agents call inspect again to wait.

The gate binds the run, role, card, action parameters, upload bytes and page fingerprint. It rechecks current role permissions, cancellation, site access, preparation rules and page state before executing. A changed URL, DOM or form value requires a new request. Approval is consumed before interacting, so failed or uncertain actions cannot reuse it. Run completion, cancellation, failure and daemon restart expire pending/approved actions. Browser actions never automatically mark cards submitted; users verify the website confirmation and record the outcome.

Uploads remain limited to `resume.md`, `cover_letter.md`, `form_answers.md`, `note.md` and generated resume/cover-letter PDF or DOCX files from the current approved, exported packet for the attached job. Paths resolve beneath that card's packet directory and file bytes are checked against the reviewed export. Neither agents nor manual browser controls expose arbitrary filesystem upload, shell execution or JavaScript evaluation.

Pages are untrusted data. Public HTTP(S) requests, redirects and subresources are checked against DNS/IP private-network rules. Local/private URLs, URL credentials, service workers, WebSockets and downloads remain blocked, keeping the browser away from the daemon's approval API. These are application boundaries, not protection against adversarial DNS rebinding at the OS network level. First-level iframe targeting retains inspected frame fingerprints and unique selectors in Supervised mode; nested frames are uninspected. Popups become the selected page. Browser chrome, native file pickers, OS dialogs, desktop applications and cloud hosting are outside this feature.

`pnpm test` covers real headless Chromium against intercepted fictional forms for all five providers, blocked preparation writes, credential redaction, persistent isolated profiles, resets, manual leases and in-flight privacy, idle closure, task grants, HTTP streaming/session protection, cancellation, approval replay and MCP contracts. It performs no live provider runs or external submissions. Live provider/browser combinations and third-party application site variants still require manual verification. Run `pnpm browser:install` before testing on a new checkout.

## Form assessments and submission receipts

`assessForms` and `recordSubmissions` are separate optional capabilities, defaulting off and requiring computer use. `pitchcrew_assess_form` snapshots current server-inspected controls onto the attached card; agent-provided selectors must match inspected controls exactly, and duplicates fail. All controls remain present, including unassessed ones. Required/visible/disabled flags, labels, types, select choices and accepted file extensions come from the browser. Conditional requirements, missing answers and blockers are explicitly agent annotations, with uninspected sections recorded. Writer reads them through the normal card context/tools; existing scoped crew messages provide the handoff.

Mark the final click or Enter request `purpose: submission` with the exact `exportApprovalId`. Before performing the approved action, the gate atomically consumes its approval and records an uncertain attempt bound to the card, packet digest, export and browser page. All further interactions on the card are blocked, even an ordinary click without a purpose. `pitchcrew_capture_submission` saves an exact quotation from the changed browser snapshot for that attempt. It never marks a card submitted. Users verify the evidence on the job. After restart, users may enter a source URL, quotation/reference and explicit verification checkbox; this evidence is clearly recorded as user-reported, not server-observed. Verification rechecks the current packet and consumed/failed submission action; it transitions awaiting-approval cards or preserves later tracked states. Verifying no submission occurred resolves uncertainty and permits a separately approved retry.

## Binary packet review

Select PDF and/or DOCX when requesting export approval. Generation completes first; approval stores frozen bytes, MIME type and SHA-256 manifest alongside the exact packet. PDF displays every page inline in Inbox through lazy PDF.js, with only a local worker and whitelisted bundled Helvetica substitute font; formatted PDFs embed their own font. Closing cancels rendering and disposes the worker/document; failures are visible. DOCX previews complete source text. Formatted documents lay out Markdown structure and plain text documents print it literally; neither executes HTML or loads remote assets. PDF names unsupported characters explicitly; DOCX supports Unicode. Inbox shows page counts derived from the frozen bytes. See [packet exports](packet-exports.md). Local export validates the reviewed manifest before consuming approval and writes its exact bytes. Binary uploads verify SHA-256 and complete Buffer equality, plus the current packet and card-scoped export path; they never decode binary bytes as UTF-8 for verification. Browser upload proposals show the reviewed text, format and byte digest. Download links appear after approved export.

An uncertain submission can continue through a separately approved browser dialog only when `submissionAttemptId` binds the same run, card, current exported packet and observed dialog. The consumed continuation approval is saved on the attempt. No click, keypress or navigation retry is allowed.
