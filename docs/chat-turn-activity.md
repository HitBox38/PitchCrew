# Chat turn activity

Rules for contributors and coding agents. If a change makes anything here false, update this file in the same change.

Job activity saves a concise one-line description with each applied agent workflow result, attributed to the agent. Runtime prompts request a `changeSummary` describing the specific completed change (up to 300 characters); older results without it receive factual document/fit/review summaries. Each write keeps its own append-only event, including deep-review corrections and rechecks. Job-changing tools use their reason for the activity description.

Conversation transcripts initially load and render a target of 50 message/activity entries (up to 51 to keep a settled turn and its answer together) through the session-protected history route; the renderer retains the selected page rather than the full saved history. Older, Newer and Latest controls keep every entry accessible without mounting an entire history; while the reader follows the latest page, entries already shown stay put (the newest window never drops its oldest entries under the reader, and an entry that leaves the live data, such as a finished reply or turn, stays until a page fetched for the current revision arrives), and only user messages sent since the page opened are scroll anchors, because the shadcn scroller pins any unpinned anchor when the entry count holds steady; the scroller pins a new message only as the last entry, so `usePinSent` pins one the agent's turn rendered before, anchored like the scroller's own pin; older pages remain anchored while replies stream, and Latest restores live following. Browser find and text selection cover the displayed page. Chat shows each agent turn between its triggering message and answer, with one collapsed activity disclosure per turn, step/update counts, expandable outcomes, elapsed time and a Stop control in the composer. Live turns preview the latest public update, the latest failed step while it is among the turn's last three tool steps (thinking markers and commentary do not count), and the current step, in their original order; completed turns keep their latest failed step visible, and failed, stopped or waiting turns up to their three latest, each with its reason line, or otherwise the latest interrupted step; a browser call stopped by the user's takeover is saved as an interrupted "Paused while you had control" step, summarized as "paused while you had control" (no count, since one takeover can span several waits) and never counted as failed, interrupted or kept as the settled issue. While a browser request waits (its step ochre from the moment it is asked, whether or not the agent has started waiting on it), the turn heading (one line in every state; its counts give way first) reads "Waiting for your OK" with the request's own title (ochre bead, no running timer), the chat header says "Waiting for your OK" and the participant bead turns ochre; while the user holds a running agent's page the turn and header read "Paused · you have control" (no timer) with ochre beads and an ochre Browser button dot, and the collapsed turn shows the last finished step rather than the call blocked on the user (while a request awaits their OK it previews that request's own ochre step). Browser steps the gateway records are named like the tray ("Read the page", "Asked to click “Learn more”", "Clicked “Learn more”", "Typed into “Customer name”", "Waited for your OK to …") by the shared types-only `@pitchcrew/core/browser-action-labels`, and step labels never carry typed or chosen values. A request the server allowed without asking never says "Asked": it reads "Allowed by Auto to click “Next”" (the run's browser mode label) or, for an Autonomous preparation site grant, "Allowed for a site you granted to …". Each browser action is one row: the row that asked for an approval is carried out in place and moves to the latest position, while an overlapping duplicate call gets its own row and never overwrites the outcome. A request the user rejects through a decision reads "You declined to …" (never a failed step), and the agent is told the user declined rather than that the browser failed; requests invalidated by job, form or page changes keep the neutral wording. The waiting step is found once per turn: the current request's running row, or else only the latest asked row. Only browser steps (kind `browser`, or older steps saved without a kind) can wait on the user, so another tool whose label happens to match a browser label never reads as waiting. Ordinary answers have a Copy action and timestamp below their content (hover/focus on fine pointers, persistent on touch); question records exclude Copy; normal prose is bounded to 76ch while tables and code retain the lane width. The composer has no separate progress strip; queued, paused and failed follow-ups use a compact disclosure that remembers collapse per device and reopens on new attention without remounting editors, shows the saved pause reason and reuses user-paused queue recovery and running-only requests never appear there. Follow-up action choices appear only once the user drafts text or attaches files. All runtime chats observe scoped Pitchcrew tool calls at the daemon gateway; adapters add the runtime's own tool calls (below); native assistant commentary is separated from structured reply previews, and supported native thinking signals show a phase marker without private reasoning text; a marker that arrives in the same event as a tool call (Goose) shows before that call's step and ends when the call starts. `pitchcrew_report_progress` supplies up to eight public updates per chat turn. Raw tool arguments and results, secrets, browser inputs and manual takeover content are excluded; a tool step carries only its kind, label, bounded public target and failure reason. Live entries are bounded to 80 per run, commentary to 4,000 characters, a step's target to 200 and its failure reason to 300 (shared `activityLimits`); truncation is visible. SSE merges run snapshots by ID and avoids re-sending unchanged activity with reply tokens. Completed, failed, waiting and cancelled turns persist their activity on the run when execution settles, with unconfirmed running steps marked interrupted; in-flight public activity, including each step's kind, target and reason, is checkpointed in one bounded SQLite row per run, immediately on first activity and at most every ten seconds thereafter (an invalid optional step field is dropped on save or restore without discarding the checkpoint); startup restores the last checkpoint and marks unconfirmed steps interrupted, while the latest uncheckpointed interval can be lost. Agent conversation history remains final messages only. See [docs/chat-redesign.md](chat-redesign.md).

**Tool steps.** Every new tool step records a kind from `activityToolKinds` in `@pitchcrew/core/tool-activity` (command, read, edit, search, fetch, web_search, mcp, agent, todo, browser, ask, check or other) and a verb-first label in the tense of its outcome. Crew tool steps recorded by the gateway take their words from `crewToolLabels` ("Reading profile" while running, "Read profile" once done, "Couldn't read profile" when failed); an action without an entry reads "Using a crew tool" and never echoes its name or arguments. Browser actions keep the browser labels above, and every browser tool is kind `browser`. A crew step's target comes only from the per-action allowlist in `packages/orchestrator/src/crew/gateway/tool-details.ts`: the connected service and tool ("Gmail · search messages"), skill name, recipient role name, job-link host, attachment file name (only when the run may read its conversation), memory query, application company and title, target state in words or delegated subtask count. Browser tools never get one, and message, memory, profile and packet text never becomes one. A failed gateway call is classified once (`packages/orchestrator/src/crew/gateway/failures.ts`) into a closed reason from `@pitchcrew/core/tool-failures`, and its step says why: the first line of Pitchcrew's refusal (cut before any Playwright "Call log:", with the run token and credential shapes removed), at most two validation issues as `<issue> at <field path>` ("Unexpected field" for an unrecognized key, then "(+N more)"), or a fixed sentence for browser tools, local file and network system errors and internal faults. A refusal's wording is classified from that same first line (only the user's own outcomes are recognized anywhere in the message), so a call log or quoted packet text never changes its reason. `setup_required` needs a sentence that tells the user to install, connect, reconnect or sign in, or says something is not installed, connected or signed in; a connection that failed ("Could not connect …") is `unavailable`, and a sentence that only mentions installing falls through to the other refusals. The error returned to the agent is unchanged. Declined requests, takeover pauses and stopped runs carry no reason.

In chat turns (including source extraction) and deep-review stages, adapters also show the runtime's own tool calls, parsed from its native stream by `packages/adapters/src/<runtime>/tools.ts` or, for Kiro, the shared ACP parser (see [runtimes](runtimes.md#native-tool-activity)); ordinary workflow runs never show them. Workflow and document-correction runs still parse the stream for failure reports (`RunContext.onToolFailure`) and pass on only each failed call's closed failure (its reason, kind and any reviewed tool name), for diagnostics only, never shown or saved. Native steps use generic labels by kind ("Running command", "Read file", "Search failed") and a target derived from the call's input, such as the command's first line without a `bash -lc` style wrapper, a path relative to the run folder or `~`, `<pattern> in <folder>`, a URL's origin and path without credentials, query or fragment (only the scheme for non-web URLs), the web query, plan progress ("2/5 done"), a subagent's short description (never its prompt or goal: Codex names only its collab tool, `spawn_agent`, `send_input`, `wait` or `close_agent`, and Hermes `delegate_task` shows none) or another MCP server's tool and server names. A failed native step shows the runtime's error text, with commands as `Exit code N: <last output line>`, or the closed reason's fixed description when no text remains; image content is never read, and error text a runtime builds from the call's arguments is dropped (Gemini CLI MCP errors, OpenCode invalid-tool calls, Goose calls it could not parse, Pi's echoed arguments). Input Claude Code could not parse as JSON fails as invalid input with only the first sentence of Claude's answer: everything from its "You sent (first N of M bytes):" quote of that input on is dropped. Calls to Pitchcrew's own MCP server, matched by server name so its connector tools match too, get no target and are left to the gateway, except a call that failed before the daemon received it (MCP input validation, an unknown tool, or the runtime's own refusal, timeout or transport failure): it becomes one failed step with its crew tool's kind (kind `mcp` for a name Pitchcrew does not publish) and failed label, and the runtime's reason, in which the MCP server's list of unrecognized keys reads "Unexpected field" so the keys a model sent are never named; a failure it cannot recognize is `unclassified` rather than a tool error, since the call never ran, and a browser tool's step shows only the closed reason's shared description, never runtime text. A request Goose could not parse at all names no tool, so it shows as a generic "Tool failed" step with the shared invalid-input sentence. A runtime timeout on a call the daemon still finishes therefore shows both steps. Native targets and reasons first lose the exact secret values in the runtime's spawn environment (the run token included, and each line of a multi-line secret), then terminal formatting, control and bidirectional characters and repeated whitespace, then credential shapes (matched only in the first 4,096 characters, or 16 times the bound if longer, and the word that window cuts is dropped whole), before their bounds. The shapes include known token prefixes, private keys, URL user info and secret query parameters, secret flags and environment assignments, an `Authorization` or secret header's whole value with its scheme word, a `Cookie` header, and curl's `-u name:password`, `-b name=value` and `--oauth2-bearer`; a secret with no recognizable shape (an unprefixed token typed into a path) is removed only when it is an exact value from the runtime's environment; the daemon applies that line cleanup and the bounds again when it records a tool step.

Each step row shows its outcome bead, a muted kind glyph (the generic tool glyph for steps saved without a kind), the label, its target on one line (truncated, with the full text in a tooltip; a target with no room beside the label moves below it, and on touch and narrow screens it always takes its own line under the label) and the duration. Targets use the app face; only a runtime's own command line, path, search pattern or URL (a native step of kind command, read, edit, search or fetch) uses the code face. The renderer tells native steps apart by their shared `native-` id prefix (`runtimeStepId` and `isRuntimeStep` in `@pitchcrew/core/tool-activity`), so no other step id may start with `native-`. Targets and reasons take their own text direction, so right-to-left text keeps its first words when cut short and a right-to-left reason aligns right. A failed step's reason is plain rose text below the row, outside its button: clamped to two lines, with the full text in a tooltip, linked to the button by `aria-describedby` and never an alert. It is absent while the step waits on the user and on declined or paused steps, and shows in full, in place, while that step's details are open. A step's details show its outcome, start time, full target, a Copy reason action and, for thinking, that its text stays private. Long step groups show their latest six steps, with earlier ones behind "Show N earlier steps". Telemetry never receives activity text: a failed tool call reports only closed words (a reviewed tool name or a tool kind, and the failure reason); see [error tracking](analytics/error-tracking.md).

Chat history presents automatic same-run @mention forwards once, preserving saved messages and tasks; never-started queued, paused and failed inputs remain in the queue. Settled activity anchors to its own reply through shared server/renderer ordering. Pending questions have one answer form, with a compact transcript record; choices take natural height before bounded scrolling, with answer/actions outside the scroll area. Chat prose uses 14/20 type and hanging lists, tables keep one copy action, and one live announcer serves each conversation. Mobile job chat uses compact current-stage/next-action text and the existing job controls below the title.

Chat dispatch presentation uses the first saved run start for each user request, preserving original written timestamps and sharing server/live ordering. The queue remembers collapse per conversation/device, reopens only for new attention and offers full-text reading plus a reference-preserving multiline editor without changing the main draft. Interrupted or failed requests expose a gated Retry for the head request, preserving finished recipients; diagnostics remain behind Details. Non-head request resumes reject before mutation; explicit Send now and resume queue retains its reorder action. Head retry continues later never-started paused messages and stops for separate review at another attempted failure. User-paused queues expose Resume all, row menus avoid duplicate primary recovery, and successful recovery restores owned focus to the composer or Stop. Paused sends visibly say Sends after you resume with a matching accessible name. Messages held by a question retain an After your answer state on phones. An open question replaces the empty idle composer with Write a message for later; drafts, attachments and live Stop controls remain available. Automatic question handoffs focus the free-answer text field, never a one-click choice; unavailable targets keep the composer visible. Deleting the last draft text keeps that composer session visible across focus changes until question collapse, resolution or navigation. Question answer drafts, selections and response locks survive chat navigation in memory; own acknowledged responses clear their drafts; external resolution keeps a different unsent response in a recovery tray, and collapsing known questions never suppresses a future question. Failed answers retain text and owned focus; acknowledged typed answers restore owned text focus, while choice answers use a neutral focus target without opening a touch keyboard. An open dock suppresses the matching transcript question record. Failure follow-ups use the same controlled reveal-and-focus action. Historical run failures use quiet explanations and copyable diagnostics rather than alert roles. The single chat announcer reports coarse working/question state and observed failed/stopped transitions, never repeated commentary text or old failures on navigation; it starts empty on each conversation. The transcript log explicitly disables live announcements. A visibly open question suppresses only its matching transient toast; saved attention, the bell and unrelated notices remain intact.

Short windows compact secondary chat chrome and preserve readable history; bounded queue previews and whole-column scrolling keep controls reachable independently of the browser viewport. The active Scroll to latest control has its own strip clear of reading text. New devices use the Comfortable chat reading width; existing device width preferences remain intact. Chat tables have a semantic keyboard-scroll viewport and overflow-only cue, with one copy action below. Read-only Markdown task states use labelled shared checkboxes. New messages and queued edits share the strict reference-input serializer: display labels stay local while identity, trim-relative offsets and skill revisions go to the API.

Question responses distinguish an acknowledged mutation with a failed refresh from a rejected save; ambiguous responses retain their lock and offer a read-only status check before another POST. Shared job queue holds remain visible in attached conversations without local queued rows and link to the actual blocker. Worked durations exclude saved human-answer waits and idle continuation queue gaps. Reference decoration retains the default GFM pipeline; inline references preserve prose line height with larger hit areas. Question animation clips never own scrolling; the chat column reveals growing inputs and actions while respecting deliberate reading and active pointer presses.

Main composer text, atomic references and File objects live in a renderer-scoped store keyed by conversation, preserving drafts across page navigation. Sending snapshots the submitted payload and leaves a fresh editable draft; acknowledged completion consumes only that snapshot. Unconfirmed sends keep separate recoverable drafts without automatic retries or content-based receipt guesses; using a kept draft swaps whole payloads without discarding the other draft. Neither composer nor question drafts promise persistence after a full process restart. Definite HTTP question rejections retain the server's reason instead of claiming a retry will work. Choice confirmation keeps focus out of text entry, accepts a corrected digit during the short delay and excludes unrelated controls; custom single-answer typing clears a stale choice. Short coarse-pointer chats temporarily prefer the sidebar rail without overwriting the normal preference, phone view tabs share the row below the title, and short job sheets scroll identity, tabs and content together above the action footer. Chat list renderers own outside markers, including multi-digit ordered gutters; reference popovers use padded clay surfaces with a working Agent settings action for available mentions.
