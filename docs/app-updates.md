# Pitchcrew update checks

Production workspaces check for a newer published build when opened and once an hour while open. Settings > General shows the running version and commit, the last check, an automatic-check preference, and **Check for updates**. The shared sidebar footer keeps a refresh icon on every workspace screen when no update notice is shown. Clicking it checks for updates and shows the result in a toast; it is busy during a check and disabled when the installation disables checks. A newer build replaces it with an update download icon. Settings and Getting started share that compact icon row, and all controls have accessible labels and tooltips. The collapsed desktop sidebar stacks the same controls vertically; the mobile sidebar drawer keeps the compact row. Opening it shows a release download link and **Dismiss for this session**. Dismissal lasts for this workspace session and applies only to that build; the release remains available in Settings, and a manual check restores the notice if that build is still available. The workspace shell owns update checks independently of the sidebar drawer's lifecycle. Downloads and installation remain user actions; no installer is downloaded or executed automatically.

The daemon reads the public `HitBox38/PitchCrew` GitHub Releases API without credentials. It accepts only full, published `build-<40-character commit SHA>` releases and constructs the release URL itself. When the commits differ, GitHub's commit comparison determines whether the published build descends from the running build. Identical builds and source checkouts ahead of the release do not prompt a downgrade. Unknown identities, divergent histories, and unavailable comparisons never claim the app is current. A valid release link remains available when comparison is inconclusive.

Installer preparation writes the exact build commit to `runtime/build-info.json`; this works without Git in the installed app. Source launches read local HEAD once per daemon. The version is read from the root package metadata. The reported build belongs to the daemon serving the UI, including when the desktop launcher reuses a running daemon or background service. Source users should update their checkout; installed users can download a replacement installer from the release page and keep their existing data folder.

Status and check endpoints require the existing loopback UI session. Status reads do not make network requests. Checks have a ten-second deadline, a 256 KB response limit, no redirects, and no application content, tokens, cookies or custom identifiers. The commit comparison uses page two with one commit per page to omit file diffs. Concurrent checks share one request; automatic results are cached for an hour and repeated manual checks for a minute. Failures show a readable status and never interrupt other work. The daemon cancels checks when closing.

The automatic-check preference is device local, persists under `pitchcrew-automatic-updates-v1`, and synchronizes across same-origin tabs. Development launches support manual checks but do not check automatically. `PITCHCREW_UPDATE_CHECKS=0` disables all release checks. Direct daemon construction is unconfigured by default. Desktop smoke tests inject public API fixtures to verify automatic notices, manual checks, dismissal and saved preferences in the real renderer; packaged smoke scripts disable checks. Automated verification stays offline.

Electron permits only the exact Pitchcrew build release URL in addition to its existing connector setup links. The link opens in the system browser through the existing origin-checked main-process navigation handler; no new renderer Electron API is exposed.
