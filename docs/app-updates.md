# Pitchcrew update checks

Production workspaces check for a newer published build when opened and once an hour while open. Settings > General shows the running version and commit, the last check, an automatic-check preference, and **Check for updates**. The shared sidebar footer keeps a refresh icon on every workspace screen when no update notice is shown. Clicking it checks for updates and shows the result in a toast; it is busy during a check and disabled when the installation disables checks. A newer build adds a full-width teal **Download update** row above Settings and Getting started. The collapsed desktop sidebar uses an icon-only action; the mobile drawer retains the full row. Hovering or focusing the action shows a text-only tooltip with the available version and up to five change bullets (180 characters each); truncated summaries point to the full release notes in Settings. Older releases without a changelog say **Release notes unavailable**. Tooltips have no links or buttons. The adjacent × offers **Dismiss for this session** and returns focus to the check control; dismissal is disabled while checking, downloading or restarting. Dismissal lasts for this workspace session and applies only to that build; the release remains available in Settings, and a manual check restores the notice if that build is still available. The workspace shell owns update checks independently of the sidebar drawer's lifecycle. Downloads and installation remain explicit user actions. Supported installed Windows and Linux builds offer **Download update**, percentage progress, then **Restart to update** in the sidebar (**Install and restart** in Settings). Download progress is shown in the row, and busy actions remain focusable so their tooltip is available without allowing repeated activation. Starting a download from Settings restores a dismissed sidebar notice. Download or installation errors stay available for retry, with details in the tooltip and Settings. The desktop main process asks for confirmation and warns that running agents will be interrupted. Neither checks nor ordinary app quits download or install updates.

Release publishing titles new builds `Pitchcrew <version>` using the verified Windows installer filename and appends GitHub-generated **What’s Changed** notes since the preceding published build release to the existing installer instructions. The release job continues to execute no repository code; resumed drafts keep their original notes. The checker extracts a bounded plain-text changelog from that section, never renders release HTML or images, and never treats installer instructions as changes. Native tooltips use release notes only when their version matches the native updater’s available version.

The daemon reads the public `HitBox38/PitchCrew` GitHub Releases API without credentials. It accepts only full, published `build-<40-character commit SHA>` releases and constructs the release URL itself. When the commits differ, GitHub's commit comparison determines whether the published build descends from the running build. Identical builds and source checkouts ahead of the release do not prompt a downgrade. Unknown identities, divergent histories, and unavailable comparisons never claim the app is current. A valid release link remains available when comparison is inconclusive.

Installer preparation writes the exact build commit to `runtime/build-info.json`; this works without Git in the installed app. Source launches read local HEAD once per daemon. The version is read from the root package metadata. The reported build belongs to the daemon serving the UI, including when the desktop launcher reuses a running daemon or background service. Source users should update their checkout; installed users can use the in-app updater where supported, or download a replacement installer from the release page and keep their existing data folder. Native desktop checks compare installer semantic versions; each production release must bump the version. Source/browser checks retain their commit-ancestry comparison.

Status and check endpoints require the existing loopback UI session. Status reads do not make network requests. Checks have a ten-second deadline, a 256 KB response limit, no redirects, and no application content, tokens, cookies or custom identifiers. The commit comparison uses page two with one commit per page to omit file diffs. Concurrent checks share one request; automatic results are cached for an hour and repeated manual checks for a minute. Failures show a readable status and never interrupt other work. The daemon cancels checks when closing.

The automatic-check preference is device local, persists under `pitchcrew-automatic-updates-v1`, and synchronizes across same-origin tabs. Development launches support manual checks but do not check automatically. `PITCHCREW_UPDATE_CHECKS=0` disables all release checks. Direct daemon construction is unconfigured by default. Desktop smoke tests inject public API fixtures to verify automatic notices, manual checks, dismissal and saved preferences in the real renderer; packaged smoke scripts disable checks. Automated verification stays offline.

Electron permits only the exact Pitchcrew build release URL in addition to its existing connector setup links. The link opens in the system browser through the existing origin-checked main-process navigation handler. The update bridge described below exposes actions and status only.

## Desktop download, installation and daemon handoff

A sandboxed preload exposes only `getState`, `check`, `download`, `install`, and state subscriptions. Main-process IPC accepts no renderer-supplied URLs, paths, versions or process IDs and checks the current window, main frame and daemon origin. The main process owns `electron-updater`, disables automatic download, installation on quit and downgrades, and serializes checks, downloads and installation. The mounted workspace shell subscribes once and drives checks using the existing hourly schedule and device preference. Browser and source launches retain the release-page flow.

Before checking native metadata, the bounded public GitHub reader validates the latest full `build-<SHA>` release. The generic updater feed is pinned to that exact release's download directory, so publishing another release while a download is pending cannot change its payload. Metadata channels are architecture-specific: `latest-x64.yml` for Windows, `latest-x64-linux.yml` for Linux, and `latest-arm64-mac.yml` / `latest-x64-mac.yml` for macOS. Electron-builder produces SHA-512 metadata and blockmaps. The updater validates downloaded bytes; only a successful download becomes installable. CI retains these assets and the macOS ZIP payloads alongside the verified installers. The Release workflow publishes the artifacts from the successful main CI run without executing repository code. Full-version release tags remain `build-<SHA>`.

After confirmation, the packaged launcher gracefully closes a daemon it owns over IPC, including on Windows, and waits for shutdown. A matching installed background service is stopped through its service manager so restart-on-failure cannot revive the old runtime during replacement. Service ownership is rechecked against its CLI path, data folder and port. A separately running daemon or a service from another checkout is never stopped or reconfigured; the UI explains that it must be closed and the desktop reopened first. Services registered to an AppImage's temporary mount cannot be handed off automatically. Existing source/service reuse stays available for ordinary launches.

`update-restart.json` in the data folder records the intended version. After replacement, the new launcher uses the ordinary daemon/service startup path, then verifies the serving daemon's version and exact commit against its own installed build before showing the UI. An old or unrelated daemon cannot silently serve the updated window. Successful verification clears the marker. Reopening the previous version after an unsuccessful OS installer also clears the marker and restores ordinary startup. Installation failures detected before the app exits restart the previous owned daemon or matching service and keep the downloaded version available for retry. Errors detected after the OS installer takes over require reopening or manually reinstalling the app; this is not a general OS-level rollback mechanism.

The updater leaves the data directory and CLI credentials in place. Active agent work is interrupted; it is not automatically resumed by an update. Normal startup recovery and the existing board/event compatibility rules apply.

Current macOS installers are unsigned. Electron's macOS updater requires signing, so those builds retain the manual DMG download flow. ZIPs and architecture-specific manifests are published for packaging compatibility, but signing/notarization setup remains separate. Packaged smoke checks stay hidden and offline; they never download a public update or invoke an OS installer. Unit tests cover confirmation, serialization, retry and recovery, and an actual launcher test covers daemon stop/restart and retained local files. Cross-version OS installer replacement is not performed by these tests.

Before installing and restarting Pitchcrew, the desktop waits for runtime CLI maintenance to finish and offers Cancel quitting. This prevents app replacement from interrupting an installer owned by the daemon; ordinary service-owned desktop closing remains independent.
