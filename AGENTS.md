# AGENTS.md

Instructions for coding agents and contributors working on Pitchcrew. If a change makes anything here false, update this file with the change.

## What Pitchcrew is

A local-first job-search app with a crew of role agents. Pitchcrew starts runtime CLIs, gives them scoped MCP tools, and keeps shared state on a board. It does not implement a provider agent loop. See [README.md](README.md) for setup and the product view.

## Status

Working MVP with a shared browser/Electron UI, Scout/Writer/Reviewer runs, persistent role and crew chats with AI Elements, persistent routines and scheduled actions managed by users and agents, capability-gated batch pipeline reviews with every-seat assessments and user-approved targeted crew changes, shared and role-assigned Markdown skills with skills.sh imports and user-reviewed chat suggestions, bounded agent-triggered follow-ups, user-approved role change proposals, watched profile maintenance proposals, source-backed Markdown packets, approval-gated local export, manual application tracking, user-only learning signals (application weights and lessons) with an Insights page, tag merge and previewed stale-submission cleanup, approval-gated local Chromium computer use, and role-scoped read-only GitHub/Google Workspace connectors. Demo is deterministic and available only with the daemon’s --dev flag; production seeds paused Claude Code roles and preserves existing Demo roles as unavailable until the user selects a real runtime. Claude Code, Codex, Gemini CLI, OpenCode, GitHub Copilot CLI, Cursor Agent, Goose, Kiro CLI, Grok Build, Pi and oh-my-pi adapters are implemented; live provider runs are not part of automated verification. Automatic discovery, outreach, and whole-desktop control are deferred. Literal-text PDF/DOCX packets, inspected form assessments and durable browser submission receipts are supported.

## Stack

- Strict TypeScript, Node 22.18+ or 24.11+ (supported LTS), pnpm 11 workspaces. Follow pnpm-lock.yaml and root engines.
- SQLite through better-sqlite3; versioned append-only events and projections.
- Fastify serves the loopback HTTP API and production UI; request hooks enforce Host, Origin and local sessions before body parsing. Encapsulated route plugins compose the orchestration services. Development uses Vite through @fastify/middie; chat SSE retains Node response backpressure and disconnect cleanup.
- Official TypeScript MCP SDK with stdio transport and per-run capabilities.
- React and shadcn/ui (Base UI primitives), Tailwind, Vite 8, shared browser/Electron renderer. Form selects share the app select wrapper and bounded menu height; date/time fields compose a shadcn Calendar (React DayPicker), Popover and Intent UI's registry TimeField (React Aria editable segments) while retaining local wall-clock values for the chosen timezone. Use shared controls instead of native selects, date/time dialogs or checkboxes. Compose with `render`, not `asChild`; `Button` defaults to `type="button"`, so submit buttons need `type="submit"`; menu labels sit inside `DropdownMenuGroup`.
- Motion for React supplies pointer-driven clay card tilt, board layout changes, proposal and approval decisions, and new chat message reveals. Base UI surfaces use shared interruptible CSS transitions; frequent navigation and the command palette stay instant. Buttons use brief CSS press feedback. The shared `AppMotion` provider loads Motion features and respects system reduced motion; pointer-driven effects also use its reduced-motion context. Base UI retains dialog semantics, exit lifecycles, and focus management. Reduced motion removes surface translation and scaling while retaining short fades.
- TanStack Router with a typed code-based route tree and browser history for both renderers. The shared workspace shell stays mounted around lazy page outlets. Board lives at `/`; other views use named paths, chat threads use `/chat/<thread>`, skill assignments use `/skills?filter=<assignment>`, Activity search/type filters use `/activity?q=<query>&kind=<event-kind>`, and Insights filters use `/insights?tag=<tag>&from=<local-date-time>&to=<local-date-time>&sort=<count|positive|weight|tag>`. Profile, role, skill, and routine editors protect unsaved changes when closing, switching notes, navigating, or leaving the page. The daemon serves the SPA entry for deep links in development and production.
- Zustand owns the renderer workspace snapshot, shared UI state and API actions in `packages/ui/src/WorkspaceStore/index.ts`. Pages use selectors; the mounted shell owns polling and chat-stream cleanup. Route state stays in TanStack Router; component-only form state stays local.
- Sidebar categories (Workspace, Crew and Recently opened) collapse independently through keyboard-accessible headings and remember their state in device-local storage. Categories start expanded; the desktop icon sidebar shows every category's shortcuts while preserving the expanded sidebar's preferences.
- App-wide settings live at `/settings`, with URL-backed General, Accounts, Runtimes and Local data tabs. Shared Base UI tabs provide linked tab panels and arrow-key navigation with automatic activation. Settings is pinned in the sidebar footer and available in the command palette. Theme and notification sounds share a device preference store and retain their existing local storage keys; the notification panel also offers a synchronized sound shortcut. Crew owns agent configuration; connected accounts and installed runtime checks live in Settings, with contextual account connection still available from Profile.
- Oxlint for linting and Oxfmt for formatting. Do not add ESLint or Prettier.
- Oxc transforms / Rolldown in Vite, tsdown / Rolldown for Electron's main process.
- Electron uses a paper-themed draggable title bar with native macOS traffic lights and Windows/Linux window-control overlays. Shared sheets and their backdrops fit below the title bar, including the mobile sidebar; macOS fullscreen uses the full viewport. Its sandboxed CommonJS preload synchronizes the renderer theme through a main-frame, origin-checked IPC channel without exposing Electron APIs to the page. Explicit Google PKCE sign-in links with a loopback callback and the exact GitHub and Google Workspace CLI installation pages open in the system browser through a narrow main-process URL allowlist; other external navigation is denied.
- Vitest for unit, HTTP workflow, adapter contract, and actual MCP stdio tests.

## Code organization

- Keep React component files at most 100 lines after formatting. `pnpm lint` checks every production TSX file.
- Put each feature in a named folder with `index.tsx` as its public entry, `components/` for sections, `hooks/` for state/effects, and `__tests__/` for colocated tests. Use `types.ts`, `helpers.ts`, `constants.ts` and `api.ts` when the feature needs them; do not create empty placeholders.
- Keep components focused on rendering. Put pure transformations in helpers, network operations in API modules, and reusable stateful behavior in hooks. Name handlers as actions; reserve `use` prefixes for hooks.
- Share repeated domain labels, formatting and status calculations under `packages/ui/src/lib/`. Keep shadcn and AI Elements families under `components/ui/` and `components/ai-elements/` with explicit public exports.
- Backend entry points preserve their public contracts and compose private modules by domain: `board/`, orchestrator `crew/` and `http/`, adapter `process/`, MCP `tools/`, connector `auth/` and computer modules. Keep transactions and approval checks together.
- Use ordinary Tailwind utilities for routine feature layout and spacing. Keep materials, complex selectors and shared motion in ordered feature files under `packages/ui/src/styles/`. Shared UI and AI Elements defaults use the `primitive:` variant: `styles.css` orders `base`, `primitives` and `components` below ordinary, unlayered caller utilities. Keep the utility import unlayered so the variant emits into the top-level `primitives` layer. Theme tokens and named responsive thresholds live in `styles/theme.css`; remaining feature CSS uses those thresholds through `@variant`. Oxfmt sorts classes, including `cn` and CVA arguments. See [docs/code-organization.md](docs/code-organization.md).

## Commands

```sh
pnpm install
pnpm dev          # daemon + hot-reloading UI at http://127.0.0.1:4417
pnpm desktop      # build Electron main process; reuse or launch development daemon
pnpm build        # UI and Electron main bundles
pnpm icon:build   # regenerate Electron's PNG from the canonical favicon SVG
pnpm start        # daemon serving built UI
pnpm desktop:prod # build and launch Electron with built UI
pnpm browser:install # install Chromium for browser tools and tests
pnpm test         # fixtures, loopback HTTP, MCP and isolated Chromium; no provider calls
pnpm test:desktop # isolated production daemon + actual Electron renderer check
pnpm lint         # Oxlint; warnings fail
pnpm format       # Oxfmt
pnpm format:check
pnpm typecheck
pnpm check        # lint, typecheck, tests, build
```

The UI has hot reload; restart the daemon after backend changes. The default data directory is ~/.pitchcrew, optionally PITCHCREW_HOME outside the repository. PITCHCREW_PORT defaults to 4417. Tests use temporary directories outside the repository and fictional fixtures under packages/*/test/fixtures/.

## Core concepts

- **Onboarding.** Fresh data directories show a two-screen introduction to the crew and approval flow, followed by a Board setup checklist for nonblank profile notes, enabled and available agents in all three workflow seats, and a real (non-demo) job card. Other pages show compact setup progress linking back to Board. Users can defer setup or explicitly finish it, and reopen the introduction from Getting started in the sidebar. Versioned onboarding preferences live in `onboarding.json` in the data directory and synchronize through snapshots across browser/Electron; they do not change board events, role capabilities or approvals. Existing databases default to deferred onboarding on upgrade.
- **Role.** A stored role with a stable safe lowercase ID, editable name/responsibilities, runtime, model, enabled flag, instructions and agent capabilities. One runtime agent belongs to each role. Users choose Create agent from Crew for a generic six-step setup: purpose, runtime, tools, skills, optional first routine and review. Creation commits the role, selected skill assignments and optional routine in one board transaction after asynchronous instruction writes; selected skill revisions and instruction limits are rechecked before commit. Shared skills apply automatically; adding assignments preserves existing assignments and provenance. The first routine defaults paused. Unsaved setup is protected on close and navigation. New custom roles default to chat and scoped tools with crew actions and connectors disabled. Startup supplies Scout, Writer, Reviewer, Submitter, Tracker, Documenter and Pipeline Coach, backfilling missing IDs within creation limits without changing existing or retired roles. The four support defaults use chat with specialized capabilities and crew messaging; account connectors stay disabled and no schedules or watches are seeded. Production defaults start paused. See docs/roles.md for presets and setup requirements. The optional workflow seat is Scout (fit), Writer (draft), Reviewer (review), or chat-only, independently of role identity; legacy built-ins retain their seats. Retirement preserves all history and prevents future runs/edits/ID reuse; it pauses responsible routines and cancels queued target tasks. Active runs or settings writes block editing and retirement. Edit a role in a full-height side panel with a scrolling form and persistent save actions, opened from Crew, chat, the sidebar or command palette. Settings produce AGENTS.md and CLAUDE.md under the data directory. Each run gets an isolated subfolder and MCP configuration. Change instructions and capabilities through Crew settings or approve an agent’s proposal in chat; generated files are refreshed on startup.
- **Skill.** A user-managed Markdown instruction with a name, description and assignment to all agents or selected roles. Manage skills on the Skills page or open it from role settings. Skills display a Made by label: the GitHub source owner for imports, the originating role for approved custom agent suggestions, or You for user-created skills. Creator and repository names are searchable. Skill creation, updates and deletion append version 6 board events; deletion uses a tombstone so replay retains history. Each chat/workflow run snapshots its assigned skills into the runtime context, prompt and isolated `skills/<skill-id>/SKILL.md` files. Edits affect future runs only, including follow-ups; active runs retain their original copy. Import public GitHub-backed skills.sh links in the editor, review the loaded Markdown and assignment, then save; imported skills can explicitly refresh their source instructions. The bounded public GitHub reader uses immutable blobs, no credentials, no CLI installer and no redirects, and copies only SKILL.md instructions. Imported skills retain source URL, path and blob SHA. Skills grant no capabilities. Agents can discuss skills in user and crew chats and persist up to three suggestions per run through `pitchcrew_propose_skill`; suggestions appear in Crew work with their reason, assignment and exact instructions. Only a user decision adds the stored proposal snapshot, atomically with its decision; approval never re-fetches the source. Bundled scripts, assets, private repositories and non-GitHub skills.sh sources are deferred.
- **Notifications.** Saved agent messages and pending packet/browser/role/skill approvals feed the notification bell, unread history and shadcn/Base UI Toast alerts. Transient action confirmations and failures use the same paper-themed toaster and three-toast stack, with success/error/info types; they do not enter saved notification history or play crew notification sounds. Up to three toasts stack in a portaled viewport; Base UI manages hover/focus timer pauses, keyboard access, announcements and swipe dismissal. Alert actions are typed router links. Message toasts show a headline and action only; attention toasts add a normalized preview of at most 96 characters and two visible lines. Full messages remain in chat. Notification context comes from saved entities: messages, user-input questions, packet/browser approvals and role/skill proposals each have their own icon and action label; questions use ochre, approvals teal, proposals plum and messages blue accents, using theme tokens in light and dark modes. Message and attention requests have distinct sounds; sounds can be disabled in the notification panel. History never plays alerts on initial load, and repeated snapshots/stream updates do not repeat alerts. Scoped `pitchcrew_notify_user` saves an exact user-facing message with `message` or `attention` priority (three per run), without granting approval, queuing work or pausing a run. Agents finish their turn when asking for input and continue on the user’s reply. Notification clicks open chat or Inbox, never decide requests. Notifications and sounds stay inside the browser/Electron renderer; no native OS alerts or notification IPC bridge are used.
- **Chat and crew tasks.** User messages launch isolated chat turns. User and crew chat replies stream through a session-protected HTTP channel, using native CLI text updates when available (some CLIs emit only complete messages). Live previews are transient; only validated final replies are persisted and passed to agents. Reconnecting restores active previews and saved messages; cancellation or failure clears unfinished text. Agents can message roles, invoke themselves or others, and update the attached job through scoped board tools. Follow-ups wait for their parent to finish, obey enabled roles/capabilities and the card state machine, and are capped at six per user-started chain. Cancelling a run stops its chain. Interrupted queued work is marked failed on restart.
- **Routines.** Persistent one-time and repeating scheduled chat actions, managed on `/routines` or through scoped list/save/delete MCP tools from user or crew chats. An optional attached card scopes agent access. Start timestamps and IANA timezones support one-time actions, minute intervals and five-field deterministic cron calendar patterns; total run limits and end dates bound repeats. The daemon dispatches while listening, postpones busy/paused/unavailable roles and coalesces overdue repeats into one occurrence. It consumes occurrences before launch to prevent replay after crashes, and never retries failed/interrupted attempts automatically. Each occurrence starts an isolated chat turn using current role settings and skills, with the existing bounded follow-ups and outward-action approval gates. `manageRoutines` controls agent mutations; cross-role management also requires `invokeAgents`. The last agent editor's current capabilities are rechecked at dispatch; a user edit takes responsibility. Pausing/deleting stops future runs without cancelling active work. Deletion uses a tombstone. See [docs/routines.md](docs/routines.md).
- **Starter skills.** On startup, the daemon loads missing starter skills from the latest public GitHub HEAD into the board before serving the workspace. The ten-entry schema-free `@pitchcrew/core/base-skills` catalog stores source paths and default role assignments, never supplied version hashes. Renamed catalog repositories use explicit canonical aliases (article-writing now uses affaan-m/ECC). Writing skills default to Writer, research/questioning to Scout, and humanizer/PDF review to Reviewer. Existing matching skills and deleted tombstones prevent automatic reinstallation; edits and renames preserve source identity. Missing or offline sources are reported on the Skills page and can be retried without restoring deletions. All loads resolve HEAD afresh and only immutable blobs are cached; proposals still approve their exact reviewed snapshot. Individual skills allow up to 50,000 characters; assigned skills still total at most 60,000 characters per role. view-pdf requires separate viewer tooling. Set PITCHCREW_SEED_SKILLS=0 to skip automatic seeding, as isolated automated tests do.
- **Connector.** GitHub CLI login (gh) with manual fine-grained tokens under Advanced, and Google Desktop OAuth or an optional saved Google Workspace CLI login provide read-only repository, Gmail, Drive/Docs, Sheets and Calendar access through the scoped MCP gateway. GitHub CLI connections store only an account binding: tokens stay with gh. User-requested connection checks gh availability and account identity; fixed GET calls run without a shell, are bounded and cancellable, and recheck the active account before reads. Disconnect does not log out gh. Status never invokes gh. GitHub CLI access follows its native login and has no per-repository installation picker; no Pitchcrew GitHub App is required. Accounts connect in Settings or Profile; each service is disabled per role until the user enables it. Google defaults to a Pitchcrew-owned Desktop OAuth app supplied through daemon environment configuration; Connect Google prepares sign-in directly, with custom client credentials kept in Advanced setup even when the shared app is configured. Missing shared configuration is explained without requiring ordinary users to create a Google Cloud project. Public release still requires the shared app's applicable Google verification. Credentials live outside the repo in connectors/credentials.json, never in board events, snapshots, prompts or MCP configuration. Google OAuth client environment variables are filtered from role CLI environments. CLI connections retain only account bindings and Google scope names, recheck account identity before reads, and never extract tokens; Google CLI reads also recheck granted services. Status snapshots never invoke CLIs. Disconnect aborts requests and removes local credentials or bindings; provider revocation and CLI logout are separate. External content is untrusted data; packet evidence still requires verified local profile quotations. See [docs/connectors.md](docs/connectors.md).
- **Runtime adapter.** Implements detect(), run(context) and chat(context), supplies fallback model suggestions and optional listModels(signal) discovery for the searchable Crew settings picker, parses CLI output into validated RunResult or ChatResult values and emits progress messages. Native catalogs load on demand, are cached in memory for five minutes and can be refreshed explicitly; the UI labels runtime results and fallback suggestions. Demo has no models. Discovery uses only bounded native model-list operations, never starts a conversation or inference turn, never reads provider credentials directly and remains separate from health detection. Provider-specific commands and model catalogs belong only in adapters. See [docs/model-discovery.md](docs/model-discovery.md).
- **Computer use.** Opt-in per role; shared MCP tools open a visible isolated Chromium browser per run. Inspect returns page text and a screenshot. Every navigation, click, fill, selection, keypress and exported-packet upload requires an exact-action single-use user approval from Inbox, checked and consumed in the MCP gate against the current page and run. Computer-enabled CLI/ACP runs have a 30-minute limit; other runs keep three minutes. Agents wait using bounded execute calls; pending approvals expire and browsers close when the run ends or the daemon restarts. The page fingerprint includes inspected iframe DOM and values; unique frame selectors allow first-level iframe interactions. Browser alert/confirm decisions need their own exact approval; prompts and authentication/CAPTCHA handling stay manual. Optional `assessForms` persists all inspected controls with assessed/unassessed flags and agent annotations on the attached card for Writer handoff. Optional `recordSubmissions` records purpose-marked click/Enter attempts before execution; uncertain attempts allow only separately approved dialog continuation bound to that attempt and otherwise block further interactions until a user verifies captured confirmation or supplies explicitly user-reported external confirmation, or verifies no submission occurred. Existing tracked statuses are preserved when resolving later. No arbitrary JS, filesystem upload or desktop control. Public network checks block local/private URLs; website scripts remain untrusted and this is not an OS network sandbox. See [docs/computer-use.md](docs/computer-use.md).
- **Board.** One card per application. Allowed transitions live in core. Agents coordinate through persistent board state; launches start with user actions or stored routines and can continue through bounded board-backed agent tasks. Users can register known external submissions with a timestamp and confirmation note without generating or exporting a packet; registration performs no outward action and prevents likely duplicate company/title/URL or job-ID records. Existing pre-submission cards support a narrow user-only external fact registration that rejects active work, retains prior packets without identifying them as submitted, invalidates unused approvals and preserves history. Ordinary moves and email reconciliation into submitted still require successful current-packet export. Card details expose user-managed job identifiers, Gmail thread links, tracking evidence and learning signals.
- **Application tracking.** Optional `readApplications` and `trackApplications` capabilities default to false for custom agents; Tracker has both configured and Submitter has read access. Cross-application search is bounded; reconciliation additionally requires Gmail. Server-owned scan checkpoints retain pending pages on failure and resume across restart, and completed sweeps can discover new messages. Verified mailbox/message IDs deduplicate across roles and queries. Automatic updates require a unique stable job URL/identifier or user-linked Gmail thread, conservative agreement between the exact quotation and full fetched text, a newer effective time and an allowed state transition. Truncated/quoted/conflicting sources and uncertain matches are persisted for user review on Board with full fetched context. User status corrections set a separate effective-time boundary; unrelated packet edits do not change it. Decisions and evidence/scan consumption use board transactions, never raw agent database writes. Existing routines provide periodic scans only while the daemon is open. Tracker is seeded as a default role, paused in production with Gmail disabled; no schedule is seeded. See [docs/tracking.md](docs/tracking.md).
- **Learning signals.** Each card has a user-only weight (-2 strong miss to +2 strong win, default 0, independent of outcome) and up to 20 timestamped lessons of at most 1,000 characters, edited in card details. Outcomes are derived in `@pitchcrew/core/insights`: interviewing/offer positive, rejected/ghosted negative, withdrawn neutral, everything else pending. The pure `applicationInsights` function there produces outcome counts, a case-insensitive tag scoreboard (count, positive share of decided cards, average weight, up to five companies, sortable), weight distribution and recent lessons by outcome, filtered by tag and applied date; example cards are excluded. The Insights page (`/insights`) computes it from the snapshot. Users can merge tags (old tag dropped, so cards stay within 10) and preview submitted cards with no effective status change for N days (default 21, 1-365), then mark up to 200 selected ones per batch ghosted with a history note. The ghosted effective time is the end of the silence period, so later replies can still advance the card; the batch rechecks state, `updatedAt`, active workflow ownership and staleness in one transaction, and never runs automatically. All of these are session-protected HTTP routes with no agent gateway action. The read-only `pitchcrew_application_insights` MCP tool requires `readApplications` or `reviewPipeline` (both already grant cross-application reads), is rechecked per call against the active run, caps lists at 50 tags and 10 lessons per outcome with 500-character lessons, and shortens lists to stay within 64 KB. Default Scout and Writer instructions use it only when granted one of those capabilities; Pipeline Coach starts reviews with it. Default capabilities are unchanged. See [docs/insights.md](docs/insights.md).
- **Pipeline review.** Optional `reviewPipeline` grants bounded cross-application board review, role/skill configuration access and saved batch reviews. Optional `proposeCrewChanges` additionally permits targeted instruction/capability proposals linked to the originating role's own saved finding. Both default off for custom agents and are configured for the default Pipeline Coach. Reviews explicitly assess every current seat or record insufficient evidence, distinguish observations from hypotheses, preserve bounded event evidence, and track concrete next-run improvements and measurable follow-up results. Saved attention notices precede reviews and targeted proposals; notices never authorize adoption. Only an explicit user decision applies the exact proposal, with target-revision, target-idle and current originating-permission checks. Run launches persist exact role/skill snapshots and input/output packet digests; existing historical configurations remain unknown. Pipeline Coach is seeded as a default role, paused in production; no routine is installed automatically. See [docs/pipeline-reviews.md](docs/pipeline-reviews.md).
- **Event log.** Version 10 adds optional user-only card `weight` and `lessons` fields; tag merges and stale-submission marks are ordinary user card events. All newly appended events use version 10; versions 1 through 9 remain decodable and replayable, and cards without the new fields read as weight 0 with no lessons. Version 9 adds configurable role identities, explicit workflow seats, retirement, profile-maintenance proposals, tracking signals/checkpoints, form assessments, submission attempts, frozen artifact manifests, pipeline reviews, run configuration snapshots and opt-in profile/application/submission/review capabilities. Versions 1 through 8 remain decodable and replayable. Version 8 adds routine events, scheduled-run metadata and the optional routine-management capability; versions 1–7 remain decodable and replayable. Version 7 adds optional message notification priority; versions 1–6 remain decodable and replayable. Version 6 adds computer-use capability and browser action approvals; versions 1–5 remain decodable and replayable. Version 5 added skill provenance and skill proposals. Version 4 added managed skills and version 3 added optional connector capabilities. Every card, role, skill, skill proposal, run, approval, computer approval, message, role proposal, task and routine update appends a versioned event and changes its projection atomically. Rebuild replays events in order.
- **Profile.** User Markdown files under the data directory's profile folder. Profile sources import nested GitHub folders (one pinned commit) or Google Drive folders (Docs, Markdown and plain text) through the existing read-only account connectors. Users review and select exact server-staged snapshots; import never re-fetches, and previews expire after ten minutes or restart. Per-source bounds are 100 documents, 30 folders, 50,000 characters per document and 1 million characters total. Imported source paths, links, revisions and content hashes live in profile-sources.json outside the repo. Maintenance proposals also persist exact reviewed documents, evidence and provenance in the board event log. Notes retain stable local filenames, with original paths and searchable labels in the UI. Manual refresh flags locally edited notes and preserves removed upstream files; removing a source keeps its notes and account connection. Source imports grant no agent connector capabilities. Users may enable/pause watches or remove source connections during active runs; dedicated maintenance tools recheck the current watch and account after asynchronous reads. Profile note writes are serialized and blocked during active runs; workflows recheck the profile revision after asynchronous setup. Registered packet claims must be exact supported quotations. Mechanical lint is not a complete semantic fact checker.
- **Profile maintenance.** Users opt individual imported GitHub/Drive folders into watching or add a GitHub project watch without importing any files. Agents need maintainProfile plus the matching connector capability and a connected account; source imports grant neither. Scoped tools detect exact Markdown changes and removed upstream documents, or record repository commit observations even when Markdown is unchanged. Project evidence reads stay inside the watched folder and pin the observed commit; agent-written notes retain exact evidence and require explicit user verification of personal facts. Pending proposals expose before/after contents and evidence on Profile. Approval binds the exact snapshot digest and selected files, never re-fetches, and applies only while all runs are idle. Local conflicts require selection; removed upstream documents are kept. An interrupted approved update retains its exact selection for retry after restart; agent launches, scheduled occurrences and other profile-note writes wait until it finishes. Existing routines schedule scans while the daemon is open. See [docs/profile-maintenance.md](docs/profile-maintenance.md).
- **Packet.** Versioned resume.md, cover_letter.md, form_answers.md, note.md and claims.json. The job post is stored on its card. Users select Markdown, PDF and/or DOCX before requesting export approval. PDF/DOCX render literal Markdown text without fetching links, executing markup or silently dropping glyphs. PDF explicitly rejects unsupported characters; DOCX preserves Unicode. Frozen artifact bytes and SHA-256 manifest are reviewed, exported and uploaded through the existing gates. The lazy PDF.js preview renders every page from those bytes using only bundled worker/font resources, with cancellation and visible errors; no native PDF plugin or remote asset loading is needed. The lazy DOCX preview renders those exact bytes with docx-preview in a sandboxed iframe, with scripts, navigation links and remote resources disabled. Embedded images use data URLs; embedded fonts and HTML chunks are disabled. Closing or replacing a document discards unfinished renders; loading and errors are visible. Browser layout can differ from Word and the complete literal source text remains available.
- **Approval.** Exact packet snapshot and SHA-256 digest bound to a card and export action. It is single-use; export calls enter the shared MCP gate. Agents have no approval tool. Successfully exported current packets allow users to record manual submissions.

## Invariants

These must stay true. A change that breaks one is a bug even if tests pass.

1. **No outward action without approval.** Anything that sends, submits, posts or emails must go through a gated MCP tool checking an unused approval bound to the exact payload. The check belongs in MCP, not in prompts or UI. Browser interactions use an exact-action approval bound to run, role, card, page fingerprint and upload contents; website-controlled scripts remain outside payload verification. Local export also uses its gate.
2. **Provider code stays in packages/adapters/.** The orchestrator, board and UI see only the runtime interface and normalized results/progress.
3. **Agents coordinate through the board only.** Internal messages and invocations are persisted board entities with scoped MCP tools; no adapter-to-adapter messaging and no shared runtime sessions across roles.
4. **Events are append-only and stay decodable.** Never rewrite or delete stored events. Schema changes add a new version and retain a decoder for every old version.
5. **Health checks have no side effects.** detect() never signs in, creates a session or spends tokens.
6. **Credentials stay with the runtime.** Pitchcrew never reads, copies or stores provider tokens. Adapters rely on the CLI's native authentication, including its environment configuration.
7. **The daemon binds to 127.0.0.1 only.** Keep origin/Host checks and user-session/run-capability boundaries intact.
8. **User data never enters the repo.** Profile notes, packets and DB live outside it. Tests use fictional fixtures and checked temporary cleanup paths.
9. **Rules change only with user approval.** Agents propose their own instruction/capability changes, or capability-gated targeted crew changes tied to saved reviews, in chat and never apply them directly. Only user settings or an explicit user decision on a proposal updates roles; skills are added or changed only through startup defaults, user settings or user-approved skill proposals; rules.yaml is deferred.

## Card states

The authoritative transition graph is packages/core/src/states.ts, kept free of zod so the UI can import it from @pitchcrew/core/states (Oxlint allows only type imports of @pitchcrew/core in the UI). Typical flow:

```text
lead -> shortlisted -> drafting -> in_review -> agreed -> awaiting_approval
                            ^          |                        |
                            +-- changes_requested <-------------+
                                                                |
                                                            submitted
                                                                |
                                              screening -> interviewing -> offer
                                                  |             |
                                             rejected / withdrawn / ghosted
```

Scout evaluates an existing lead; the user shortlists it. Writer drafts, Reviewer agrees or requests changes. Approval exports files locally; the user submits independently or approves browser interactions, then verifies confirmation and records the outcome. Keep active-run ownership, revised-packet approvals, cancellation and interrupted-run recovery covered when modifying this flow.

An uncertain submission can continue through a separately approved browser dialog only when `submissionAttemptId` binds the same run, card, current exported packet and observed dialog. The consumed continuation approval is saved on the attempt. No click, keypress or navigation retry is allowed.
