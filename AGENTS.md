# AGENTS.md

Instructions for coding agents and contributors working on Pitchcrew. If a change makes anything here false, update this file with the change.

## What Pitchcrew is

A local-first job-search app with a crew of role agents. Pitchcrew starts runtime CLIs, gives them scoped MCP tools, and keeps shared state on a board. It does not implement a provider agent loop. See [README.md](README.md) for setup and the product view.

## Status

Working MVP with a shared browser/Electron UI, Scout/Writer/Reviewer runs, persistent named conversations, groups, live turn commentary and grouped tool activity, visible read-only agent DMs, local agent memory and user file attachments with AI Elements, persistent routines and scheduled actions managed by users and agents, an optional per-user background service that starts the production daemon at login, capability-gated batch pipeline reviews with every-seat assessments and user-approved targeted crew changes, shared and role-assigned Markdown skills with skills.sh imports and user-reviewed chat suggestions, bundled career skills and chat-based Career Coach, bounded agent-triggered follow-ups, user-approved role change proposals, watched profile maintenance proposals, optional seven-perspective deep resume reviews with automatic Writer corrections, scoped temporary CLI subagents, parent-controlled deadline extensions and saved before/after reports, source-backed Markdown packets with user-configurable packet rules and worker-bounded pattern checks, approval-gated local export, manual application tracking with user-reviewed bulk import of past applications from JSON/CSV exports or supported legacy SQLite trackers, user-only learning signals with Insights, tag merge and previewed stale-submission cleanup, chat-embedded local Chromium browsers with per-agent profiles, private manual takeover and supervised or bounded autonomous preparation, role-scoped read-only GitHub/Google Workspace connectors, capability-gated job discovery from user-saved public Greenhouse, Ashby, Lever, Comeet and Workable boards, capability-gated single posting link imports by agents, and user-only Add job prefill from a single Greenhouse, Ashby, Lever, Comeet or Workable posting link. Demo is deterministic and available only with the daemon’s --dev flag; production seeds paused roles with role-specific recommended runtime/model/reasoning selected from the installed runtime checks and bounded model catalogs and preserves existing Demo roles as unavailable until the user selects a real runtime. Claude Code, Codex, Gemini CLI, OpenCode, GitHub Copilot CLI, Cursor Agent, Goose, Kiro CLI, Grok Build, Pi, oh-my-pi and Hermes Agent adapters are implemented; live provider runs are not part of automated verification. Discovery from other job sites, outreach, and whole-desktop control are deferred. Formatted and plain text PDF/DOCX packets, inspected form assessments and durable browser submission receipts are supported.

## Branch and release workflow

- `dev` is the integration branch for all development. Create every feature, fix, refactor, documentation and maintenance branch from the latest `dev`, and target `dev` when opening its pull request.
- `main` is the production release branch. Release through a pull request with `dev` as the head and `main` as the base; individual work branches must not target `main`.
- Every release pull request must include a version bump above the current `main` version. Prepare the bump on `dev` (directly or through a preparation branch merged into `dev`) before opening the release pull request. The root `package.json` supplies the installer version; keep workspace package versions in sync with it.
- Use semantic versioning (`MAJOR.MINOR.PATCH`): patch for fixes, minor for backward-compatible features, and major for breaking changes. Select and explain the bump in each `dev` → `main` release pull request based on the changes since the previous release.
- Include the chosen version, a summary of changes and validation in the release pull request. Required CI must pass before merging. Merging into `main` triggers the existing verified-installer publication workflow with `build-<full commit SHA>` tags.
- After a release, merge `main` back into `dev` so subsequent work includes the release merge and version history. Preserve the shared branches and their history.

## Stack

- Node utilities and CLI fixtures use strict TypeScript and are included in the root typecheck. Package scripts use the existing `tsx` loader; Electron compiles its main/preload and icon utility to JavaScript. The early UI theme initializer is TypeScript compiled by Vite to a blocking `/theme.js` asset in development and production. NSIS/PowerShell installer sources and the Next.js PostCSS configuration retain their required formats.
- Strict TypeScript, Node 22.18+ or 24.11+ (supported LTS), pnpm 11 workspaces. Follow pnpm-lock.yaml and root engines.
- SQLite through better-sqlite3; versioned append-only events and projections.
- Document rendering engines and Playwright load on first document/browser use rather than daemon import. Snapshots containing frozen PDF artifacts still load the PDF reader to count their pages.
- Fastify serves the loopback HTTP API and production UI; request hooks enforce Host, Origin and local sessions before body parsing. Encapsulated route plugins compose the orchestration services. Development uses Vite through @fastify/middie; chat SSE retains Node response backpressure and disconnect cleanup.
- Official TypeScript MCP SDK with stdio transport and per-run capabilities.
- Codex launches, including resumed chats, require the scoped Pitchcrew MCP server at startup and approve its native tool calls through server-specific configuration. Pitchcrew's gateway retains capability and exact-action approval enforcement; read-only sandboxing and disabled native shell tools remain. See [docs/runtimes.md](docs/runtimes.md).
- React and shadcn/ui (Base UI primitives), Tailwind, Vite 8, shared browser/Electron renderer. Shared buttons, inputs, textareas, checkboxes and switches carry the app's clay, glazed and recessed materials without requiring a form wrapper. Switches use recessed tracks, glazed checked tracks and raised thumbs; keyboard focus remains visible above material shadows. Multiline fields respect their row count, while the chat composer grows with its content. Form selects share the app select wrapper and bounded menu height; date/time fields compose a shadcn Calendar (React DayPicker), Popover and Intent UI's registry TimeField (React Aria editable segments) while retaining local wall-clock values for the chosen timezone. Use shared controls instead of native selects, date/time dialogs or checkboxes. Compose with `render`, not `asChild`; `Button` defaults to `type="button"`, so submit buttons need `type="submit"`; menu labels sit inside `DropdownMenuGroup`.
- Motion for React supplies pointer-driven clay card tilt, board layout changes, proposal and approval decisions, new chat message reveals and question cards that spring from behind the message composer. Question cards return behind that input on resolution and become inert during exit; existing conversations and snapshot refreshes do not replay their entrance. Base UI surfaces use shared interruptible CSS transitions; frequent navigation and the command palette stay instant. Buttons use brief CSS press feedback. The shared `AppMotion` provider loads Motion features and respects system reduced motion; pointer-driven effects also use its reduced-motion context. Base UI retains dialog semantics, exit lifecycles, and focus management. Reduced motion removes surface translation and scaling while retaining short fades.
- Board job dragging uses `@dnd-kit/react` and `@dnd-kit/dom` with a floating preview, whole-card mouse dragging, per-status targets and screen-reader announcements. A three-dot card menu provides touch and keyboard access to individual statuses through Move to…, contextual status and crew shortcuts, job details, posting-link copying and confirmed deletion. The menu button and card body share one Motion surface so hover lift and tilt stay aligned; the menu button never starts dragging. Status and deletion actions are disabled during owned workflow work or attached chat runs, with Cancel run available. Menu status changes keep the current Pipeline or Closed view, while drags follow the destination; both reveal the destination page and restore focus to a visible menu button, the board view control or the empty board’s Add job action. Deletion uses the existing history-preserving transaction, invalidates approvals, cancels queued follow-ups and pauses attached routines, with no user-facing restore. See [docs/board-card-actions.md](docs/board-card-actions.md). Users can drag an idle job from any status to any other status, including within a grouped column and reopening closed jobs. Drops record user-only status changes without launching agents, generating packets, exporting or submitting; the daemon rejects owned cards and active workflow or attached chat runs. Status changes atomically invalidate unused packet export approvals and update the user status timestamp. Crew workflow transitions and approval/export/browser submission gates remain enforced independently. Moves preview immediately and return on failure; the board follows successful drag moves between Pipeline and Closed views. Keep drag transforms separate from Motion's card tilt and layout animations.
- Board lists search all jobs before paging: up to 20 per pipeline column and 40 closed jobs remain mounted, with accessible Previous/Next controls and full counts. Moves within the current view reveal their destination page before keyboard focus returns. The command palette uses cmdk fuzzy matching across every job before rendering 25 results, with keyboard-selectable result pages; no job is removed from search.
- TanStack Router with a typed code-based route tree and browser history for both renderers. The shared workspace shell stays mounted around lazy page outlets. Route wrappers import their view directly; avoid a second React.lazy boundary inside an already lazy route. Board lives at `/`; other views use named paths, chat threads use `/chat/<thread>`, skill assignments use `/skills?filter=<assignment>`, Activity search/type filters use `/activity?q=<query>&kind=<event-kind>`, and Insights filters use `/insights?tag=<tag>&from=<local-date-time>&to=<local-date-time>&sort=<count|positive|weight|tag>`. Profile, role, skill, and routine editors protect unsaved changes when closing, switching notes, navigating, or leaving the page. The daemon serves the SPA entry for deep links in development and production.

Pages use selectors; the mounted shell owns polling and chat-stream cleanup. The UI requests compact workspace snapshots and streams: conversation previews/counts and eligible notifications replace bulk message history, complete job source loads when opening details, and 50-entry indexed history pages preserve all messages and saved activity. Sidebar message search runs against the full persisted history. The unqualified snapshot/stream APIs retain full-history compatibility. Action reloads remain unconditional and chat disconnection clears the validator for an authoritative fallback. See [docs/workspace-synchronization.md](docs/workspace-synchronization.md). Route state stays in TanStack Router; component-only form state stays local.

Chat and Profile retain their dedicated workspaces with matching bounds and materials. Other pages use `WorkspacePage`; feature actions reach its persistent header through `WorkspaceHeaderActions`. Feature-specific work-area layouts override the low-specificity shared body defaults. Keep editor headings, body spacing and persistent actions consistent between embedded panels and sheets.

Categories start expanded; the desktop icon sidebar shows category shortcuts while preserving the expanded sidebar's preferences. Conversations live in this shared app sidebar, with search, new conversation, pin/unread/activity indicators, archived conversations and collapsible agent DMs. Its icon view offers Open conversations and New conversation. Shared Base UI tabs provide linked tab panels and arrow-key navigation with automatic activation. Settings, Getting started and an app update control share a compact icon row in the sidebar footer, with tooltips and a vertical stack in the collapsed desktop sidebar. Settings is also available in the command palette. Audio unlock runs only while sounds are enabled, and the audio context suspends after the final overlapping alert. ## Code organization

- Keep React component files at most 100 lines after formatting. `pnpm lint` checks every production TSX file.
- Put each feature in a named folder with `index.tsx` as its public entry, `components/` for sections, `hooks/` for state/effects, and `__tests__/` for colocated tests. Use `types.ts`, `helpers.ts`, `constants.ts` and `api.ts` when the feature needs them; do not create empty placeholders.
- Keep components focused on rendering. Put pure transformations in helpers, network operations in API modules, and reusable stateful behavior in hooks. Name handlers as actions; reserve `use` prefixes for hooks.
- Share repeated domain labels, formatting and status calculations under `packages/ui/src/lib/`. Keep shadcn and AI Elements families under `components/ui/` and `components/ai-elements/` with explicit public exports.
- Backend entry points preserve their public contracts and compose private modules by domain: `board/`, orchestrator `crew/` and `http/`, adapter `process/`, MCP `tools/`, connector `auth/` and computer modules. Keep transactions and approval checks together.
- Use ordinary Tailwind utilities for routine feature layout and spacing. Keep materials, complex selectors and shared motion in ordered feature files under `packages/ui/src/styles/`. Shared UI and AI Elements defaults use the `primitive:` variant: `styles.css` orders `base`, `primitives` and `components` below ordinary, unlayered caller utilities. Keep the utility import unlayered so the variant emits into the top-level `primitives` layer. Theme tokens and named responsive thresholds live in `styles/theme.css`; remaining feature CSS uses those thresholds through `@variant`. Oxfmt sorts classes, including `cn` and CVA arguments. See [docs/code-organization.md](docs/code-organization.md).


The UI has hot reload; restart the daemon after backend changes. The default data directory is ~/.pitchcrew, optionally PITCHCREW_HOME outside the repository. PITCHCREW_PORT defaults to 4417. Tests use temporary directories outside the repository and fictional fixtures under packages/*/test/fixtures/.

Local desktop and packaged smoke checks must stay hidden and never take focus. They use a hidden, non-focusable Electron window, background macOS activation and `capturePage` with `stayHidden`; evidence asserts the window was never shown or focused. Use `PITCHCREW_SMOKE_VISIBLE=1` only when the user explicitly requests a visible debugging run. Startup failures in hidden smoke mode go to stderr and exit with failure instead of opening a native dialog. Ordinary `pnpm test` Chromium checks remain headless. Desktop smoke checks record native quit phases separately from parent-observed process exit and fail after a 10-second shutdown deadline; forced cleanup applies only to failed test children and never counts as success. See [docs/desktop-shutdown-performance.md](docs/desktop-shutdown-performance.md) for the isolated native exit diagnosis.

GitHub Actions CI runs on every pull request, pushes to main, merge queues and manual dispatches. It checks lint, formatting, types and production builds on Ubuntu, runs the full test suite with Chromium on Node 22 and 24, runs the actual Electron smoke test on macOS and Windows, and builds and checks standalone installers on Windows x64, macOS Apple Silicon/Intel and Linux x64. It uses the packageManager pin, frozen lockfile and read-only repository permissions without provider credentials. Installer artifact uploads retry once after 30 seconds when the upload action fails, replacing any incomplete artifact with the same name; a failed retry still fails the job. The aggregate CI check must pass all jobs. The GitHub main branch ruleset requires that check from GitHub Actions and an up-to-date branch, with no bypass actors. Main push runs have distinct concurrency groups so every push can produce a release; other superseded runs are cancelled. Test reports, desktop evidence, installers, macOS ZIP update payloads, architecture-specific updater manifests and blockmaps are retained for seven days. The separate Release workflow publishes those exact verified installer/update artifacts and SHA-256 checksums after successful main push CI under build-<full commit SHA> tags; only it has contents write permission and it never executes repository code. Reruns resume drafts or skip published releases. Windows and macOS installers are unsigned, and macOS builds are not notarized.

Standalone desktop packaging uses electron-builder with an isolated app directory and an unpacked runtime resource tree containing the source-layout daemon, production-only hoisted dependencies with workspace links materialized as directories, the build machine's Node 24 executable and Chromium. Native SQLite targets that Node runtime, so Electron native rebuilding is disabled. The packaged main process forks the bundled launcher, which retains daemon/service reuse and ownership rules; closing the app stops only its own daemon, and launcher IPC disconnect handles Electron crashes. Windows NSIS setup and uninstall use the scoped process check in `packages/desktop/installer/`: only the app executable and bundled Node/Chromium helpers under the selected or previous installation directories are closed, with a graceful window-close interval before forced cleanup. Existing installation directories expand Windows 8.3 aliases before comparison with executable paths. Downloads, the running installer/uninstaller and sibling paths are excluded; PowerShell profiles never load. Windows installer CI also runs the compiled NSIS macro against isolated fixtures, including short paths, without changing installed apps, registry keys or shortcuts. User data remains outside installation resources in the existing data directory. Source desktop launches keep their existing launcher. Build installers on each target platform/architecture with Node 24; provider CLIs/authentication remain separate.

## Core concepts

- **Public landing page.** `packages/landing` is a standalone Next.js App Router website with Tailwind, Base UI/shadcn controls, Motion and locally served Fraunces/Source Sans 3. It uses committed light/dark app screenshots with fictional demo data and does not access the local daemon. Its Light/Dark/System menu uses a separate website preference, synchronizes across tabs and applies before paint. The download chooser reads validated public GitHub release assets with hourly caching and an explicit Releases fallback, with separate platform/architecture choices. Production anonymous visits, native page/session/pageleave events, numeric Web Vitals, public-page heatmap/frustration coordinates and download clicks use the public PostHog project, a closed property allowlist and Do Not Track; they are on by default with a quiet footer opt-out synchronized across tabs, and masked replay stays off; development stays offline by default. Optional `NEXT_PUBLIC_POSTHOG_TOKEN`/`NEXT_PUBLIC_POSTHOG_HOST` override ingestion and an empty token disables it. `NEXT_PUBLIC_SITE_URL` supplies the canonical HTTPS origin, Open Graph URLs, website/application JSON-LD and image sitemap. Only configured production builds are indexable; development and Vercel previews emit noindex. Root lint/types and CI cover the site; Vercel publishing is separate from the desktop build/release workflow. See [docs/landing-page.md](docs/landing-page.md).

- **Agent and skill updates.** Crew and Skills sidebar badges count pending default-instruction and imported-skill update decisions, remain visible in collapsed/mobile navigation and clear only after applying or dismissing that version. Quiet notification entries open exact reviews; reading them never clears badges. Both pages keep dismissed versions in Updates and have URL-backed Updates only filters. The mounted shell requests daily imported-skill checks while open; the daemon deduplicates clients and enforces a shared 24-hour interval per source. Settings > General has a synchronized automatic-check switch, and Skills/Settings offer Check now with a result toast. Local edits alone never count as an upstream update. Existing exact-preview approval replaces local skill text only after explicit review and keeps assignments; Keep mine dismisses only that version. Offline failures retain known notices and success times. Metadata/preferences live in skill-updates.json outside board events and participate in snapshot revision checks without loading skill projections; checks use the bounded public GitHub reader, share repository HEAD within each sweep and abort on shutdown. No agent gateway action or automatic adoption. See [docs/agent-updates.md](docs/agent-updates.md).

- **Career support.** Career Coach is an ordinary paused-by-default production chat role with seven bundled offline skills and chat starters for interview preparation, coached practice or mock interviews, debriefs, career planning, offer evaluation, company research and LinkedIn profile drafting. Scout also receives the company research skill. The local scoped `pitchcrew_check_linkedin_draft` tool measures exact supplied field lengths and skill counts in active chat; it reports sources and provisional text limits, preserves Unicode counting caveats and never publishes or verifies claims. LinkedIn drafts use Profile evidence plus user-supplied current text, remain in chat and are published by the user; supplied LinkedIn text never becomes verified Profile evidence automatically. It uses optional job context, Profile, attachments, source-linked own memory, read-only application search/Insights and supervised public browser research. Coaching summaries save automatically through existing memory tools; they never become verified Profile evidence. Offer support explains supplied compensation/contract terms and prepares employer/lawyer questions, with negotiation drafts only on explicit request for the user to send. Results stay in chat. Scout, Writer and Reviewer receive focused bundled assessment, tailoring and coverage-review skills preserving the 0–100 fit score, isolated drafting, exact claims, packet rules and independent review. Startup preserves edited/reassigned/deleted skills and existing roles. No extra workflow engine, report exporter, connectors, schedules or submission permissions are introduced. See [docs/career-support.md](docs/career-support.md) and [docs/hunter-skills.md](docs/hunter-skills.md).

- **Runtime execution budget.** Ordinary production CLI and ACP workflow/chat turns have the same fixed 30-minute wall-clock limit, including routines and crew follow-ups, independent of role, model, reasoning and computer-use permission. Managed deep resume reviews instead share an initial 30-minute budget across drafting, review, corrections, recheck and optional subagents; only the parent Reviewer can extend it in justified 1–30-minute increments. Questions pause that budget until continuation, and Stop cancels the parent and all child work. Both launch paths retain user cancellation and terminate the child process at the deadline. Timeout errors identify Pitchcrew as the source of the stop. See [docs/roles.md](docs/roles.md).

- **Deep resume review.** The job’s Deep review resume action and chat requests (including /hiring-panel) start the same managed flow after shortlisting and job-context confirmation. Writer creates an initial draft if needed, one Reviewer applies all seven original perspectives, Writer corrects supported findings, and Reviewer rechecks the complete packet. The bundled hiring-panel skill is assigned to Reviewer; importing a skill grants no tools. Optional targeted subagents inherit Reviewer’s runtime/model or use explicitly user-configured alternatives. Users can explicitly request additional perspectives in the start dialog or chat. The usual two-child allowance is a default rather than a total cap; audited Codex, Claude Code, OpenCode and development Demo adapters support up to four concurrent isolated child CLI runs per runtime per review. Children cannot delegate, approve or extend time; missing/failed opinions are reported without independently blocking a valid packet. Writer time requests receive a parent Reviewer decision. Native tools remain disabled. Reports, attributed blocking/advisory findings, deadline decisions and before/after resume versions are saved with the job under event version 21 and fetched through paged report routes rather than bulk workspace snapshots. Profile evidence, confirmed context, packet digests and export/submission approvals remain enforced. See [docs/deep-resume-review.md](docs/deep-resume-review.md).

- **App updates.** Production workspaces check public GitHub Releases when opened and hourly while open, with a manual check and device-local automatic-check switch in Settings > General. Installer preparation writes the exact commit to runtime/build-info.json; source launches read HEAD once. Commit ancestry distinguishes newer releases from identical builds and newer source checkouts; unknown or divergent identities never claim to be current. A persistent refresh icon at the end of the shared sidebar footer utility row checks manually and shows the result in a toast; an available update replaces it with a download icon that opens a popover with the exact Pitchcrew build release link and session dismissal; collapsed desktop and mobile drawer controls share the same state. Manual checks restore a dismissed available build; automatic checks preserve session dismissal. The refresh control shows checking progress and is disabled when installation checks are disabled. The workspace shell owns checking independently of the drawer lifecycle. Release links open in the system browser. Supported installed Windows/Linux builds offer explicit in-app download with progress, then main-process-confirmed installation and restart through electron-updater; automatic download, installation on quit and downgrades are disabled. Exact build-SHA feeds and architecture-specific updater metadata preserve the current release tags. The launcher stops only its owned daemon or a matching installed runtime service, recovers pre-exit failures and verifies the new daemon version/commit after relaunch through update-restart.json. External source daemons/services and AppImage services on temporary mounts require manual handling. Unsigned macOS builds retain manual DMG installation; signing is required for native Mac updates. The session-protected daemon checker uses no credentials or app content, rejects redirects, bounds responses/deadlines and deduplicates/caches requests. Development is manual only; PITCHCREW_UPDATE_CHECKS=0 disables checks. Direct daemon construction and smoke tests stay offline. See [docs/app-updates.md](docs/app-updates.md).

- **Usage analytics.** Production CLI launches use Pitchcrew's bundled public PostHog project token and EU ingestion host; `PITCHCREW_POSTHOG_TOKEN` and `PITCHCREW_POSTHOG_HOST` override them. Anonymous page views and successful user action counts are enabled by default, with a device-local opt-out in Settings > General synchronized across same-origin tabs. Current and legacy chat sends, conversation creation/continuation, question decisions, browser open/close and take/release control, and pipeline follow-up saves are tracked without content or entity IDs; browser inputs, streams and control renewals stay excluded. Main-process `downloading`/`installing` transitions count accepted user update requests once, excluding initial state/progress and requiring native installation confirmation. All app/landing events include the shipped root package version, a fixed renderer vocabulary and analytics schema 2; no runtime/model or commit identity is sent. The Diagnostics Coverage dashboard has reviewed error/request/run charts; unsupported ratings stay Not collected, and empty charts never imply healthy behavior. `PITCHCREW_POSTHOG_DISABLED=1` or an explicitly empty token disables installation telemetry. Development additionally requires `PITCHCREW_POSTHOG_DEV=1`. Direct daemon construction is unconfigured unless analytics options are supplied, keeping automated tests offline. The session-protected config endpoint and production CSP share the exact configured origin. The master usage preference gates all telemetry; diagnostics are a separate default-on preference and masked replay is separately opt-in, default off. Manual sanitized native exceptions, observed request/run measurements, numeric OTLP metrics, fixed operational logs, native runtime AI traces/spans and scoped MCP tool calls use reviewed modules. AI/MCP correlation uses fresh telemetry-only UUIDs, never app entity IDs. Wireframe replay masks text/attributes and blocks private app surfaces; native app heatmap capture stays disabled. Backend diagnostics remain bounded in memory behind a session-protected read route and are uploaded only by an opted-in renderer; origin-wide Web Lock leadership avoids duplicate shared observations. Native diagnostic transports abort on opt-out and do not retry. ## Invariants

These must stay true. A change that breaks one is a bug even if tests pass.

1. **No outward action without approval.** Anything that sends, submits, posts or emails must go through a gated MCP tool checking an unused approval bound to the exact payload. The check belongs in MCP, not in prompts or UI. Browser interactions use an exact-action gate bound to run, role, card, page fingerprint and upload contents. User-approved task site grants can authorize only the bounded preparation rules described above; submission, buttons, keys, dialogs and unfamiliar controls always require an exact user decision. Website-controlled scripts remain outside payload verification. Local export also uses its gate. Configured anonymous app analytics follows the device opt-out preference described above; it never carries application content or grants agents an outward-action bypass.
2. **Provider code stays in packages/adapters/.** The orchestrator, board and UI see only the runtime interface and normalized results/progress.
3. **Agents coordinate through the board only.** Internal messages and invocations are persisted board entities with scoped MCP tools; no adapter-to-adapter messaging and no shared runtime sessions across roles.
4. **Events are append-only and stay decodable.** Never rewrite or delete stored events. Schema changes add a new version and retain a decoder for every old version.
5. **Health checks have no side effects.** detect() never signs in, creates a session or spends tokens.
6. **Credentials stay with the runtime.** Pitchcrew never reads, copies or stores provider tokens. Adapters rely on the CLI's native authentication, including its environment configuration.
7. **The daemon binds to 127.0.0.1 only.** Keep origin/Host checks and user-session/run-capability boundaries intact.
8. **User data never enters the repo.** Profile notes, packets and DB live outside it. Tests use fictional fixtures and checked temporary cleanup paths.
9. **Rules change only with user approval.** Agents propose their own instruction/capability changes, or capability-gated targeted crew changes tied to saved reviews, in chat and never apply them directly. Only user settings (including adopting a reviewed default instruction update) or an explicit user decision on a proposal updates roles; skills are added or changed only through startup defaults, user settings or user-approved skill proposals; packet rules change only through user Settings actions, and agents can only read them.

## Card states

The normal workflow transition graph is packages/core/src/states.ts, kept free of zod so the UI can import it from @pitchcrew/core/states (Oxlint allows only type imports of @pitchcrew/core in the UI). Agents with `manageWorkflow` can also list board job summaries, move any job between any valid statuses through `pitchcrew_change_workflow`, and delete jobs in any status through `pitchcrew_delete_job`. An explicit `cardId` targets a board job; omitting it uses the attached card. `pitchcrew_bulk_move_jobs` and `pitchcrew_bulk_delete_jobs` accept 1–100 unique explicit card IDs with one shared reason (and one target status for moves), validate the complete input before any mutation, and return ordered per-job results plus succeeded/failed counts. Each job commits independently; busy or missing jobs fail without blocking the rest. Active workflow runs block these mutations. Status corrections invalidate unused packet/browser approvals and set a fresh effective timestamp; they never launch runs, export files or submit externally. Deletion appends a version 18 card tombstone, removes the current projection, invalidates unused approvals, cancels queued follow-ups and pauses attached routines while preserving history and exported files. Normal workflow execution and user board moves retain the transition graph. Typical flow:

```text
lead -> shortlisted -> drafting -> in_review -> agreed -> awaiting_approval
                            ^          |                        |
                            +-- changes_requested <-------------+
                                                                |
                                                            submitted
                                                                |
                                              screening -> interviewing -> offer
                                                  |             |
                                             rejected / withdrawn / ghosted
```

Scout evaluates an existing lead; the user shortlists it. Writer drafts, Reviewer agrees or requests changes. Approval exports files locally; the user submits independently or approves browser interactions, then verifies confirmation and records the outcome. Keep active-run ownership, revised-packet approvals, cancellation and interrupted-run recovery covered when modifying this flow.

An uncertain submission can continue through a separately approved browser dialog only when `submissionAttemptId` binds the same run, card, current exported packet and observed dialog. The consumed continuation approval is saved on the attempt. No click, keypress or navigation retry is allowed.

## Chat turn activity

Conversation transcripts initially load and render the latest 50 message/activity entries through the session-protected history route; the renderer retains the selected page rather than the full saved history. Older, Newer and Latest controls keep every entry accessible without mounting an entire history; older pages remain anchored while replies stream, and Latest restores live following. Browser find and text selection cover the displayed page. Chat shows each agent turn between its triggering message and answer, with public progress commentary, collapsed groups of tool steps, expandable outcomes, elapsed time and a Stop control in the composer. The composer has no separate progress strip; queued, paused and failed follow-ups use a compact, initially collapsed disclosure and running-only requests never appear there. Follow-up action choices appear only once the user drafts text or attaches files. All runtime chats observe scoped Pitchcrew tool calls at the daemon gateway; native assistant commentary is separated from structured reply previews, and supported native thinking signals show a phase marker without private reasoning text. `pitchcrew_report_progress` supplies up to eight public updates per chat turn. Tool arguments/results, secrets, browser inputs and manual takeover content are excluded. Live entries are bounded to 80 per run and commentary to 4,000 characters; truncation is visible. SSE merges run snapshots by ID and avoids re-sending unchanged activity with reply tokens. Completed, failed, waiting and cancelled turns persist their activity on the run when execution settles, with unconfirmed running steps marked interrupted; in-flight activity is memory-only and is lost if the daemon crashes. Agent conversation history remains final messages only. See [docs/chat-redesign.md](docs/chat-redesign.md).
