# AGENTS.md

Instructions for coding agents and contributors working on Pitchcrew. If a change makes anything here false, update this file with the change.

## What Pitchcrew is

A local-first job-search app with a crew of role agents. Pitchcrew starts runtime CLIs, gives them scoped MCP tools, and keeps shared state on a board. It does not implement a provider agent loop. See [README.md](README.md) for setup and the product view.

## Status

## Branch and release workflow

- `dev` is the integration branch for all development. Create every feature, fix, refactor, documentation and maintenance branch from the latest `dev`, and target `dev` when opening its pull request.
- `main` is the production release branch. Release through a pull request with `dev` as the head and `main` as the base; individual work branches must not target `main`.
- Every release pull request must include a version bump above the current `main` version. Prepare the bump on `dev` (directly or through a preparation branch merged into `dev`) before opening the release pull request. The root `package.json` supplies the installer version; keep workspace package versions in sync with it.
- Use semantic versioning (`MAJOR.MINOR.PATCH`): patch for fixes, minor for backward-compatible features, and major for breaking changes. Select and explain the bump in each `dev` → `main` release pull request based on the changes since the previous release.
- Include the chosen version, a summary of changes and validation in the release pull request. Required CI must pass before merging. Merging into `main` triggers the existing verified-installer publication workflow with `build-<full commit SHA>` tags.
- After a release, merge `main` back into `dev` so subsequent work includes the release merge and version history. Preserve the shared branches and their history.

## Stack

- Daemon, MCP and utility entry points use Bun and strict TypeScript and are included in the root typecheck. Vitest and build CLIs retain Node; bounded extraction/verification workers run in genuine Node helpers with the existing `tsx` loader and V8 heap limits, because Bun does not enforce `worker_threads.resourceLimits`. Never silently remove these limits. Electron compiles its main/preload and icon utility to JavaScript. The early UI theme initializer is TypeScript compiled by Vite to a blocking `/theme.js` asset in development and production. NSIS/PowerShell installer sources and the Next.js PostCSS configuration retain their required formats.
- Strict TypeScript, Bun 1.4.4 workspaces and Node 22.18+ or 24.11+ (supported LTS; Node 24 for packaging). Follow `.bun-version`, `bun.lock`, root `workspaces`, explicit trusted dependency builds, root engines and `patchedDependencies` (`patches/`; the `@shadcn/react` patch lets `scrollToMessage` take `keepPreviousPeek` and pin anchored, as the scroller pins a new last message; edit it with `bun patch`). Use `bun run <script>` for package scripts so Bun built-ins such as `test` and `build` do not bypass them.
- SQLite through better-sqlite3; versioned append-only events and projections.
- Document rendering engines and Playwright load on first document/browser use rather than daemon import. Snapshots containing frozen PDF artifacts still load the PDF reader to count their pages.
- Fastify serves the loopback HTTP API and production UI; request hooks enforce Host, Origin and local sessions before body parsing. Encapsulated route plugins compose the orchestration services. Development uses Vite through @fastify/middie; chat SSE retains Node response backpressure and disconnect cleanup.
- Official TypeScript MCP SDK with stdio transport and per-run capabilities.
- Oxlint for linting and Oxfmt for formatting. Do not add ESLint or Prettier.
- Oxc transforms / Rolldown in Vite, tsdown / Rolldown for Electron's main process.
- Vitest for unit, HTTP workflow, adapter contract, and actual MCP stdio tests.
- Chat suggestions use `@` for conversation participants, `$` for assigned skills, and `/` for Pitchcrew actions and skills. A small Lexical plain-text editor displays atomic inline references, preserving portable Markdown, IME, undo, file paste/drop and queue/interrupt behavior. Enter/Tab selects without sending, Escape preserves the draft, and no-match Enter never submits. `/attach`, `/job` and `/skills` open existing pickers; `/hiring-panel` retains managed review confirmation. Event version 22 persists server-validated reference IDs, occurrence ranges and label snapshots, with skill revisions/digests checked again before queued turns and deep-review stages. Shared runtime prompts receive only the explicit skill selections assigned to that role. Sent chips identify references rather than completed work and never rerun actions; deleted targets retain readable history. Agent replies also render canonical crew mentions as chips with saved display names, including live replies. File citations use manifest-provided identities for chat attachments, current Profile files and frozen packet approvals; they open the shared read-only file viewer and retain packet download gates. Missing targets explain their unavailability. Native copy preserves tokens, and code/links/emails/paths/prices do not select references. See [docs/chat-references.md](docs/chat-references.md).

## Code organization

- Use `const` arrow functions for standalone functions, callbacks, object actions and owned class methods. Pass shared backend context as an explicit first argument; context factories close over their instance. Preserve constructors, accessors and library-required prototype methods or dynamically bound hooks (Lexical nodes, dnd-kit modifiers and Vite plugin hooks).
- Keep React component files at most 100 lines after formatting. `bun run lint` checks every production TSX file.
- App disclosure controls must use the shared shadcn/Base UI `Accordion` family for grouped rows, `AccordionSection` for a standalone section, or `Collapsible` for custom triggers. Never add native `<details>`/`<summary>` to `packages/ui/src` or `packages/design-system/src`; `bun run lint` rejects them. Import from `@pitchcrew/design-system/accordion` or `@pitchcrew/design-system/collapsible`, preserve initial expansion and independent row expansion, keep form drafts mounted, and use `onOpenChange` for lazy preview resources. Do not recreate disclosure behavior with ad hoc buttons and hidden panels.
- Put each feature in a named folder with `index.tsx` as its public entry, `components/` for sections, `hooks/` for state/effects, and `__tests__/` for colocated tests. Use `types.ts`, `helpers.ts`, `constants.ts` and `api.ts` when the feature needs them; do not create empty placeholders.
- Keep components focused on rendering. Put pure transformations in helpers, network operations in API modules, and reusable stateful behavior in hooks. Name handlers as actions; reserve `use` prefixes for hooks.
- Share repeated domain labels, formatting and status calculations under `packages/ui/src/lib/`. Keep reusable shadcn primitives in `packages/design-system/src/components/` with explicit per-family package exports; app-specific AI Elements compositions stay under `packages/ui/src/components/ai-elements/`. The design system must not depend on app state, routes, daemon or domain models. Both app and landing import `@pitchcrew/design-system/styles.css` for Tailwind, shared tokens, primitive materials and source scanning; each owns its feature styles and font loading. See [packages/design-system/README.md](packages/design-system/README.md).
- Backend entry points preserve their public contracts and compose private modules by domain: `board/`, orchestrator `crew/` and `http/`, adapter `process/`, MCP `tools/`, connector `auth/` and computer modules. Keep transactions and approval checks together.
- Every persisted status has one lifecycle table in `packages/core/src/lifecycles.ts` (zod-free, also `@pitchcrew/core/lifecycles` for the UI): runs, crew tasks, per-recipient message deliveries, questions, packet and browser action approvals, submission attempts, deep reviews and their subagents, delegation rounds, role/skill proposals, profile updates and tracking signals, beside the job workflow graph. A table lists the statuses, the only moves between them and named status sets (`approvalLifecycle.is('open', status)`, `runLifecycle.is('live', status)`, `deliveryLifecycle.is('unsent', status)`); use a set instead of spelling a status list inline, and add a set when two call sites need the same list. `board.record` checks every write against its table inside the write transaction (`board/lifecycle.ts`): creation in any status and writes that keep the status always pass, and replay never rechecks history. Tests run with `PITCHCREW_LIFECYCLES=enforce` (set in `scripts/test-setup.ts`), where an undeclared move throws a `LifecycleError` naming the allowed moves before anything is appended; other daemons save the move, warn once per edge on stderr and record a content-free `daemon_lifecycle_violation` operational log (table name and the two statuses only, through consented diagnostics; see [operational logs](docs/analytics/logs.md)), so a move the tables missed never stops a user's work but still surfaces. A test fixture that must move a status backwards, such as making a finished run active again, uses `rewind` from `packages/orchestrator/test/helpers/rewind.ts`, which switches the board's `lifecycleMode` to `off` for that one write; product code never does. To add a move, change the table, cover the edge with a test and run `bun run docs:state-machines`, which regenerates the diagrams in [docs/state-machines.md](docs/state-machines.md); a core test fails while the document and tables differ. Job statuses are checked by `board.move` (the normal graph) and `board.crewMove` (the normal graph plus `reworkTransitions` in `states.ts`: reviewing an existing packet again from changes_requested, agreed or awaiting_approval, and a correction pass from in_review straight to drafting), with the same enforce/report modes; crew work saving a job with a new status uses `crewMove`, never a raw `record('card', …)`. User and `manageWorkflow` corrections record jobs directly and may set any status.
- Use ordinary Tailwind utilities for routine feature layout and spacing. App and landing base layers default borders (including pseudo-elements) to the theme hairline; shared border recipes must still specify a border color, and meaningful warning/error colors and keyboard focus stay explicit. Keep app-specific materials and complex selectors in ordered feature files under `packages/ui/src/styles/`; reusable primitive materials and shared motion live in `packages/design-system/src/styles/`. Never style descendants through a `:has()` on an ancestor (Tailwind `group-has-*`, `:root:has(…) …`, `.a:has(…) .b`) or test emptiness inside `:has()` (`:has(…:empty)`, `:not(:has(> *))`): Chrome rechecks such rules after DOM changes anywhere on the page, which once made every chat update restyle 350–850 elements. A `:has()` that styles the element it is on (`has-*` utilities) is fine. Use `:empty` or sibling selectors, or a rendered attribute: `createPresence` (`design-system/src/lib/presence.ts`) sets `data-has-<slot>` on a group's root (menu item action, code block header, an inset sidebar on its wrapper; in chat, `ChatView/presence.ts` marks the workspace's side panel and docked browser and the panel's question dock, welcome and hidden composer; apps import it from `@pitchcrew/design-system/presence`), `useRootFlag` (`lib/use-root-flag.ts`) sets page-wide flags on the document element (`data-app-bar`, `data-browser-expanded`), and `TabsList` sets `data-indicator` when it holds a `TabsIndicator`. Shared UI and AI Elements defaults use the `primitive:` variant: `styles.css` orders `base`, `primitives` and `components` below ordinary, unlayered caller utilities. Keep the utility import unlayered so the variant emits into the top-level `primitives` layer. Feature files load in the `components` layer, so they lose to unlayered third-party styles whatever their specificity: overrides of CodeMirror theme rules and Streamdown utilities must use `!important`. Theme tokens and named responsive thresholds live in `packages/design-system/src/styles/theme.css`; remaining feature CSS uses those thresholds through `@variant`. Oxfmt sorts classes, including `cn` and CVA arguments. See [docs/code-organization.md](docs/code-organization.md).

The UI has hot reload; restart the daemon after backend changes. The default data directory is ~/.pitchcrew, optionally PITCHCREW_HOME outside the repository. PITCHCREW_PORT defaults to 4417. Tests use temporary directories outside the repository and fictional fixtures under packages/*/test/fixtures/.

Local desktop and packaged smoke checks must stay hidden and never take focus. They use a hidden, non-focusable Electron window, background macOS activation and `capturePage` with `stayHidden`; evidence asserts the window was never shown or focused. Use `PITCHCREW_SMOKE_VISIBLE=1` only when the user explicitly requests a visible debugging run. Startup failures in hidden smoke mode go to stderr and exit with failure instead of opening a native dialog. Ordinary `bun run test` Chromium checks remain headless. Desktop smoke checks record native quit phases separately from parent-observed process exit and fail after a 10-second shutdown deadline; forced cleanup applies only to failed test children and never counts as success. See [docs/desktop-shutdown-performance.md](docs/desktop-shutdown-performance.md) for the isolated native exit diagnosis.

Vitest defaults to two workers, matching each CI shard, to keep browser and bounded-worker fixtures within host resources; `--maxWorkers` can override it. `expect.poll` waits up to 5 seconds, since fixtures that boot, reload or reopen a page share the host. Start slow fixtures in `beforeAll` rather than inside a test's 15-second budget: production daemons, first visits to Vite fixture pages and the first import of a route's page module. Test daemons from `packages/orchestrator/test/helpers/daemon.ts` listen on OS-assigned ports (`setup()` returns `port`; `reservePort()` holds one for direct `createDaemon` calls), so parallel files never share a fixed port; never hard-code a listening port. `setup()` also replaces every non-Demo adapter's `detect`/`listModels` with an unavailable fixture (`isolateRuntimes()`, undone by `cleanup()`/`restoreRuntimes()`), so no test runs an installed provider CLI; adapters a test already mocked keep that mock, and `nativeRuntimes` names runtimes a test deliberately detects from fixture executables. Vitest builds the production UI once when UI test files are selected. Full-app browser suites serve that build through the shared UI test fixture; backend fixtures serve APIs only, preserving the same Host, Origin and session checks. Development UI serving remains covered by dedicated Vite tests. The Vitest-only Demo fixture removes presentation delays while retaining asynchronous streaming and aborts; tests requiring in-flight work use explicit deferred gates. Ordinary development Demo timing is unchanged.

## Core concepts

- **Public landing page.** `packages/landing` is a standalone Next.js App Router website with Tailwind, Base UI/shadcn controls from `@pitchcrew/design-system` and locally served Fraunces/Source Sans 3. It shows the app's clay vocabulary at marketing scale (a crew roster whose run grooves replay one fictional job and stop on an ochre decision that holds Download, a packet sheet whose lines trace to profile quotes, a three-gate track, a sticky stage track beside a job card, chat turn, browser approval tray and board, the paused support crew, runtime pebbles, a bead stepper beside the platform chooser and an accordion FAQ) with labelled fictional data, keeps one app screenshot only for search metadata, and does not access the local daemon. Its Light/Dark/System menu uses a separate website preference, synchronizes across tabs and applies before paint. The download chooser reads validated public GitHub release assets with hourly caching and an explicit Releases fallback, with separate platform/architecture choices. Production anonymous visits, native page/session/pageleave events, numeric Web Vitals, public-page heatmap/frustration coordinates and download clicks use the public PostHog project, a closed property allowlist and Do Not Track; they are on by default with a quiet footer opt-out synchronized across tabs, and masked replay stays off; development stays offline by default. The default landing ingestion path `/relay` proxies only the fixed EU PostHog ingestion/assets hosts. Optional `NEXT_PUBLIC_POSTHOG_TOKEN`/`NEXT_PUBLIC_POSTHOG_HOST` override ingestion and an empty token disables it. `NEXT_PUBLIC_SITE_URL` supplies the canonical HTTPS origin, Open Graph URLs, website/application JSON-LD and image sitemap. Only configured production builds are indexable; development and Vercel previews emit noindex. Root lint/types and CI cover the site; Vercel publishing is separate from the desktop build/release workflow. See [docs/landing-page.md](docs/landing-page.md).

- **Agent and skill updates.** Crew and Skills sidebar badges count pending default-instruction and imported-skill update decisions, remain visible in collapsed/mobile navigation and clear only after applying or dismissing that version. Quiet notification entries open exact reviews; reading them never clears badges. Both pages keep dismissed versions in Updates and have URL-backed Updates only filters, shown while updates are listed or the filter is active. The mounted shell requests daily imported-skill checks while open; the daemon deduplicates clients and enforces a shared 24-hour interval per source. Settings > Updates has a synchronized automatic-check switch, and Skills/Settings offer Check now with a result toast. Local edits alone never count as an upstream update. Existing exact-preview approval replaces local skill text only after explicit review and keeps assignments; Keep mine dismisses only that version. Offline failures retain known notices and success times. Metadata/preferences live in skill-updates.json outside board events and participate in snapshot revision checks without loading skill projections; checks use the bounded public GitHub reader, share repository HEAD within each sweep and abort on shutdown. No agent gateway action or automatic adoption. See [docs/agent-updates.md](docs/agent-updates.md).

- **Career support.** Career Coach is an ordinary paused-by-default production chat role with seven bundled offline skills and chat starters for interview preparation, coached practice or mock interviews, debriefs, career planning, offer evaluation, company research and LinkedIn profile drafting. Scout also receives the company research skill. The local scoped `pitchcrew_check_linkedin_draft` tool measures exact supplied field lengths and skill counts in active chat; it reports sources and provisional text limits, preserves Unicode counting caveats and never publishes or verifies claims. LinkedIn drafts use Profile evidence plus user-supplied current text, remain in chat and are published by the user; supplied LinkedIn text never becomes verified Profile evidence automatically. It uses optional job context, Profile, attachments, source-linked own memory, read-only application search/Insights and supervised public browser research. Coaching summaries save automatically through existing memory tools; they never become verified Profile evidence. Offer support explains supplied compensation/contract terms and prepares employer/lawyer questions, with negotiation drafts only on explicit request for the user to send. Results stay in chat, with scoped career action plans additionally saved in Insights. Scout, Writer and Reviewer receive focused bundled assessment, tailoring and coverage-review skills preserving the 0–100 fit score, isolated drafting, exact claims, packet rules and independent review. Startup preserves edited/reassigned/deleted skills and existing roles. No extra workflow engine, report exporter, connectors, schedules or submission permissions are introduced. See [docs/career-support.md](docs/career-support.md) and [docs/hunter-skills.md](docs/hunter-skills.md).

- **Application process quality.** PDF/DOCX export verifies actual frozen bytes for readability and retained content, blocks essential failures per file and warns on heuristic layout findings; DOCX final layout remains unverified. Ordinary draft/review can perform one isolated Writer formatting correction and Reviewer recheck within the original budget; managed deep review uses its existing correction stage. Settings > Writing holds the revisioned shared guide, explicit preferences, chat-sourced before/after evidence, two-application learning, Disable/Undo and user-reviewed critic proposals. Isolated runs save the applicable guide snapshot; chat corrections queue through existing workflow tasks with exact draft digests and source isolation. Insights holds user-scoped source-linked career plans with three user-selected priorities, progress and stale-source checks. The optional `manageCareerPlans` capability plus `readApplications` gates agent refresh/progress; new Career Coach defaults receive it and existing roles retain settings. Version 25 persists guides, corrections and plans in board events. Existing weights/lessons remain user-only, and no schedules are seeded. See [docs/application-process-quality.md](docs/application-process-quality.md).

- **Deep resume review.** The job’s Deep review resume action and chat requests (including /hiring-panel) start the same managed flow after shortlisting and job-context confirmation. Writer creates an initial draft if needed, one Reviewer applies all seven original perspectives, Writer corrects supported findings, and Reviewer rechecks the complete packet. The bundled hiring-panel skill is assigned to Reviewer; importing a skill grants no tools. Optional targeted subagents inherit Reviewer’s runtime/model or use explicitly user-configured alternatives. Users can explicitly request additional perspectives in the start dialog or chat. The usual two-child allowance is a default rather than a total cap; audited Codex, Claude Code, OpenCode and development Demo adapters support up to four concurrent isolated child CLI runs per runtime per review. Children cannot delegate, approve or extend time; missing/failed opinions are reported without independently blocking a valid packet. Writer time requests receive a parent Reviewer decision. Native tools remain disabled. Reports, attributed blocking/advisory findings, deadline decisions and before/after resume versions are saved with the job under event version 21 and fetched through paged report routes rather than bulk workspace snapshots. Profile evidence, confirmed context, packet digests and export/submission approvals remain enforced. See [docs/deep-resume-review.md](docs/deep-resume-review.md).

- **App updates.** Production workspaces check public GitHub Releases when opened and hourly while open, with a manual check and device-local automatic-check switch in Settings > Updates. Installer preparation writes the exact commit to runtime/build-info.json; source launches read HEAD once. Commit ancestry distinguishes newer releases from identical builds and newer source checkouts; unknown or divergent identities never claim to be current. A compact teal update indicator appears beside Settings in the app bar or phone drawer footer only when an update is available, downloading or ready to restart. Opening it shows a popover with the version, up to five bounded plain-text changes, status details and explicit Download update / Restart to update actions; opening the popover never starts either action. Older releases show an unavailable-notes fallback, and the full release link stays in Settings. macOS/browser actions open the exact release page. Dismiss update notice is disabled during checking, download and restart, and returns focus to Settings; the app bar and phone drawer share the same state. Release publishing appends GitHub-generated changelog notes since the preceding published build and derives the versioned title from verified installer filenames without executing repository code. Manual checks restore a dismissed available build; automatic checks preserve session dismissal. Download progress fills the compact indicator and its accessible label; the popover remains available while busy, with its activation action disabled. The workspace shell owns checking independently of the drawer lifecycle. Release links open in the system browser. Supported installed Windows/Linux builds offer explicit in-app download with progress, then main-process-confirmed installation and restart through electron-updater; automatic download, installation on quit and downgrades are disabled. Exact build-SHA feeds and architecture-specific updater metadata preserve the current release tags. The launcher stops only its owned daemon or a matching installed runtime service, recovers pre-exit failures and verifies the new daemon version/commit after relaunch through update-restart.json. A truncated or damaged marker is cleared instead of failing the launch. External source daemons/services and AppImage services on temporary mounts require manual handling. Unsigned macOS builds retain manual DMG installation; signing is required for native Mac updates. The session-protected daemon checker uses no credentials or app content, rejects redirects, bounds responses/deadlines and deduplicates/caches requests. Development is manual only; PITCHCREW_UPDATE_CHECKS=0 disables checks. Direct daemon construction and smoke tests stay offline. See [docs/app-updates.md](docs/app-updates.md).

- **Usage analytics.** Production CLI launches use Pitchcrew's bundled public PostHog project token and EU ingestion host; `PITCHCREW_POSTHOG_TOKEN` and `PITCHCREW_POSTHOG_HOST` override them. Anonymous page views and successful user action counts are enabled by default, with a device-local opt-out in Settings > Privacy synchronized across same-origin tabs. Current and legacy chat sends, conversation creation/continuation, question decisions, browser open/close and take/release control, and pipeline follow-up saves are tracked without content or entity IDs; browser inputs, streams and control renewals stay excluded. Main-process `downloading`/`installing` transitions count accepted user update requests once, excluding initial state/progress and requiring native installation confirmation. All app/landing events include the shipped root package version, a fixed renderer vocabulary and analytics schema 2; no runtime/model or commit identity is sent. Desktop startup diagnostics measure native process start through the first rendered workspace, including packaged daemon preparation, once per process; they exclude OS click-to-process delay, reloads and window reopen/focus, freeze timing before analytics initialization and require both usage and diagnostic consent. A saved average/p95 startup chart tracks consented launches after release. The Diagnostics Coverage dashboard has reviewed error/request/run charts; unsupported ratings stay Not collected, and empty charts never imply healthy behavior. `PITCHCREW_POSTHOG_DISABLED=1`, CI, native smoke mode or an explicitly empty token disables installation telemetry. CI landing builds also use an empty public token. Development additionally requires `PITCHCREW_POSTHOG_DEV=1`. Direct daemon construction is unconfigured unless analytics options are supplied, keeping automated tests offline. The session-protected config endpoint and production CSP share the exact configured origin. The master usage preference gates all telemetry; diagnostics are a separate default-on preference and masked replay is separately opt-in, default off. Manual sanitized native exceptions, agent-reported bugs and missing MCP capabilities, observed request/run measurements, numeric OTLP metrics, fixed operational logs, native runtime AI traces/spans and scoped MCP tool calls use reviewed modules. AI/MCP correlation uses fresh telemetry-only UUIDs, never app entity IDs. Wireframe replay masks text/attributes and blocks private app surfaces; native app heatmap capture stays disabled. Backend diagnostics remain bounded in memory behind a session-protected read route and are uploaded only by an opted-in renderer; origin-wide Web Lock leadership avoids duplicate shared observations. HTTP failure logs preserve consented originating PostHog session/distinct IDs and genuine active/incoming W3C span context across the relay; missing HTTP identity never falls back to the uploading tab. No HTTP tracing provider/exporter is configured, and background logs do not acquire a replay session. Native diagnostic transports abort on opt-out and do not retry. The lazy no-external SDK disables app autocapture, automatic recording, surveys, flags, automatic performance/exceptions and person profiles; a closed event/property allowlist excludes app content, URLs, referrers, custom identifiers and error text. Analytics is best effort, does not queue disabled events and never changes agent capabilities or approval gates. Native dashboards, four endpoints, seven draft virtual models and two notebooks have activation audits under posthog/; eleven governed metrics remain unapproved proposals pending catalog write access. Five chart-only weekly emails use fixed Sunday 06:00 UTC, independently of Jerusalem DST. Engineering analytics uses an opt-in daily collector of public repository metadata (05:23 UTC, two-day overlap) and manual bounded backfills. Two observed-failure/startup alerts run daily at 06:00 UTC; checks and live repair evidence are recorded in posthog/audit-repair.json. New instrumentation requires updated builds and consented traffic. Agents encountering a Pitchcrew bug or missing MCP capability that blocks authorized work or causes avoidable manual effort must call `pitchcrew_report_technical_problem` before asking for help or ending their turn, without investigating or asking questions solely for reporting. Chat, workflow, isolated application and review subagents report a fixed area, bug/missing_capability kind, summary and expected/actual behavior, with optional generic steps, workaround and an existing related public MCP tool name; tools-free source extraction remains excluded. Exact sanitized duplicates are suppressed, with up to eight distinct reports per run capability; legacy area-only calls remain valid. ## Invariants

Deep-review stages retain local `deep-review-input.json` and `deep-review-output.json` run artifacts before semantic quotation validation. Exact resume Markdown quotation checks remain strict. Invalid parent quotations get at most one isolated repair per stage against current provenance gates; rejected stages remain failed and never populate successful before/after assessments. See [deep resume review](docs/deep-resume-review.md).

These must stay true. A change that breaks one is a bug even if tests pass.

1. **No outward action without approval.** Anything that sends, submits, posts or emails must go through a gated MCP tool checking an unused approval bound to the exact payload. The check belongs in MCP, not in prompts or UI. Browser interactions use an exact-action gate bound to run, role, card, page fingerprint and upload contents. User-approved task site browsing grants can authorize bounded HTTPS read navigation, hover and scroll, while separate preparation grants authorize only the bounded preparation rules described above; submission, buttons, keys, dialogs and unfamiliar controls always require an exact user decision. Website-controlled scripts remain outside payload verification. Local export also uses its gate. Configured anonymous app analytics follows the device opt-out preference described above; it never carries application content or grants agents an outward-action bypass.
2. **Provider code stays in packages/adapters/.** The orchestrator, board and UI see only the runtime interface and normalized results/progress.
3. **Agents coordinate through the board only.** Internal messages and invocations are persisted board entities with scoped MCP tools; no adapter-to-adapter messaging and no shared runtime sessions across roles.
4. **Events are append-only and stay decodable.** Never rewrite or delete stored events. Schema changes add a new version and retain a decoder for every old version.
5. **Health checks have no side effects.** detect() never signs in, creates a session or spends tokens.
6. **Runtime credentials stay private and user-controlled.** User settings can save allowlisted runtime secrets in the private credentials file; secret reads expose only source/configured status. Native account credentials remain with their CLI except the explicit managed Grok auth home and bounded private transport. Credentials, temporary auth interactions and secret backups never enter board events, snapshots, prompts, job run folders or agent tools. Adapters apply the selected runtime connection without broadening tool permissions.
7. **The daemon binds to 127.0.0.1 only.** Keep origin/Host checks and user-session/run-capability boundaries intact.
8. **User data never enters the repo.** Profile notes, packets and DB live outside it. Tests use fictional fixtures and checked temporary cleanup paths.
9. **Rules change only with user approval.** Agents propose their own instruction/capability changes, or capability-gated targeted crew changes tied to saved reviews, in chat and never apply them directly. Only user settings (including adopting a reviewed default instruction update) or an explicit user decision on a proposal updates roles; skills are added or changed only through startup defaults, user settings or user-approved skill proposals; packet rules change only through user Settings actions, and agents can only read them.

## Card states

The normal workflow transition graph is packages/core/src/states.ts, kept free of zod so the UI can import it from @pitchcrew/core/states (Oxlint allows only type imports of @pitchcrew/core in the UI). Agents with `manageWorkflow` can correct saved company/title/location/salary through `pitchcrew_update_job`, list board job summaries, move any job between any valid statuses through `pitchcrew_change_workflow`, and delete jobs in any status through `pitchcrew_delete_job`. An explicit `cardId` targets a board job; omitting it uses the attached card. `pitchcrew_bulk_move_jobs` and `pitchcrew_bulk_delete_jobs` accept 1–100 unique explicit card IDs with one shared reason (and one target status for moves), validate the complete input before any mutation, and return ordered per-job results plus succeeded/failed counts. Each job commits independently; busy or missing jobs fail without blocking the rest. Active workflow runs block these mutations. Status corrections invalidate unused packet/browser approvals and set a fresh effective timestamp; they never launch runs, export files or submit externally. Deletion appends a version 18 card tombstone, removes the current projection, invalidates unused approvals, cancels queued follow-ups and pauses attached routines while preserving history and exported files. Job-detail corrections require an active ordinary chat, default to its attached card and cannot target a different attached job. They preserve posting source, status, user bookkeeping and packet files, but clear stale fit, application context, packet review and form assessments and reject unused export/browser approvals. Only supplied fields change; an identical correction is a no-op. Other active job runs, owned cards and uncertain submissions block corrections; the calling chat is exempt. A corrected job needs a fresh user-confirmed brief and packet review through the existing isolated application flow. Normal workflow execution and user board moves retain the transition graph. Typical flow:

```text
lead -> shortlisted -> drafting -> in_review -> agreed -> awaiting_approval
                            ^          |                        |
                            +-- changes_requested <-------------+
                                                                |
                                                            submitted
                                                                |
                                              screening -> interviewing -> offer
                                                  |             |
```

Scout evaluates an existing lead; the user shortlists it. Writer drafts, Reviewer agrees or requests changes. Packet approval authorizes local export; choosing a submission method exports the files.
