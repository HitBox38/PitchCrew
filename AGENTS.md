# AGENTS.md

Instructions for coding agents and contributors working on Pitchcrew. If a change makes anything here false, update this file with the change.

## What Pitchcrew is

A local-first job-search app with a crew of role agents. Pitchcrew starts runtime CLIs, gives them scoped MCP tools, and keeps shared state on a board. It does not implement a provider agent loop. See [README.md](README.md) for setup and the product view.

## Status

## Branch and release workflow

- `dev` is the integration branch for all development. Create every feature, fix, refactor, documentation and maintenance branch from the latest `dev`, and target `dev` when opening its pull request.
- `main` is the production release branch. Release through a pull request with `dev` as the head and `main` as the base; individual work branches must not target `main`.
- Every release pull request must include a version bump above the current `main` version. Prepare the bump on `dev` (directly or through a preparation branch merged into `dev`) before opening the release pull request. The root `package.json` supplies the installer version; keep workspace package versions in sync with it.
- Use semantic versioning (`MAJOR.MINOR.PATCH`): patch for fixes, minor for backward-compatible features, and major for breaking changes. Select and explain the bump in each `dev` → `main` release pull request based on the changes since the previous release.
- Include the chosen version, a summary of changes and validation in the release pull request. Required CI must pass before merging. Merging into `main` triggers the existing verified-installer publication workflow with `build-<full commit SHA>` tags.
- After a release, merge `main` back into `dev` so subsequent work includes the release merge and version history. Preserve the shared branches and their history.

## Stack

- Daemon, MCP and utility entry points use Bun and strict TypeScript and are included in the root typecheck. Vitest and build CLIs retain Node; bounded extraction/verification workers run in genuine Node helpers with the existing `tsx` loader and V8 heap limits, because Bun does not enforce `worker_threads.resourceLimits`. Never silently remove these limits. Electron compiles its main/preload and icon utility to JavaScript. The early UI theme initializer is TypeScript compiled by Vite to a blocking `/theme.js` asset in development and production. NSIS/PowerShell installer sources and the Next.js PostCSS configuration retain their required formats.
- Strict TypeScript, Bun 1.4.4 workspaces and Node 22.18+ or 24.11+ (supported LTS; Node 24 for packaging). Follow `.bun-version`, `bun.lock`, root `workspaces`, explicit trusted dependency builds, root engines and `patchedDependencies` (`patches/`; the `@shadcn/react` patch lets `scrollToMessage` take `keepPreviousPeek` and pin anchored, as the scroller pins a new last message; edit it with `bun patch`). Use `bun run <script>` for package scripts so Bun built-ins such as `test` and `build` do not bypass them.
- SQLite through better-sqlite3; versioned append-only events and projections.
- Document rendering engines and Playwright load on first document/browser use rather than daemon import. Snapshots containing frozen PDF artifacts still load the PDF reader to count their pages.
- Fastify serves the loopback HTTP API and production UI; request hooks enforce Host, Origin and local sessions before body parsing. Encapsulated route plugins compose the orchestration services. Development uses Vite through @fastify/middie; chat SSE retains Node response backpressure and disconnect cleanup.
- Official TypeScript MCP SDK with stdio transport and per-run capabilities.
- Oxlint for linting and Oxfmt for formatting. Do not add ESLint or Prettier.
- Oxc transforms / Rolldown in Vite, tsdown / Rolldown for Electron's main process.
- Vitest for unit, HTTP workflow, adapter contract, and actual MCP stdio tests.

## Code organization

- Use `const` arrow functions for standalone functions, callbacks, object actions and owned class methods. Pass shared backend context as an explicit first argument; context factories close over their instance. Preserve constructors, accessors and library-required prototype methods or dynamically bound hooks (Lexical nodes, dnd-kit modifiers and Vite plugin hooks).
- Keep React component files at most 100 lines after formatting. `bun run lint` checks every production TSX file.
- App disclosure controls must use the shared shadcn/Base UI `Accordion` family for grouped rows, `AccordionSection` for a standalone section, or `Collapsible` for custom triggers. Never add native `<details>`/`<summary>` to `packages/ui/src` or `packages/design-system/src`; `bun run lint` rejects them. Import from `@pitchcrew/design-system/accordion` or `@pitchcrew/design-system/collapsible`, preserve initial expansion and independent row expansion, keep form drafts mounted, and use `onOpenChange` for lazy preview resources. Do not recreate disclosure behavior with ad hoc buttons and hidden panels.
- Put each feature in a named folder with `index.tsx` as its public entry, `components/` for sections, `hooks/` for state/effects, and `__tests__/` for colocated tests. Use `types.ts`, `helpers.ts`, `constants.ts` and `api.ts` when the feature needs them; do not create empty placeholders.
- Keep components focused on rendering. Put pure transformations in helpers, network operations in API modules, and reusable stateful behavior in hooks. Name handlers as actions; reserve `use` prefixes for hooks.
- Share repeated domain labels, formatting and status calculations under `packages/ui/src/lib/`. Keep reusable shadcn primitives in `packages/design-system/src/components/` with explicit per-family package exports; app-specific AI Elements compositions stay under `packages/ui/src/components/ai-elements/`. The design system must not depend on app state, routes, daemon or domain models. Both app and landing import `@pitchcrew/design-system/styles.css` for Tailwind, shared tokens, primitive materials and source scanning; each owns its feature styles and font loading. See [packages/design-system/README.md](packages/design-system/README.md).
- Backend entry points preserve their public contracts and compose private modules by domain: `board/`, orchestrator `crew/` and `http/`, adapter `process/`, MCP `tools/`, connector `auth/` and computer modules. Keep transactions and approval checks together.
- Use ordinary Tailwind utilities for routine feature layout and spacing. App and landing base layers default borders (including pseudo-elements) to the theme hairline; shared border recipes must still specify a border color, and meaningful warning/error colors and keyboard focus stay explicit. Keep app-specific materials and complex selectors in ordered feature files under `packages/ui/src/styles/`; reusable primitive materials and shared motion live in `packages/design-system/src/styles/`. Never style descendants through a `:has()` on an ancestor (Tailwind `group-has-*`, `:root:has(…) …`, `.a:has(…) .b`) or test emptiness inside `:has()` (`:has(…:empty)`, `:not(:has(> *))`): Chrome rechecks such rules after DOM changes anywhere on the page, which once made every chat update restyle 350–850 elements. A `:has()` that styles the element it is on (`has-*` utilities) is fine. Use `:empty` or sibling selectors, or a rendered attribute: `createPresence` (`design-system/src/lib/presence.ts`) sets `data-has-<slot>` on a group's root (menu item action, code block header, an inset sidebar on its wrapper; in chat, `ChatView/presence.ts` marks the workspace's side panel and docked browser and the panel's question dock, welcome and hidden composer; apps import it from `@pitchcrew/design-system/presence`), `useRootFlag` (`lib/use-root-flag.ts`) sets page-wide flags on the document element (`data-app-bar`, `data-browser-expanded`), and `TabsList` sets `data-indicator` when it holds a `TabsIndicator`. Shared UI and AI Elements defaults use the `primitive:` variant: `styles.css` orders `base`, `primitives` and `components` below ordinary, unlayered caller utilities. Keep the utility import unlayered so the variant emits into the top-level `primitives` layer. Feature files load in the `components` layer, so they lose to unlayered third-party styles whatever their specificity: overrides of CodeMirror theme rules and Streamdown utilities must use `!important`. Theme tokens and named responsive thresholds live in `packages/design-system/src/styles/theme.css`; remaining feature CSS uses those thresholds through `@variant`. Oxfmt sorts classes, including `cn` and CVA arguments. See [docs/code-organization.md](docs/code-organization.md).

The UI has hot reload; restart the daemon after backend changes. The default data directory is ~/.pitchcrew, optionally PITCHCREW_HOME outside the repository. PITCHCREW_PORT defaults to 4417. Tests use temporary directories outside the repository and fictional fixtures under packages/*/test/fixtures/.

Local desktop and packaged smoke checks must stay hidden and never take focus. They use a hidden, non-focusable Electron window, background macOS activation and `capturePage` with `stayHidden`; evidence asserts the window was never shown or focused. Use `PITCHCREW_SMOKE_VISIBLE=1` only when the user explicitly requests a visible debugging run. Startup failures in hidden smoke mode go to stderr and exit with failure instead of opening a native dialog. Ordinary `bun run test` Chromium checks remain headless. Desktop smoke checks record native quit phases separately from parent-observed process exit and fail after a 10-second shutdown deadline; forced cleanup applies only to failed test children and never counts as success. See [docs/desktop-shutdown-performance.md](docs/desktop-shutdown-performance.md) for the isolated native exit diagnosis.

Vitest defaults to two workers, matching each CI shard, to keep browser and bounded-worker fixtures within host resources; `--maxWorkers` can override it. `expect.poll` waits up to 5 seconds, since fixtures that boot, reload or reopen a page share the host. Start slow fixtures in `beforeAll` rather than inside a test's 15-second budget: production daemons, first visits to Vite fixture pages and the first import of a route's page module. Test daemons from `packages/orchestrator/test/helpers/daemon.ts` listen on OS-assigned ports (`setup()` returns `port`; `reservePort()` holds one for direct `createDaemon` calls), so parallel files never share a fixed port; never hard-code a listening port. `setup()` also replaces every non-Demo adapter's `detect`/`listModels` with an unavailable fixture (`isolateRuntimes()`, undone by `cleanup()`/`restoreRuntimes()`), so no test runs an installed provider CLI; adapters a test already mocked keep that mock, and `nativeRuntimes` names runtimes a test deliberately detects from fixture executables. Vitest builds the production UI once when UI test files are selected. Full-app browser suites serve that build through the shared UI test fixture; backend fixtures serve APIs only, preserving the same Host, Origin and session checks. Development UI serving remains covered by dedicated Vite tests. The Vitest-only Demo fixture removes presentation delays while retaining asynchronous streaming and aborts; tests requiring in-flight work use explicit deferred gates. Ordinary development Demo timing is unchanged.

## Core concepts

## Invariants

These must stay true. A change that breaks one is a bug even if tests pass.

1. **No outward action without approval.** Anything that sends, submits, posts or emails must go through a gated MCP tool checking an unused approval bound to the exact payload. The check belongs in MCP, not in prompts or UI. Browser interactions use an exact-action gate bound to run, role, card, page fingerprint and upload contents. User-approved task site browsing grants can authorize bounded HTTPS read navigation, hover and scroll, while separate preparation grants authorize only the bounded preparation rules described above; submission, buttons, keys, dialogs and unfamiliar controls always require an exact user decision. Website-controlled scripts remain outside payload verification. Local export also uses its gate. Configured anonymous app analytics follows the device opt-out preference described above; it never carries application content or grants agents an outward-action bypass.
2. **Provider code stays in packages/adapters/.** The orchestrator, board and UI see only the runtime interface and normalized results/progress.
3. **Agents coordinate through the board only.** Internal messages and invocations are persisted board entities with scoped MCP tools; no adapter-to-adapter messaging and no shared runtime sessions across roles.
4. **Events are append-only and stay decodable.** Never rewrite or delete stored events. Schema changes add a new version and retain a decoder for every old version.
5. **Health checks have no side effects.** detect() never signs in, creates a session or spends tokens.
6. **Runtime credentials stay private and user-controlled.** User settings can save allowlisted runtime secrets in the private credentials file; secret reads expose only source/configured status. Native account credentials remain with their CLI except the explicit managed Grok auth home and bounded private transport. Credentials, temporary auth interactions and secret backups never enter board events, snapshots, prompts, job run folders or agent tools. Adapters apply the selected runtime connection without broadening tool permissions.
7. **The daemon binds to 127.0.0.1 only.** Keep origin/Host checks and user-session/run-capability boundaries intact.
8. **User data never enters the repo.** Profile notes, packets and DB live outside it. Tests use fictional fixtures and checked temporary cleanup paths.
9. **Rules change only with user approval.** Agents propose their own instruction/capability changes, or capability-gated targeted crew changes tied to saved reviews, in chat and never apply them directly. Only user settings (including adopting a reviewed default instruction update) or an explicit user decision on a proposal updates roles; skills are added or changed only through startup defaults, user settings or user-approved skill proposals; packet rules change only through user Settings actions, and agents can only read them.

## Card states

The normal workflow transition graph is packages/core/src/states.ts, kept free of zod so the UI can import it from @pitchcrew/core/states (Oxlint allows only type imports of @pitchcrew/core in the UI). Agents with `manageWorkflow` can correct saved company/title/location/salary through `pitchcrew_update_job`, list board job summaries, move any job between any valid statuses through `pitchcrew_change_workflow`, and delete jobs in any status through `pitchcrew_delete_job`. An explicit `cardId` targets a board job; omitting it uses the attached card. `pitchcrew_bulk_move_jobs` and `pitchcrew_bulk_delete_jobs` accept 1–100 unique explicit card IDs with one shared reason (and one target status for moves), validate the complete input before any mutation, and return ordered per-job results plus succeeded/failed counts. Each job commits independently; busy or missing jobs fail without blocking the rest. Active workflow runs block these mutations. Status corrections invalidate unused packet/browser approvals and set a fresh effective timestamp; they never launch runs, export files or submit externally. Deletion appends a version 18 card tombstone, removes the current projection, invalidates unused approvals, cancels queued follow-ups and pauses attached routines while preserving history and exported files. Job-detail corrections require an active ordinary chat, default to its attached card and cannot target a different attached job. They preserve posting source, status, user bookkeeping and packet files, but clear stale fit, application context, packet review and form assessments and reject unused export/browser approvals. Only supplied fields change; an identical correction is a no-op. Other active job runs, owned cards and uncertain submissions block corrections; the calling chat is exempt. A corrected job needs a fresh user-confirmed brief and packet review through the existing isolated application flow. Normal workflow execution and user board moves retain the transition graph. Typical flow:

```text
lead -> shortlisted -> drafting -> in_review -> agreed -> awaiting_approval
                            ^          |                        |
                            +-- changes_requested <-------------+
                                                                |
                                                            submitted
                                                                |
                                              screening -> interviewing -> offer
                                                  |             |
                                             rejected / withdrawn / ghosted
```

Scout evaluates an existing lead; the user shortlists it. Writer drafts, Reviewer agrees or requests changes. Packet approval authorizes local export; choosing a submission method exports the files. The user submits independently or explicitly starts agent preparation, approves the exact browser submission, then verifies confirmation and records the outcome. Keep active-run ownership, revised-packet approvals, cancellation and interrupted-run recovery covered when modifying this flow.

An uncertain submission can continue through a separately approved browser dialog only when `submissionAttemptId` binds the same run, card, current exported packet and observed dialog. The consumed continuation approval is saved on the attempt. No click, keypress or navigation retry is allowed.

## Chat turn activity

Job activity saves a concise one-line description with each applied agent workflow result, attributed to the agent. Runtime prompts request a `changeSummary` describing the specific completed change (up to 300 characters); older results without it receive factual document/fit/review summaries. Each write keeps its own append-only event, including deep-review corrections and rechecks. Job-changing tools use their reason for the activity description.

Conversation transcripts initially load and render a target of 50 message/activity entries (up to 51 to keep a settled turn and its answer together) through the session-protected history route; the renderer retains the selected page rather than the full saved history. Older, Newer and Latest controls keep every entry accessible without mounting an entire history; while the reader follows the latest page, entries already shown stay put (the newest window never drops its oldest entries under the reader, and an entry that leaves the live data, such as a finished reply or turn, stays until a page fetched for the current revision arrives), and only user messages sent since the page opened are scroll anchors, because the shadcn scroller pins any unpinned anchor when the entry count holds steady; the scroller pins a new message only as the last entry, so `usePinSent` pins one the agent's turn rendered before, anchored like the scroller's own pin; older pages remain anchored while replies stream, and Latest restores live following. Browser find and text selection cover the displayed page. Chat shows each agent turn between its triggering message and answer, with one collapsed activity disclosure per turn, step/update counts, expandable outcomes, elapsed time and a Stop control in the composer. Live turns preview only the latest public update and step; settled turns keep a failed step, or otherwise the latest interrupted step, visible; a browser call stopped by the user's takeover is saved as an interrupted "Paused while you had control" step, summarized as "paused while you had control" (no count, since one takeover can span several waits) and never counted as failed, interrupted or kept as the settled issue. While a browser request waits (its step ochre from the moment it is asked, whether or not the agent has started waiting on it), the turn heading (one line in every state; its counts give way first) reads "Waiting for your OK" with the request's own title (ochre bead, no running timer), the chat header says "Waiting for your OK" and the participant bead turns ochre; while the user holds a running agent's page the turn and header read "Paused · you have control" (no timer) with ochre beads and an ochre Browser button dot, and the collapsed turn shows the last finished step rather than the call blocked on the user (while a request awaits their OK it previews that request's own ochre step). Browser steps are named like the tray ("Read the page", "Asked to click “Learn more”", "Clicked “Learn more”", "Typed into “Customer name”", "Waited for your OK to …") by the shared types-only `@pitchcrew/core/browser-action-labels`, and step labels never carry typed or chosen values. Each browser action is one row: the row that asked for an approval is carried out in place and moves to the latest position, while an overlapping duplicate call gets its own row and never overwrites the outcome. A request the user rejects through a decision reads "You declined to …" (never a failed step), and the agent is told the user declined rather than that the browser failed; requests invalidated by job, form or page changes keep the neutral wording. The waiting step is found once per turn: the current request's running row, or else only the latest asked row. Ordinary answers have a Copy action and timestamp below their content (hover/focus on fine pointers, persistent on touch); question records exclude Copy; normal prose is bounded to 76ch while tables and code retain the lane width. The composer has no separate progress strip; queued, paused and failed follow-ups use a compact disclosure that remembers collapse per device and reopens on new attention without remounting editors, shows the saved pause reason and reuses user-paused queue recovery and running-only requests never appear there. Follow-up action choices appear only once the user drafts text or attaches files. All runtime chats observe scoped Pitchcrew tool calls at the daemon gateway; native assistant commentary is separated from structured reply previews, and supported native thinking signals show a phase marker without private reasoning text. `pitchcrew_report_progress` supplies up to eight public updates per chat turn. Tool arguments/results, secrets, browser inputs and manual takeover content are excluded. Live entries are bounded to 80 per run and commentary to 4,000 characters; truncation is visible. SSE merges run snapshots by ID and avoids re-sending unchanged activity with reply tokens. Completed, failed, waiting and cancelled turns persist their activity on the run when execution settles, with unconfirmed running steps marked interrupted; in-flight public activity is checkpointed in one bounded SQLite row per run, immediately on first activity and at most every ten seconds thereafter; startup restores the last checkpoint and marks unconfirmed steps interrupted, while the latest uncheckpointed interval can be lost. Agent conversation history remains final messages only. See [docs/chat-redesign.md](docs/chat-redesign.md).

Chat history presents automatic same-run @mention forwards once, preserving saved messages and tasks; never-started queued, paused and failed inputs remain in the queue. Settled activity anchors to its own reply through shared server/renderer ordering. Pending questions have one answer form, with a compact transcript record; choices take natural height before bounded scrolling, with answer/actions outside the scroll area. Chat prose uses 14/20 type and hanging lists, tables keep one copy action, and one live announcer serves each conversation. Mobile job chat uses compact current-stage/next-action text and the existing job controls below the title.

Chat dispatch presentation uses the first saved run start for each user request, preserving original written timestamps and sharing server/live ordering. The queue remembers collapse per conversation/device, reopens only for new attention and offers full-text reading plus a reference-preserving multiline editor without changing the main draft. Interrupted or failed requests expose a gated Retry for the head request, preserving finished recipients; diagnostics remain behind Details. Non-head request resumes reject before mutation; explicit Send now and resume queue retains its reorder action. Head retry continues later never-started paused messages and stops for separate review at another attempted failure. User-paused queues expose Resume all, row menus avoid duplicate primary recovery, and successful recovery restores owned focus to the composer or Stop. Paused sends visibly say Sends after you resume with a matching accessible name. Messages held by a question retain an After your answer state on phones. An open question replaces the empty idle composer with Write a message for later; drafts, attachments and live Stop controls remain available. Automatic question handoffs focus the free-answer text field, never a one-click choice; unavailable targets keep the composer visible. Deleting the last draft text keeps that composer session visible across focus changes until question collapse, resolution or navigation. Question answer drafts, selections and response locks survive chat navigation in memory; own acknowledged responses clear their drafts; external resolution keeps a different unsent response in a recovery tray, and collapsing known questions never suppresses a future question. Failed answers retain text and owned focus; acknowledged typed answers restore owned text focus, while choice answers use a neutral focus target without opening a touch keyboard. An open dock suppresses the matching transcript question record. Failure follow-ups use the same controlled reveal-and-focus action. Historical run failures use quiet explanations and copyable diagnostics rather than alert roles. The single chat announcer reports coarse working/question state and observed failed/stopped transitions, never repeated commentary text or old failures on navigation; it starts empty on each conversation. The transcript log explicitly disables live announcements. A visibly open question suppresses only its matching transient toast; saved attention, the bell and unrelated notices remain intact.
Short windows compact secondary chat chrome and preserve readable history; bounded queue previews and whole-column scrolling keep controls reachable independently of the browser viewport. The active Scroll to latest control has its own strip clear of reading text. New devices use the Comfortable chat reading width; existing device width preferences remain intact. Chat tables have a semantic keyboard-scroll viewport and overflow-only cue, with one copy action below. Read-only Markdown task states use labelled shared checkboxes. New messages and queued edits share the strict reference-input serializer: display labels stay local while identity, trim-relative offsets and skill revisions go to the API.

Question responses distinguish an acknowledged mutation with a failed refresh from a rejected save; ambiguous responses retain their lock and offer a read-only status check before another POST. Shared job queue holds remain visible in attached conversations without local queued rows and link to the actual blocker. Worked durations exclude saved human-answer waits and idle continuation queue gaps. Reference decoration retains the default GFM pipeline; inline references preserve prose line height with larger hit areas. Question animation clips never own scrolling; the chat column reveals growing inputs and actions while respecting deliberate reading and active pointer presses.

Main composer text, atomic references and File objects live in a renderer-scoped store keyed by conversation, preserving drafts across page navigation. Sending snapshots the submitted payload and leaves a fresh editable draft; acknowledged completion consumes only that snapshot. Unconfirmed sends keep separate recoverable drafts without automatic retries or content-based receipt guesses; using a kept draft swaps whole payloads without discarding the other draft. Neither composer nor question drafts promise persistence after a full process restart. Definite HTTP question rejections retain the server's reason instead of claiming a retry will work. Choice confirmation keeps focus out of text entry, accepts a corrected digit during the short delay and excludes unrelated controls; custom single-answer typing clears a stale choice. Short coarse-pointer chats temporarily prefer the sidebar rail without overwriting the normal preference, phone view tabs share the row below the title, and short job sheets scroll identity, tabs and content together above the action footer. Chat list renderers own outside markers, including multi-digit ordered gutters; reference popovers use padded clay surfaces with a working Agent settings action for available mentions.
