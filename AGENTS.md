# AGENTS.md

Instructions for coding agents and contributors working on Pitchcrew. If a change makes anything here false, update this file with the change.

## What Pitchcrew is

A local-first job-search app with a crew of role agents. Pitchcrew starts runtime CLIs, gives them scoped MCP tools, and keeps shared state on a board. It does not implement a provider agent loop. See [README.md](README.md) for setup and the product view.

## Branch and release workflow

- `dev` is the integration branch for all development. Create every feature, fix, refactor, documentation and maintenance branch from the latest `dev`, and target `dev` when opening its pull request.
- `main` is the production release branch. Release through a pull request with `dev` as the head and `main` as the base; individual work branches must not target `main`.
- Every release pull request must include a version bump above the current `main` version. Prepare the bump on `dev` (directly or through a preparation branch merged into `dev`) before opening the release pull request. The root `package.json` supplies the installer version; keep workspace package versions in sync with it.
- Use semantic versioning (`MAJOR.MINOR.PATCH`): patch for fixes, minor for backward-compatible features, and major for breaking changes. Select and explain the bump in each `dev` → `main` release pull request based on the changes since the previous release.
- Include the chosen version, a summary of changes and validation in the release pull request. Required CI must pass before merging. Merging into `main` triggers the existing verified-installer publication workflow with `build-<full commit SHA>` tags.
- After a release, merge `main` back into `dev` so subsequent work includes the release merge and version history. Preserve the shared branches and their history.

- Daemon, MCP and utility entry points use Bun and strict TypeScript and are included in the root typecheck. Vitest and build CLIs retain Node; bounded extraction/verification workers run in genuine Node helpers with the existing `tsx` loader and V8 heap limits, because Bun does not enforce `worker_threads.resourceLimits`. Never silently remove these limits. Electron compiles its main/preload and icon utility to JavaScript. The early UI theme initializer is TypeScript compiled by Vite to a blocking `/theme.js` asset in development and production. NSIS/PowerShell installer sources and the Next.js PostCSS configuration retain their required formats.
- Strict TypeScript, Bun 1.4.4 workspaces and Node 22.18+ or 24.11+ (supported LTS; Node 24 for packaging). Follow `.bun-version`, `bun.lock`, root `workspaces`, explicit trusted dependency builds and root engines. Use `bun run <script>` for package scripts so Bun built-ins such as `test` and `build` do not bypass them.
- SQLite through better-sqlite3; versioned append-only events and projections.
- Document rendering engines and Playwright load on first document/browser use rather than daemon import. Snapshots containing frozen PDF artifacts still load the PDF reader to count their pages.
- Fastify serves the loopback HTTP API and production UI; request hooks enforce Host, Origin and local sessions before body parsing. Encapsulated route plugins compose the orchestration services. Development uses Vite through @fastify/middie; chat SSE retains Node response backpressure and disconnect cleanup.
- Conversation message sends accept an optional client UUID and persist a payload digest on the queued request in the same transaction as the user message (including managed review requests). Concurrent identical sends coalesce; committed retries replay their receipt without repeating interrupt actions or starting new work, and changed payloads return 409. A session-protected receipt GET reconciles ambiguous responses. The composer retains the UUID and original queue/interrupt intent for unchanged kept-draft retries; delegation sends retain their existing recovery behavior. Public run activity keeps at most 80 recent/active entries and checkpoints one bounded SQLite row per run at most every 10 seconds after the first update; startup saves interrupted steps through normal events. Abrupt termination may lose the latest 10 seconds of activity, never a committed send. See [docs/orchestrator-comparison.md](docs/orchestrator-comparison.md).
- Interrupt sends commit persisted queue/question cancellations with acceptance before aborting runtimes or changing live ownership; failed writes leave prior work running. Restored unchanged retries visibly lock their original Queue/Interrupt intent across both composers and keyboard shortcuts until the payload is edited. Chat stream readers reset a 45-second silence deadline on incoming bytes (including the daemon's 15-second heartbeats); silence cancels the reader and follows the existing disconnect/reconnect path, while caller abort closes it without reconnecting.
- Each chat stream connection has a separate 15-second response-header deadline. Explicit refresh and the first state after reconnect reconcile kept uncertain message receipts through bounded read-only lookups, without reposting. Queue admission and display select relevant Run/Task lifecycle states through an indexed query; controller-owned terminal cleanup, completed parents, reservations, paused failures and job/routine/delegation scope still participate. Activity eviction preserves failed/interrupted evidence before completed steps, and startup reads only checkpoint rows rather than deserializing historical runs again.

Delegation of an unchanged uncertain message is blocked until it is resolved or edited, without dropping its identity. Public receipt GETs return only request/conversation/submission identity, while internal replay retains the full request and digest. Numeric request ordering uses indexed ascending/descending bounds rather than scanning saved request payloads.

- **Packet.** Versioned resume.md, cover_letter.md, form_answers.md, note.md and claims.json. The job post is stored on its card. Users select Markdown, PDF and/or DOCX and a layout before requesting export approval. The default Formatted layout parses Markdown into a small document model (headings 1-4, paragraphs, bold/italic, bullet/numbered lists, links, rules, line breaks) and renders a one-column resume or cover letter template: PDF through pdf-lib with embedded Liberation Sans subsets from pdfjs-dist and URI link annotations, DOCX with Word heading styles, numbering and hyperlinks. PDF picks a font per character: Liberation Sans, then bundled Noto Sans Hebrew (OFL, `packages/packet/fonts`), then installed fonts read directly with fontkit from `PITCHCREW_FONTS`, the data folder's `fonts` folder and known Japanese/Chinese/Korean system fonts (an injectable `FontSearch`; tests use fixture fonts). Paragraphs follow the Unicode bidirectional algorithm (bidi-js): lines wrap in logical order and reorder for display, and right-to-left paragraphs align right with mirrored list indents. Arabic and Indic scripts stay DOCX only. DOCX marks right-to-left paragraphs and runs (`w:bidi`, `w:rtl`) and East Asian runs (font hint and language). It ignores YAML frontmatter and strips raw LaTeX layout commands without printing them. Plain text keeps the original literal Helvetica rendering; its PDF bytes match earlier exports. Neither layout fetches links, executes markup or silently drops words: HTML stays visible text and PDF names the first character no available font can show, with the kind of font to install; DOCX preserves Unicode. Identical input and available fonts give identical bytes (fixed dates, subset names, hyperlink IDs and ZIP timestamps). Page counts are derived from frozen bytes into the snapshot's `artifactPages`, keyed by artifact digest, so no event field is added; formatted DOCX stores the matching PDF layout's count in `docProps/app.xml`. Inbox and `pitchcrew_lint_packet` warn, without blocking, when the resume exceeds its one-page target. See [docs/packet-exports.md](docs/packet-exports.md). Frozen artifact bytes and SHA-256 manifest are reviewed, exported and uploaded through the existing gates. The lazy PDF.js preview renders every page from those bytes using only bundled worker/font resources, with cancellation and visible errors; no native PDF plugin or remote asset loading is needed. The lazy DOCX preview renders those exact bytes with docx-preview in a sandboxed iframe, with scripts, navigation links and remote resources disabled. Embedded images use data URLs; embedded fonts and HTML chunks are disabled. Closing or replacing a document discards unfinished renders; loading and errors are visible. Browser layout can differ from Word and the complete literal source text remains available.
- **Packet rules.** User house rules in `packet-rules.json` in the data directory, validated by the zod schema in `packages/core/src/packet-rules.ts` and evaluated by `checkPacket` in `packages/packet`. Kinds: word limit (body or all words), bullets per section, canonical lines and regex patterns with an optional match cap or required captured value. Severity is `error` or `warn`. Errors block Writer drafts, fail reviews and stop exports exactly as claim problems do; warnings are saved as `Warning: ...` review notes and never block. A missing file means the defaults (650-word resume and 500-word cover letter errors, counted as before); an invalid file fails closed with a blocking error. Patterns are capped in length and count, must compile, must not match empty text, and reject backreferences and nested repeats; rules read at most 20,000 characters per document. Writer/Reviewer workflow prompts include a rule summary; `pitchcrew_get_packet_rules` and `pitchcrew_lint_packet` let agents read rules and check drafts. Settings > Packet rules defaults to a guided editor for all four rule kinds, with shared draft validation, readable summaries and a persistent Save/Discard footer. Advanced JSON preserves unsupported or malformed imported drafts and holds import, export and reset actions. Only user HTTP actions behind the UI session (Settings > Packet rules) change rules; no events are appended. See [docs/packet-rules.md](docs/packet-rules.md).
- **Application source boundary.** Every managed application uses a structured job brief and explicit user confirmation of the complete brief and requirements. Captured posting markup remains untrusted; non-rendering parsing excludes explicit hidden attributes/styles and simple hiding selectors, while all source visibility remains unknown. Source extraction is a fresh, tools-free run with no profile, skills, memories or private accounts. Codex, Claude Code, OpenCode and development Demo support isolated extraction/fit/drafting/review; other runtime adapters fail closed for these purposes. Scout sees the extracted brief; Writer/Reviewer and custom agents using the dedicated Draft application entry receive confirmed reference data and verified profile evidence rather than raw card descriptions, prior conversations, source attachments, browser pages or handoff requests. Purpose-specific MCP tools and daemon allowlists enforce the boundary; native source-discussion sessions are never resumed for it. Missing required personal answers block Ready. Answers stay application-specific unless the user explicitly saves them to Profile. Confirmation, packet review and export receipts bind exact context revisions and packet bytes in event version 19; adopting context changes invalidates unused export/browser approvals. Unchanged extraction preserves matching user answers. Existing unsent packets need confirmation and fresh review when next used for export or browser submission. Browser form values require confirmed user answers, verified profile lines or reviewed packet prose and are rechecked before sending; private manual-input fingerprints remain transient to the browser. Context edits are blocked during active job work or uncertain submission. Past submission recording/resolution and old files/history remain available. Free-form chat prose, user copying and website-owned scripts do not receive a semantic safety guarantee. See [docs/application-source-safety.md](docs/application-source-safety.md).

- **Approval.** Exact packet snapshot and SHA-256 digest bound to a card, confirmed application context revision, independent packet review and export action. It is single-use; export calls enter the shared MCP gate. Agents have no approval tool. Successfully exported current packets allow workflow submission recording. Manual board status changes record user bookkeeping independently and do not authorize export or browser submission.

## Invariants

Deep-review stages retain local `deep-review-input.json` and `deep-review-output.json` run artifacts before semantic quotation validation. Exact resume Markdown quotation checks remain strict. Invalid parent quotations get at most one isolated repair per stage against current provenance gates; rejected stages remain failed and never populate successful before/after assessments. See [deep resume review](docs/deep-resume-review.md).

These must stay true. A change that breaks one is a bug even if tests pass.

1. **No outward action without approval.** Anything that sends, submits, posts or emails must go through a gated MCP tool checking an unused approval bound to the exact payload. The check belongs in MCP, not in prompts or UI. Browser interactions use an exact-action gate bound to run, role, card, page fingerprint and upload contents. User-approved task site browsing grants can authorize bounded HTTPS read navigation, hover and scroll, while separate preparation grants authorize only the bounded preparation rules described above; submission, buttons, keys, dialogs and unfamiliar controls always require an exact user decision. Website-controlled scripts remain outside payload verification. Local export also uses its gate. Configured anonymous app analytics follows the device opt-out preference described above; it never carries application content or grants agents an outward-action bypass.
2. **Provider code stays in packages/adapters/.** The orchestrator, board and UI see only the runtime interface and normalized results/progress.
3. **Agents coordinate through the board only.** Internal messages and invocations are persisted board entities with scoped MCP tools; no adapter-to-adapter messaging and no shared runtime sessions across roles.
4. **Events are append-only and stay decodable.** Never rewrite or delete stored events. Schema changes add a new version and retain a decoder for every old version.
5. **Health checks have no side effects.** detect() never signs in, creates a session or spends tokens.
6. **Runtime credentials stay private and user-controlled.** User settings can save allowlisted runtime secrets in the private credentials file; secret reads expose only source/configured status. Native account credentials remain with their CLI except the explicit managed Grok auth home and bounded private transport. Credentials, temporary auth interactions and secret backups never enter board events, snapshots, prompts, job run folders or agent tools. Adapters apply the selected runtime connection without broadening tool permissions.
7. **The daemon binds to 127.0.0.1 only.** Keep origin/Host checks and user-session/run-capability boundaries intact.
8. **User data never enters the repo.** Profile notes, packets and DB live outside it. Tests use fictional fixtures and checked temporary cleanup paths.
9. **Rules change only with user approval.** Agents propose their own instruction/capability changes, or capability-gated targeted crew changes tied to saved reviews, in chat and never apply them directly. Only user settings (including adopting a reviewed default instruction update) or an explicit user decision on a proposal updates roles; skills are added or changed only through startup defaults, user settings or user-approved skill proposals; packet rules change only through user Settings actions, and agents can only read them.

## Card states

The normal workflow transition graph is packages/core/src/states.ts, kept free of zod so the UI can import it from @pitchcrew/core/states (Oxlint allows only type imports of @pitchcrew/core in the UI). Agents with `manageWorkflow` can correct saved company/title/location/salary through `pitchcrew_update_job`, list board job summaries, move any job between any valid statuses through `pitchcrew_change_workflow`, and delete jobs in any status through `pitchcrew_delete_job`. An explicit `cardId` targets a board job; omitting it uses the attached card. `pitchcrew_bulk_move_jobs` and `pitchcrew_bulk_delete_jobs` accept 1–100 unique explicit card IDs with one shared reason (and one target status for moves), validate the complete input before any mutation, and return ordered per-job results plus succeeded/failed counts. Each job commits independently; busy or missing jobs fail without blocking the rest. Active workflow runs block these mutations. Status corrections invalidate unused packet/browser approvals and set a fresh effective timestamp; they never launch runs, export files or submit externally. Deletion appends a version 18 card tombstone, removes the current projection, invalidates unused approvals, cancels queued follow-ups and pauses attached routines while preserving history and exported files. Job-detail corrections require an active ordinary chat, default to its attached card and cannot target a different attached job. They preserve posting source, status, user bookkeeping and packet files, but clear stale fit, application context, packet review and form assessments and reject unused export/browser approvals. Only supplied fields change; an identical correction is a no-op. Other active job runs, owned cards and uncertain submissions block corrections; the calling chat is exempt. A corrected job needs a fresh user-confirmed brief and packet review through the existing isolated application flow. Normal workflow execution and user board moves retain the transition graph. Typical flow:

```text
lead -> shortlisted -> drafting -> in_review -> agreed -> awaiting_approval
                            ^          |                        |
                            +-- changes_requested <-------------+
                                                                |
                                                            submitted
                                                                |
                                              screening -> interviewing -> offer
                                                  |             |
                                             rejected / withdrawn / ghosted
```

Scout evaluates an existing lead; the user shortlists it. Writer drafts, Reviewer agrees or requests changes. Packet approval authorizes local export; choosing a submission method exports the files. The user submits independently or explicitly starts agent preparation, approves the exact browser submission, then verifies confirmation and records the outcome. Keep active-run ownership, revised-packet approvals, cancellation and interrupted-run recovery covered when modifying this flow.

An uncertain submission can continue through a separately approved browser dialog only when `submissionAttemptId` binds the same run, card, current exported packet and observed dialog. The consumed continuation approval is saved on the attempt. No click, keypress or navigation retry is allowed.
