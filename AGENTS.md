# AGENTS.md

Instructions for coding agents and contributors working on Pitchcrew. If a change makes anything here false, update this file with the change.

## What Pitchcrew is

A local-first job-search app with a crew of role agents. Pitchcrew starts runtime CLIs, gives them scoped MCP tools, and keeps shared state on a board. It does not implement a provider agent loop. See [README.md](README.md) for setup and the product view.

## Status

Working MVP with a shared browser/Electron UI, Scout/Writer/Reviewer runs, persistent named conversations, groups, visible read-only agent DMs, local agent memory and user file attachments with AI Elements, persistent routines and scheduled actions managed by users and agents, an optional per-user background service that starts the production daemon at login, capability-gated batch pipeline reviews with every-seat assessments and user-approved targeted crew changes, shared and role-assigned Markdown skills with skills.sh imports and user-reviewed chat suggestions, bounded agent-triggered follow-ups, user-approved role change proposals, watched profile maintenance proposals, source-backed Markdown packets with user-configurable packet rules and worker-bounded pattern checks, approval-gated local export, manual application tracking with user-reviewed bulk import of past applications, user-only learning signals with Insights, tag merge and previewed stale-submission cleanup, approval-gated local Chromium computer use, role-scoped read-only GitHub/Google Workspace connectors, capability-gated job discovery from user-saved public Greenhouse, Ashby, Lever, Comeet and Workable boards, and user-only Add job prefill from a single Greenhouse, Ashby, Lever, Comeet or Workable posting link. Demo is deterministic and available only with the daemon’s --dev flag; production seeds paused roles with role-specific recommended runtime/model/reasoning selected from the installed runtime checks and bounded model catalogs and preserves existing Demo roles as unavailable until the user selects a real runtime. Claude Code, Codex, Gemini CLI, OpenCode, GitHub Copilot CLI, Cursor Agent, Goose, Kiro CLI, Grok Build, Pi, oh-my-pi and Hermes Agent adapters are implemented; live provider runs are not part of automated verification. Discovery from other job sites, outreach, and whole-desktop control are deferred. Formatted and plain text PDF/DOCX packets, inspected form assessments and durable browser submission receipts are supported.

## Stack

- Strict TypeScript, Node 22.18+ or 24.11+ (supported LTS), pnpm 11 workspaces. Follow pnpm-lock.yaml and root engines.
- SQLite through better-sqlite3; versioned append-only events and projections.
- Fastify serves the loopback HTTP API and production UI; request hooks enforce Host, Origin and local sessions before body parsing. Encapsulated route plugins compose the orchestration services. Development uses Vite through @fastify/middie; chat SSE retains Node response backpressure and disconnect cleanup.
- Official TypeScript MCP SDK with stdio transport and per-run capabilities.
- React and shadcn/ui (Base UI primitives), Tailwind, Vite 8, shared browser/Electron renderer. Form selects share the app select wrapper and bounded menu height; date/time fields compose a shadcn Calendar (React DayPicker), Popover and Intent UI's registry TimeField (React Aria editable segments) while retaining local wall-clock values for the chosen timezone. Use shared controls instead of native selects, date/time dialogs or checkboxes. Compose with `render`, not `asChild`; `Button` defaults to `type="button"`, so submit buttons need `type="submit"`; menu labels sit inside `DropdownMenuGroup`.
- Motion for React supplies pointer-driven clay card tilt, board layout changes, proposal and approval decisions, new chat message reveals and question cards that spring from behind the message composer. Question cards return behind that input on resolution and become inert during exit; existing conversations and snapshot refreshes do not replay their entrance. Base UI surfaces use shared interruptible CSS transitions; frequent navigation and the command palette stay instant. Buttons use brief CSS press feedback. The shared `AppMotion` provider loads Motion features and respects system reduced motion; pointer-driven effects also use its reduced-motion context. Base UI retains dialog semantics, exit lifecycles, and focus management. Reduced motion removes surface translation and scaling while retaining short fades.
- TanStack Router with a typed code-based route tree and browser history for both renderers. The shared workspace shell stays mounted around lazy page outlets. Board lives at `/`; other views use named paths, chat threads use `/chat/<thread>`, skill assignments use `/skills?filter=<assignment>`, Activity search/type filters use `/activity?q=<query>&kind=<event-kind>`, and Insights filters use `/insights?tag=<tag>&from=<local-date-time>&to=<local-date-time>&sort=<count|positive|weight|tag>`. Profile, role, skill, and routine editors protect unsaved changes when closing, switching notes, navigating, or leaving the page. The daemon serves the SPA entry for deep links in development and production.
- Zustand owns the renderer workspace snapshot, shared UI state and API actions in `packages/ui/src/WorkspaceStore/index.ts`. Pages use selectors; the mounted shell owns polling and chat-stream cleanup. Route state stays in TanStack Router; component-only form state stays local.
- Sidebar categories (Workspace, Conversations, Crew and Recently opened) collapse independently through keyboard-accessible headings and remember their state in device-local storage. Categories start expanded; the desktop icon sidebar shows category shortcuts while preserving the expanded sidebar's preferences. Conversations live in this shared app sidebar, with search, new conversation, pin/unread/activity indicators, archived conversations and collapsible agent DMs. Its icon view offers Open conversations and New conversation. Chat has no inner navigation rail; mobile uses the app sidebar drawer, which closes when a conversation is selected. Creation uses a shell-owned dialog that remains open after the drawer closes.
- App-wide settings live at `/settings`, with URL-backed General, Accounts, Job sources, Runtimes, Packet rules and Local data tabs. Shared Base UI tabs provide linked tab panels and arrow-key navigation with automatic activation. Settings is pinned in the sidebar footer and available in the command palette. Theme and notification sounds share a device preference store and retain their existing local storage keys; the notification panel also offers a synchronized sound shortcut. Crew owns agent configuration; connected accounts and installed runtime checks live in Settings, with contextual account connection still available from Profile.
- Oxlint for linting and Oxfmt for formatting. Do not add ESLint or Prettier.
- Oxc transforms / Rolldown in Vite, tsdown / Rolldown for Electron's main process.
- Electron uses a paper-themed draggable title bar with native macOS traffic lights and Windows/Linux window-control overlays. Shared sheets and their backdrops fit below the title bar, including the mobile sidebar; macOS fullscreen uses the full viewport. Its sandboxed CommonJS preload synchronizes the renderer theme through a main-frame, origin-checked IPC channel without exposing Electron APIs to the page. Explicit Google PKCE sign-in links with a loopback callback, the exact GitHub and Google Workspace CLI installation pages, and exact Pitchcrew build release pages open in the system browser through a narrow main-process URL allowlist; other external navigation is denied.
- Vitest for unit, HTTP workflow, adapter contract, and actual MCP stdio tests.

## Code organization

- Keep React component files at most 100 lines after formatting. `pnpm lint` checks every production TSX file.
- Put each feature in a named folder with `index.tsx` as its public entry, `components/` for sections, `hooks/` for state/effects, and `__tests__/` for colocated tests. Use `types.ts`, `helpers.ts`, `constants.ts` and `api.ts` when the feature needs them; do not create empty placeholders.
- Keep components focused on rendering. Put pure transformations in helpers, network operations in API modules, and reusable stateful behavior in hooks. Name handlers as actions; reserve `use` prefixes for hooks.
- Share repeated domain labels, formatting and status calculations under `packages/ui/src/lib/`. Keep shadcn and AI Elements families under `components/ui/` and `components/ai-elements/` with explicit public exports.
- Backend entry points preserve their public contracts and compose private modules by domain: `board/`, orchestrator `crew/` and `http/`, adapter `process/`, MCP `tools/`, connector `auth/` and computer modules. Keep transactions and approval checks together.
- Use ordinary Tailwind utilities for routine feature layout and spacing. Keep materials, complex selectors and shared motion in ordered feature files under `packages/ui/src/styles/`. Shared UI and AI Elements defaults use the `primitive:` variant: `styles.css` orders `base`, `primitives` and `components` below ordinary, unlayered caller utilities. Keep the utility import unlayered so the variant emits into the top-level `primitives` layer. Theme tokens and named responsive thresholds live in `styles/theme.css`; remaining feature CSS uses those thresholds through `@variant`. Oxfmt sorts classes, including `cn` and CVA arguments. See [docs/code-organization.md](docs/code-organization.md).

## Commands

```sh
pnpm install
pnpm dev          # daemon + hot-reloading UI at http://127.0.0.1:4417
pnpm desktop      # build Electron main process; reuse a daemon, start the installed service or launch a development daemon
pnpm build        # UI and Electron main bundles
pnpm icon:build   # regenerate Electron's PNG from the canonical favicon SVG
pnpm start        # daemon serving built UI
pnpm service install # per-user login service for the production daemon; also uninstall, status, start, stop, logs
pnpm desktop:prod # build and launch Electron with built UI
pnpm desktop:package # build standalone installers for the current platform and architecture
pnpm test:packaged # verify the unpacked app with its bundled runtime and isolated data
pnpm test:installer # Windows: verify compiled NSIS process handling with isolated fixtures after packaging
pnpm browser:install # install Chromium for browser tools and tests
node scripts/convert-legacy-tracker.mjs <tracker.db> [applications.json] # legacy SQLite tracker to import JSON
pnpm test         # fixtures, loopback HTTP, MCP and isolated Chromium; no provider calls
pnpm test:desktop # isolated production daemon + actual Electron renderer check
pnpm lint         # Oxlint; warnings fail
pnpm format       # Oxfmt
pnpm format:check
pnpm typecheck
pnpm check        # lint, typecheck, tests, build
```

The UI has hot reload; restart the daemon after backend changes. The default data directory is ~/.pitchcrew, optionally PITCHCREW_HOME outside the repository. PITCHCREW_PORT defaults to 4417. Tests use temporary directories outside the repository and fictional fixtures under packages/*/test/fixtures/.

GitHub Actions CI runs on every pull request, pushes to main, merge queues and manual dispatches. It checks lint, formatting, types and production builds on Ubuntu, runs the full test suite with Chromium on Node 22 and 24, runs the actual Electron smoke test on macOS and Windows, and builds and checks standalone installers on Windows x64, macOS Apple Silicon/Intel and Linux x64. It uses the packageManager pin, frozen lockfile and read-only repository permissions without provider credentials. The aggregate CI check must pass all jobs. The GitHub main branch ruleset requires that check from GitHub Actions and an up-to-date branch, with no bypass actors. Main push runs have distinct concurrency groups so every push can produce a release; other superseded runs are cancelled. Test reports, desktop evidence and installers are retained for seven days. The separate Release workflow publishes those exact verified installer artifacts and SHA-256 checksums after successful main push CI under build-<full commit SHA> tags; only it has contents write permission and it never executes repository code. Reruns resume drafts or skip published releases. Windows and macOS installers are unsigned, and macOS builds are not notarized.

Standalone desktop packaging uses electron-builder with an isolated app directory and an unpacked runtime resource tree containing the source-layout daemon, production-only hoisted dependencies with workspace links materialized as directories, the build machine's Node 24 executable and Chromium. Native SQLite targets that Node runtime, so Electron native rebuilding is disabled. The packaged main process forks the bundled launcher, which retains daemon/service reuse and ownership rules; closing the app stops only its own daemon, and launcher IPC disconnect handles Electron crashes. Windows NSIS setup and uninstall use the scoped process check in `packages/desktop/installer/`: only the app executable and bundled Node/Chromium helpers under the selected or previous installation directories are closed, with a graceful window-close interval before forced cleanup. Existing installation directories expand Windows 8.3 aliases before comparison with executable paths. Downloads, the running installer/uninstaller and sibling paths are excluded; PowerShell profiles never load. Windows installer CI also runs the compiled NSIS macro against isolated fixtures, including short paths, without changing installed apps, registry keys or shortcuts. User data remains outside installation resources in the existing data directory. Source desktop launches keep their existing launcher. Build installers on each target platform/architecture with Node 24; provider CLIs/authentication remain separate.

## Core concepts

- **Runtime execution budget.** All production CLI and ACP workflow/chat turns have the same 30-minute wall-clock limit, including routines and crew follow-ups, independent of role, model, reasoning and computer-use permission. Both launch paths retain user cancellation and terminate the child process at the deadline. Timeout errors identify Pitchcrew as the source of the stop. See [docs/roles.md](docs/roles.md).

- **App updates.** Production workspaces check public GitHub Releases when opened and hourly while open, with a manual check and device-local automatic-check switch in Settings > General. Installer preparation writes the exact commit to runtime/build-info.json; source launches read HEAD once. Commit ancestry distinguishes newer releases from identical builds and newer source checkouts; unknown or divergent identities never claim to be current. A dismissible notice opens only the exact Pitchcrew build release page in the system browser. Downloads and installation remain user actions. The session-protected daemon checker uses no credentials or app content, rejects redirects, bounds responses/deadlines and deduplicates/caches requests. Development is manual only; PITCHCREW_UPDATE_CHECKS=0 disables checks. Direct daemon construction and smoke tests stay offline. See [docs/app-updates.md](docs/app-updates.md).

- **Usage analytics.** Production CLI launches use Pitchcrew's bundled public PostHog project token and EU ingestion host; `PITCHCREW_POSTHOG_TOKEN` and `PITCHCREW_POSTHOG_HOST` override them. Anonymous page views and successful user action counts are enabled by default, with a device-local opt-out in Settings > General synchronized across same-origin tabs. `PITCHCREW_POSTHOG_DISABLED=1` or an explicitly empty token disables installation telemetry. Development additionally requires `PITCHCREW_POSTHOG_DEV=1`. Direct daemon construction is unconfigured unless analytics options are supplied, keeping automated tests offline. The session-protected config endpoint and production CSP share the exact configured origin. The lazy no-external SDK disables autocapture, recording, surveys, flags, performance, exceptions and person profiles; a closed event/property allowlist excludes app content, URLs, referrers, custom identifiers and error text. Analytics is best effort, does not queue disabled events and never changes agent capabilities or approval gates. See [docs/analytics.md](docs/analytics.md).

- **Onboarding.** Fresh data directories show a two-screen introduction to the crew and approval flow, followed by a Board setup checklist for nonblank profile notes, enabled and available agents in all three workflow seats, and a real (non-demo) job card. Other pages show compact setup progress linking back to Board. Users can defer setup or explicitly finish it, and reopen the introduction from Getting started in the sidebar. Versioned onboarding preferences live in `onboarding.json` in the data directory and synchronize through snapshots across browser/Electron; they do not change board events, role capabilities or approvals. Existing databases default to deferred onboarding on upgrade.
- **Role.** A stored role with a stable safe lowercase ID, editable name/responsibilities, runtime, model, optional default reasoning, enabled flag, instructions and agent capabilities. One runtime agent belongs to each role. Users choose Create agent from Crew for a generic six-step setup: purpose, runtime, tools, skills, optional first routine and review. Creation commits the role, selected skill assignments and optional routine in one board transaction after asynchronous instruction writes; selected skill revisions and instruction limits are rechecked before commit. Shared skills apply automatically; adding assignments preserves existing assignments and provenance. The first routine defaults paused. Unsaved setup is protected on close and navigation. New custom roles default to chat and scoped tools with crew actions and connectors disabled. Startup supplies Scout, Writer, Reviewer, Submitter, Tracker, Documenter and Pipeline Coach, backfilling missing IDs within creation limits without changing existing or retired roles. Default instruction updates: `default-instruction-history.ts` in board records each seeded role's shipped default texts as whitespace-normalized SHA-256 revisions with release dates and summary lines. Read-only detection marks non-retired seeded defaults up to date, unedited (an earlier default), customized (base found in the role's own events or its explicit reviewed source) or unknown base; Crew cards, a Crew summary, notifications and role settings (changelog, paragraph/word diff, tool differences mentioned only) offer Use new default, Keep mine and Edit from new default. Edit from new default preserves unsaved editor text and saves the reviewed source in optional role `defaultInstructionBase` metadata. Adoption is a user settings change through `configureRole` with its active-run and limit checks; Keep mine stores the dismissed revision in `instruction-updates.json` in the data directory until a newer revision ships. Agents cannot see or act on updates, and nothing applies automatically. When you change a default's instructions in `default-roles.ts`, append its revision and summary to that history; board tests print the expected revision. See docs/roles.md. The four support defaults use chat with specialized capabilities and crew messaging; account connectors stay disabled and no schedules or watches are seeded. Production defaults start paused and prefer Codex GPT-6.1 Sol (Medium) for Scout/Submitter/Documenter, Claude Code Sonnet (High) for Writer, Codex GPT-6 Astra (High) for Reviewer/Pipeline Coach, and Codex GPT-6 Luna (High) for Tracker. Native catalogs take precedence over suggestions, with model fit before runtime preference and supported reasoning only; all production adapters participate in fallback selection. With no installed runtime, the preferred setup stays visible and paused. Use recommended setup in a built-in agent's settings rechecks every runtime and refreshes installed catalogs, filling the editor for the normal save action. Existing/customized/retired roles are never reset and runs never silently switch. Demo defaults stay deterministic. See docs/roles.md for presets and setup requirements. The optional workflow seat is Scout (fit), Writer (draft), Reviewer (review), or chat-only, independently of role identity; legacy built-ins retain their seats. Retirement preserves all history and prevents future runs/edits/ID reuse; it pauses responsible routines and cancels queued target tasks. Users can restore retired agents from Crew to the same identity paused, preserving settings, skills and history without resuming routines or cancelled tasks. Restoration is user-only and rejects active runs or settings writes. Active runs or settings writes block editing and retirement. Edit a role in a full-height side panel with a scrolling form and persistent save actions, opened from Crew, chat, the sidebar or command palette. Settings produce AGENTS.md and CLAUDE.md under the data directory. Each run gets an isolated subfolder and MCP configuration. Change instructions and capabilities through Crew settings or approve an agent’s proposal in chat; generated files are refreshed on startup.
- **Skill.** A user-managed Markdown instruction with a name, description and assignment to all agents or selected roles. Manage skills on the Skills page or open it from role settings. Skills display a Made by label: the GitHub source owner for imports, the originating role for approved custom agent suggestions, or You for user-created skills. Creator and repository names are searchable. Skill creation, updates and deletion append version 6 board events; deletion uses a tombstone so replay retains history. Each chat/workflow run snapshots its assigned skills into the runtime context, prompt and isolated `skills/<skill-id>/SKILL.md` files. Edits affect future runs only, including follow-ups; active runs retain their original copy. Import public GitHub-backed skills.sh links in the editor, review the loaded Markdown and assignment, then save; imported skills can explicitly refresh their source instructions. The bounded public GitHub reader uses immutable blobs, no credentials, no CLI installer and no redirects, and copies only SKILL.md instructions. Imported skills retain source URL, path and blob SHA. Skills grant no capabilities. Agents can discuss skills in user and crew chats and persist up to three suggestions per run through `pitchcrew_propose_skill`; suggestions appear in Crew work with their reason, assignment and exact instructions. Only a user decision adds the stored proposal snapshot, atomically with its decision; approval never re-fetches the source. Bundled scripts, assets, private repositories and non-GitHub skills.sh sources are deferred.
- **Notifications.** Saved agent messages, pending packet/browser/role/skill approvals and unanswered default instruction updates feed the notification bell, unread history and shadcn/Base UI Toast alerts. Transient action confirmations and failures use the same paper-themed toaster and three-toast stack, with success/error/info types; they do not enter saved notification history or play crew notification sounds. Up to three toasts stack in a portaled viewport; Base UI manages hover/focus timer pauses, keyboard access, announcements and swipe dismissal. Alert actions are typed router links. Message toasts show a headline and action only; attention toasts add a normalized preview of at most 96 characters and two visible lines. Full messages remain in chat. Notification context comes from saved entities: messages, user-input questions, packet/browser approvals, role/skill proposals and instruction updates each have their own icon and action label; questions use ochre, approvals teal, proposals and instruction updates plum and messages blue accents, using theme tokens in light and dark modes. Message and attention requests have distinct sounds; sounds can be disabled in the notification panel. History never plays alerts on initial load, and repeated snapshots/stream updates do not repeat alerts. Scoped `pitchcrew_notify_user` saves an exact user-facing message with `message` or `attention` priority (three per run), without granting approval, queuing work or pausing a run. Required input uses `pitchcrew_ask_user`: it saves a structured question, ends execution, and keeps the task waiting. Inline question cards and a collapsible answer area support single/multiple choices and custom text; the sidebar shows Waiting for you. Answers atomically save their provenance and queue only the asking agent’s continuation. Answered/cancelled questions leave attention history. Questions grant no approvals. Notification clicks open chat, Inbox or Crew, never decide requests. Notifications and sounds stay inside the browser/Electron renderer; no native OS alerts or notification IPC bridge are used.
- **Chat and crew tasks.** Named conversations have stable IDs, membership, a lead, optional persistent attached job, archive/pin state and per-participant runtime/model/reasoning overrides. Each field offers Use agent default: omitted fields inherit current Crew settings at the next turn, an empty participant configuration restores full inheritance, and explicit CLI default remains distinct. Legacy agent chats preserve their IDs and messages; `crew` becomes searchable read-only Crew history. Agent DMs are user read-only and grouped separately in chat navigation. Users and messaging-capable agents create groups; groups have no participant cap. Only the user removes members; removal aborts group work, cancels deliveries and revokes scoped reads. Leads invite members and visibly hand off leadership. Unaddressed user messages evaluate every eligible participant once; explicit @ids target named agents, and `silent:true` permits no reply. Ordinary agent replies do not wake the group. Mentions and scoped delegation use the existing six follow-ups per initiating request across related groups/DMs. Each agent has one active execution across its conversations; different agents can run in parallel; queued messages retain per-recipient delivery state, edit before first delivery, removal, reordering, Make next and explicit interrupt actions. Stop group cancels related branches and pauses saved user input; Stop agent targets its branch. Resume sends only unfinished deliveries. Continue first produces a read-only source-linked summary and refreshes the next session with compact context while retaining original messages. Queue recovery pauses user requests; interrupted agent tasks fail without automatic replay. Durable user questions survive recovery, retain waiting deliveries/tasks and hold dependent follow-ups through successive questions until continuation finishes. Independent participants and conversations remain available. Stop, removal and retirement cancel affected questions; saved answers with interrupted continuations remain resumable from the queue.
- **Chat files and runtime context.** Writable conversations accept up to five UTF-8 TXT/Markdown/CSV/JSON, PDF, DOCX, PNG/JPEG/WebP/GIF files totaling 10 MB per message, including file-only messages. The composer has one Add context menu for files and a searchable conversation job picker; selected files and the persistent job appear as clay chips above the message. The job can change or be removed before the first message, then remains fixed with a lock indicator. Drafts/files remain on send failure. Verified metadata persists in message events; bytes live under `chat-attachments/`, with bounded recent-file copies in isolated run folders and session-protected downloads. Scoped attachment reads require current membership and explicitly truncate at 50,000 characters/200 PDF pages; PDF/DOCX extraction uses bounded workers. Files are untrusted data, grant no capabilities and are not verified Profile evidence. SSE previews remain transient; only validated final replies persist, and cancellation clears unfinished text. Codex/Claude Code resume separate conversation/agent sessions with fresh per-turn MCP configuration and scoped tokens; other adapters reconstruct recent saved context. Session revisions cover role settings, skills, membership, lead, job, summary and memory changes; interruption/restart invalidates native sessions. Session directories are separate from isolated run folders. Native live steering is not exposed by current adapters; use the explicit interrupt fallback. Chat fills workspace width with aligned 46rem/72rem/full reading lanes selected in Settings > General > Appearance (Wide default), retained paper/ink light/dark materials and 3D clay effects. Conversation and Crew work share a clay view switch in the chat header, wrapping below the title and actions when the chat lane is narrow. Conversation settings, runtime, agent memory and agent defaults open in a right-side chat panel; the conversation stays usable beside it on desktop, and the panel overlays it on narrow screens. Agent defaults retain unsaved-change protection when closing, switching panels or navigating. Reasoning is accessible inside Conversation runtime, outside the composer.
- **Agent memory.** Each agent saves useful durable local notes with conversation/run/message provenance and recalls only its own notes on demand. Users inspect/edit/delete entries from chat or Crew, search content/tags, and view a collapsed Memory used list on replies. Edits/tombstones affect the next turn and invalidate affected native sessions; saved messages and removed participants' earlier memory remain. Memory grants no capabilities, changes no assigned skills or role instructions, and supplies no verified packet evidence. New conversation tools recheck membership and existing messaging/invocation/workflow permissions. See [docs/chat-redesign.md](docs/chat-redesign.md).

- **Routines.** Persistent one-time and repeating scheduled chat actions, managed on `/routines` or through scoped list/save/delete MCP tools from user or crew chats. An optional attached card scopes agent access. Start timestamps and IANA timezones support one-time actions, minute intervals and five-field deterministic cron calendar patterns; total run limits and end dates bound repeats. The daemon dispatches while listening (the optional background service keeps it listening after login), postpones busy/paused/unavailable roles and coalesces overdue repeats into one occurrence. It consumes occurrences before launch to prevent replay after crashes, and never retries failed/interrupted attempts automatically. Each routine defaults to one persistent conversation; users may select an existing writable conversation with the assigned agent and matching job scope. Each occurrence calls only its assigned agent using current saved role settings and skills, with the existing bounded follow-ups and outward-action approval gates. `manageRoutines` controls agent mutations; cross-role management also requires `invokeAgents`. The last agent editor's current capabilities are rechecked at dispatch; a user edit takes responsibility. Pausing/deleting stops future runs without cancelling active work. Deletion uses a tombstone. See [docs/routines.md](docs/routines.md).
- **Background service.** `pnpm service install|uninstall|status|start|stop|logs` (orchestrator CLI, `src/background/`) registers one per-user service that runs the production daemon (`--service`, built UI, never `--dev`) headless on loopback at login: a Task Scheduler task with a current-user logon trigger, limited token, `conhost --headless` action and restart on failure on Windows; a `gui/<uid>` LaunchAgent with RunAtLoad and KeepAlive on macOS; a systemd user unit with Restart=on-failure on Linux. No elevation. Definitions bake absolute Node/checkout paths, the resolved data folder and port as `--home`/`--port` arguments, and on macOS/Linux only a cleaned PATH; provider keys and other variables are never copied. Install is idempotent and restarts only for changed definitions; uninstall removes the definition, task file and logs. Service logs rotate at 5 MB under `background-service/` in the data folder. Platform logic goes through an injectable `ServiceHost`; tests use a simulated service manager and never call schtasks, launchctl or systemctl. A daemon claims `daemon.lock` in its data folder before opening the board and refuses a second daemon for that folder or a port where Pitchcrew answers; stale locks from crashes, restarts or reused process IDs are replaced. A service daemon waits and retries instead. `/api/health` reports `service`; the desktop launcher reuses running daemons, starts a matching installed service, and stops only a daemon it spawned. Settings > Local data shows read-only service state and CLI commands through a session-protected route. See [docs/background-service.md](docs/background-service.md). Claims and releases of daemon.lock are serialized using a separate empty daemon-lock.sqlite file; operating-system locks release automatically after a crash.
- **Starter skills.** On startup, the daemon loads missing starter skills from the latest public GitHub HEAD into the board before serving the workspace. The ten-entry schema-free `@pitchcrew/core/base-skills` catalog stores source paths and default role assignments, never supplied version hashes. Renamed catalog repositories use explicit canonical aliases (article-writing now uses affaan-m/ECC). Writing skills default to Writer, research/questioning to Scout, and humanizer/PDF review to Reviewer. Existing matching skills and deleted tombstones prevent automatic reinstallation; edits and renames preserve source identity. Missing or offline sources are reported on the Skills page and can be retried without restoring deletions. All loads resolve HEAD afresh and only immutable blobs are cached; proposals still approve their exact reviewed snapshot. Individual skills allow up to 50,000 characters; assigned skills still total at most 60,000 characters per role. view-pdf requires separate viewer tooling. Set PITCHCREW_SEED_SKILLS=0 to skip automatic seeding, as isolated automated tests do.
- **Connector.** GitHub CLI login (gh) with manual fine-grained tokens under Advanced, and Google Desktop OAuth or an optional saved Google Workspace CLI login provide read-only repository, Gmail, Drive/Docs, Sheets and Calendar access through the scoped MCP gateway. GitHub CLI connections store only an account binding: tokens stay with gh. User-requested connection checks gh availability and account identity; fixed GET calls run without a shell, are bounded and cancellable, and recheck the active account before reads. Disconnect does not log out gh. Status never invokes gh. GitHub CLI access follows its native login and has no per-repository installation picker; no Pitchcrew GitHub App is required. ## Invariants

These must stay true. A change that breaks one is a bug even if tests pass.

1. **No outward action without approval.** Anything that sends, submits, posts or emails must go through a gated MCP tool checking an unused approval bound to the exact payload. The check belongs in MCP, not in prompts or UI. Browser interactions use an exact-action approval bound to run, role, card, page fingerprint and upload contents; website-controlled scripts remain outside payload verification. Local export also uses its gate. Configured anonymous app analytics follows the device opt-out preference described above; it never carries application content or grants agents an outward-action bypass.
2. **Provider code stays in packages/adapters/.** The orchestrator, board and UI see only the runtime interface and normalized results/progress.
3. **Agents coordinate through the board only.** Internal messages and invocations are persisted board entities with scoped MCP tools; no adapter-to-adapter messaging and no shared runtime sessions across roles.
4. **Events are append-only and stay decodable.** Never rewrite or delete stored events. Schema changes add a new version and retain a decoder for every old version.
5. **Health checks have no side effects.** detect() never signs in, creates a session or spends tokens.
6. **Credentials stay with the runtime.** Pitchcrew never reads, copies or stores provider tokens. Adapters rely on the CLI's native authentication, including its environment configuration.
7. **The daemon binds to 127.0.0.1 only.** Keep origin/Host checks and user-session/run-capability boundaries intact.
8. **User data never enters the repo.** Profile notes, packets and DB live outside it. Tests use fictional fixtures and checked temporary cleanup paths.
9. **Rules change only with user approval.** Agents propose their own instruction/capability changes, or capability-gated targeted crew changes tied to saved reviews, in chat and never apply them directly. Only user settings (including adopting a reviewed default instruction update) or an explicit user decision on a proposal updates roles; skills are added or changed only through startup defaults, user settings or user-approved skill proposals; packet rules change only through user Settings actions, and agents can only read them.

## Card states

The authoritative transition graph is packages/core/src/states.ts, kept free of zod so the UI can import it from @pitchcrew/core/states (Oxlint allows only type imports of @pitchcrew/core in the UI). Typical flow:

```text
lead -> shortlisted -> drafting -> in_review -> agreed -> awaiting_approval
                            ^          |                        |
                            +-- changes_requested <-------------+
                                                                |
                                                            submitted
                                                                |
                                              screening -> interviewing -> offer
                                                  |             |
                                             rejected / withdrawn / ghosted
```

Scout evaluates an existing lead; the user shortlists it. Writer drafts, Reviewer agrees or requests changes. Approval exports files locally; the user submits independently or approves browser interactions, then verifies confirmation and records the outcome. Keep active-run ownership, revised-packet approvals, cancellation and interrupted-run recovery covered when modifying this flow.

An uncertain submission can continue through a separately approved browser dialog only when `submissionAttemptId` binds the same run, card, current exported packet and observed dialog. The consumed continuation approval is saved on the attempt. No click, keypress or navigation retry is allowed.
